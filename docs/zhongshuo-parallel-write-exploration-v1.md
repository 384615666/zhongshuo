# 众说 · 多 Agent 并行写入：探索记录（2026-09-26）

> **本文是探索记录，不是施工方案。** 任何据此开工的行为都不在本轮决策范围内。
> 本文记录用户 2026-09-26 的延期决定、本轮提出的三套候选方案、多方评审形成的共识与分歧，以及后续重新评估的入口。

## 0. 当前决定：延后

用户于 2026-09-26 确认：

> **暂缓多 Agent 并行写入增强的方案定稿与实现。当前以同一物理目录默认单写者完成协作闭环；保留并行能力目标及现有候选提案，后续结合真实任务和冲突样例单独评审。**

延后期间的默认工作方式：

> 多个 Agent 可以并行分析、规划和审查；同一个物理项目目录，同时只安排一个受管理的写入任务。其他修改任务按依赖顺序排队。

即：**并行分析、并行审查；串行写入**（与 §5.3「独立分析可以并行；同一原目录修改串行」一致）。

**下列基础保护不随并行增强一起延后**（即使只有一个写入 Agent 也仍然需要）：

| 保护 | 条款 |
|---|---|
| 修改前记录基线、不 stash/reset 用户已有改动 | §14.2 |
| 撤销仅在匹配 after_ref 时执行，禁止 `reset --hard` 等 | §14.5 |
| 停止进程树、确认旧进程停止后再交接写入 | §16.3、RT-07 |
| 启动恢复核对进程身份与存活状态，不凭 PID 认定 | §16.4 |
| 验证结果必须关联真实执行记录，模型自述不算 | §5.4、§14.3 |
| 目录锁域重叠检测（junction/父子项目） | §3.3、RT-09 |

延后不等于取消需求：`parallel_writers` 作为可选策略（§14.1）与按任务 worktree（§14.4）继续保留在设计里。

## 1. 问题起点

用户提出的原始方案：三个 MCP 接口（上传 / 查询 / 解除「别改这个文件」的公告），在提示词里要求 Agent 自己评估要改哪些文件，先查询、无占用则上传公告占位、占用则一分钟轮询等待，改完解除。

评审一致确认的四个缺陷：

1. **查询与占用分离**：两个 Agent 同时查到「无人占用」后都发公告，都开始改。必须合成一个原子操作。
2. **持锁等待扩展**：写到一半发现还要改别的文件时，若持有已占用文件去等新文件，会形成交叉持锁死锁。
3. **崩溃遗留占用**：Agent 中断后占用无人解除，需要租约/续期/运行代次。
4. **占用过期但旧进程仍在写**：单纯删除公告拦不住仍在运行的进程，这是 fencing token 问题（§11.4 已有对应机制）。

## 2. 本轮提出的候选方案

| 编号 | 方案 | 核心思路 | 出处 |
|---|---|---|---|
| A | Agent 自申报 + MCP 公告锁 | 运行时悲观锁，整组原子申请、禁止持锁等待扩展、宿主续期 | 用户原始方案 + 第一轮评审修正 |
| B | 意图声明 + 乐观并发 + 整合闸门 | 不锁，事后检测重叠，ChangeSet 冻结后过整合闸门再交付 | `docs/zhongshuo-parallel-write-intent-gate-v1.md` |
| C | 派发前 writeScope 分区 + 统一准入 | 协调者在 §5.2 契约里划写范围，daemon 派发前程序校验，运行时无锁 | 本轮第三个 AI 提出 |
| D | 按任务独立工作区 / worktree | 各任务独立目录，最后统一整合 | §14.4 既有设计 |

四者不是互斥关系，最终形态大概率是「C 的规划期分区 + D 的执行期隔离 + B 的整合期验证」的组合。

## 3. 已形成的共识

以下为本轮多方评审一致认可，可作为后续设计的前提：

1. **原子性不可省，但形态可以变**：A 的「服务端原子整组申请」和 C 的「统一调度器准入」是同一件事的两种实现——把分散的 Agent 抢占，改成集中准入。Atomicity 不会消失。
2. **公告值得保留，但降级为意图声明**：用于分工可见、重叠发现、依赖调度；**不构成互斥**，界面不得暗示「已声明 = 已占用」。
3. **文件不重叠 ≠ 逻辑不冲突**：A 改接口返回结构、B 按旧结构调用，文件完全不冲突但功能坏了。必须补跨任务的语义契约。
4. **跨任务需求传递是必需件**：光划分「谁能改哪个文件」，另一个 Agent 不会自动知道对方需要自己改什么。需要「提出需求 → 接收确认 → 交付版本 → 依赖方联调」的闭环。
5. **冲突解决前不影响原项目，是有前提的**：前提是独立工作区，或全部写入经过统一应用入口。「先随意并行写原目录、再靠事后闸门保证没覆盖」不成立。
6. **无锁不等于没有运行恢复问题**：崩溃留下的半成品、未退出的子进程、调度器重启后的运行识别、重试与旧运行的互斥——这些与有没有锁无关，必须处理。
7. **并行单位应是边界清楚的工作**：不应为了让所有 Agent 同时忙起来而强行拆分；公共契约未定时，先完成契约再并行。
8. **不得过度承诺**：外部编辑器和有本机权限的 CLI 不在协调范围内（§14.1、§6.2），任何方案都只能在该边界内描述能力。

## 4. 未解决的分歧（留给后续评审）

| 议题 | 一方主张 | 另一方主张 | 需要的判据 |
|---|---|---|---|
| 原目录并行是否值得投入 | 作为可选增强，成本低 | 只能做到协作约束，不如直接上工作区 | 真实任务中「无重叠且小」的并行任务占比 |
| 派发前分区能给出多强的保证 | 规划分区 + 事后记账即可 | 必须强制写入范围才谈得上互斥 | 能否实现受控写入入口（写入是否全部经应用） |
| 范围校验规则 | 所有子任务两两求交，重叠即拒绝 | 只检查**可能同时运行**的任务，有先后依赖的允许重叠 | 顺序开发改同一文件的真实频率 |
| 阶段屏障能否替代 worktree | 「API 不返回，连 grep 都够不着」 | 不能：§6.2 明确有本机读取权限的 CLI 仍可直接读文件 | runtime 权限档位实际约束能力（§9.6） |
| 成本断言 | 「无锁后零协调成本、低一个数量级」 | 无测量依据，且运行恢复问题未消失 | 实现后的真实测量，不得写进方案承诺 |
| `out_of_scope` 与 `attribution=ambiguous` | 可合并处理 | 必须分开：前者是改动超出批准范围，后者是归属不可靠 | §14.2 归属口径 |

## 5. 候选机制清单（均未定案）

以下机制在讨论中被提出且被认为有价值，但**均未进入施工**：

- **write_intent（修改意图声明）**：`declaredPaths` + `declaredInterfaces` + kind，用于可见性和依赖发现，不互斥。
- **跨任务变更请求**：请求方/接收任务/需要改变的行为或接口/状态（待处理·已接受·需讨论·已完成）/完成后对应成果版本。消息负责解释，状态负责让调度器判断依赖是否满足。
- **派发前校验器**：写范围两两求交、越出授权目录、依赖成环。检查范围必须覆盖**同一物理锁域内所有可能同时运行的任务**（含其他房间、其他已接纳计划、扩范围请求），不能只看一个 `delegate JSON`。路径比对复用 §3.3 canonical path，第一版范围限定为「明确文件 + 目录子树」，不做任意 glob 交集。
- **整合闸门**：ChangeSet 冻结后的检查点。必须按两种模式分别定义检查对象：原目录模式检查已保存的目录版本与归属不确定项；独立工作区模式检查候选整合结果。证据绑定具体版本，版本变化不沿用旧结果；未运行验证命令记「未执行」，不得表达成测试通过。
- **公共资源归属规则**：热点公共文件（类型定义、路由、API 客户端）归一个「基础结构任务」，其他任务 `dependsOn` 它，用依赖串行解决，不用锁。
- **运行期生命周期规则**：运行代次、进程确认、停止后的交接条件（§11.4、§16.3）。

## 6. 后续评估入口

**触发条件**（满足其一即重启评估）：

1. 真实使用中出现「多个独立编码任务经常排队，等待已经明显影响效率」；
2. 出现一次真实的并行写入冲突或覆盖事故，需要用真实案例判方案；
3. 受控写入入口或任务独立工作区具备实现条件，使「强制维持分区」成为可能。

**重启时的输入**：真实任务清单与拆分粒度、真实冲突样例、排队时长数据、当时 runtime 的权限约束能力。

**建议的评估顺序**（本轮讨论收敛出的顺序）：

| 阶段 | 内容 |
|---|---|
| 规划 | 协调者给出任务、写范围、接口需求和依赖；声明绑定计划版本 |
| 准入 | daemon 检查授权、依赖环，以及整个物理目录内可能同时运行的任务冲突 |
| 选择执行方式 | 根据范围、依赖和实际约束能力，选择串行 / 受控分区并行 / 独立工作区 |
| 整合 | 使用固定成果版本完成适配、合并和验证，结果绑定实际被检查的版本 |
