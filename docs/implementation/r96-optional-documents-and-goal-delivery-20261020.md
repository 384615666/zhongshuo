# R96：按需文档与按目标交付

用户反馈普通阶段发言几乎都变成“完整详情.md”，讨论结束后仍没有可用交付。本轮同时修正输出契约、成员交接和结束条件，适用于新运行；历史记录通过只读展示补充真实共识说明。

## 根因与 Raft 对照

- 根只读核对用户当时运行的 v31：冻结预算为 14 次且已用完；主持者在第三轮检查点判断没有新证据而停止讨论。最终仍有反对与未确认项，任务却显示 DONE，并生成了 13 份通用详情文件。输入框设置的 500 次属于后续输入，不会改变既有运行快照。
- v32 虽已取消程序提取摘要，仍过度要求每阶段提供总览和详情；这不符合用户“AI 判断是否需要文档”的意思。
- Claude/Codex 的常驻提示词确实通过各自 adapter 注入。实际偏差还来自阶段契约和调度：缺少交付就绪反馈，确认成员只看结论清单，后续阶段丢失互评理由和新增证据。
- 仓库保存的 `@botiverse/raft-daemon 1.0.17` 源码证据强调最短有用消息、必要时另附报告、停止前完成具体交接。它没有要求每次发言都写文档或固定聊满轮数。本轮对照的是仓库保存的源码证据，不声称验证了最新安装版 Raft 的实时输入。

参考：[Raft 源码证据](../raft-prompt-source-evidence-1.0.17.md)、[现有开发设计的研讨收尾规则](../zhongshuo-development-design-v1.md)。

## 最终行为

- DIRECT、私信和研讨的 AI 自行提供可见正文，以及 `document: null` 或 `{filename,purpose,markdown}`。普通交流零文档；有可复用方案、清单、报告价值时才写文件。正文和 Markdown 不进行程序提炼、重排或重新编号。
- 文件名使用模型给出的安全 `.md` 名称，附件在消息底部打开；真实生成的其他文件仍走原有 files 登记。最终公开回复复用当前整合稿的同一文档 artifact。
- 旧 `detailMarkdown` 只保留接收/读取兼容；新 provider schema 和提示词移除该字段。显式 `document:null` 优先，不复活旧详情。保存失败时保留模型原文作为可见回退。
- 互评、讨论、整合按阶段传递完整的模型理由、证据、建议和文档。独立分析仍隔离其他成员草稿；应用托管附件不冒充 canonical claim 来源。
- 整合前冻结议题、立场与成果身份。标记 resolved 必须有冻结名单中每位成员本轮明确同意；主持者不能覆盖反对或缺席。修订输入校验运行、版本、类型和实际 blob 字节哈希。
- 确认成员读取完整整合交付，逐条投票以外还提交 `ready / needs_revision / needs_user`。内部要求修改、剩余预算足够且尚未修订时，最多进行一次新整合和全新确认；旧投票保持绑定旧版本。
- 可交付但有业务待确认项显示“已交付·有待确认”；缺少必要用户/外部信息为 WAITING_USER/PARTIAL；内部未就绪且无法再修订为 BLOCKED/PARTIAL。问题、责任方或具体修改要求可见。缺席不借旧格式兼容冒充完成。
- 新运行默认预算按已有 withRevision 公式推导，两成员含检查点为 17 次。前后端一致；显式用户上限及旧运行快照保留。
- 房间根卡与最终消息分别展示交付和共识事实。交付定位绑定当前正式交付与最新运行，旧报告不覆盖新运行状态。原有 user_review 仍保留验收入口。
