## 2. 备份/升级/回退（可执行步骤）

**升级（旧→新程序）**：
1. 关闭运行中的应用（窗口关闭=优雅停机链：daemon.shutdown→有界等待→kill 兜底→desktop-shutdown.json）。
2. 用新版程序打开同一数据根——启动即检测待迁移并**先写迁移前备份**：
   `<数据根>/backups/state-pre-v<旧版本>-<时间戳>.sqlite`（VACUUM INTO 一致性快照）。
3. 升级后事实保持经工程演练实证（身份/消息/附件/任务/预算/审计/保护分类器）。

**限制（如实）**：仅当「已有数据+存在待应用迁移+程序传备份目录」才产生备份；无待迁移不新建。
当前 dev entry 传 backups/；若自定义宿主未传 backupDir，则升级前请自行复制数据根整体目录。

**回退（新→旧程序）**：**不是**让旧程序直接打开升级后的库（会被入口版本门拒绝——
SCHEMA_VERSION_UNSUPPORTED，不降版本号/不删记录）。正确步骤（r61 补外部资源）：
1. 关闭新程序。
2. 将升级前备份复制为新数据根的 `state.sqlite`（例：`restore-data/state.sqlite`）。
3. **连同外部资源一起恢复**：复制原数据根的 `blobstore/` 目录到新数据根（内容寻址
   `{sha256}.{txt|bin}`，逐文件完整性=文件名即内容 hash——工程演练阶段 D 实证 manifest/
   拷贝完整/恢复库附件实读/导出含附件 missing=0）。缺 blobstore 时 SQLite 计数虽对但
   附件预览/导出会如实失败——不冒充已恢复。
4. 凭据与数据根的关系：`local.token`（本机管道凭据）与远程 CA/设备凭据文件都在**数据根
   内**——整体复制数据根即随行；只复制 state.sqlite 的最小回退不含凭据，由新根首启重生成
   （**原数据根的凭据不换不重生**——演练逐 hash 核对不变）。
5. 用**旧版本程序**打开——可读、事实与升级前一致、可继续写入（演练阶段 C+D 实证）。
   边界：演练「旧程序」=当前源码+子集迁移形态；真实已发布旧 binary 的门/重定位能力
   不由此代宣布。

**更高版本保护**：旧程序误指新数据根 → 启动即拒（明确提示用对应版本或恢复匹配备份）；
不降级、不删除未识别迁移记录后继续写入。
