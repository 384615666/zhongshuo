# ADR-0010：有子进程 runtime 的可证明安全解除机制（受管生命周期）

日期：2026-09-29（第十轮）｜状态：**候选已评估，指定承载工作包，未批准施工**｜关联：§16.3/§16.4、RT-07、第九轮保守判定、`runtime-capability-matrix.md`

## 1. 问题（工程欠项，非设计边界）

当前对 per-turn（Claude CLI）与 shared（Codex App Server）进程模型，写入保护的解除路径**保守关闭**：
周期快照+现存树观察只能得出「未观察到存活后代」，无法排除「最后快照之后派生且中间父链已断」的
执行载体（第九轮实证盲区）。因此 daemon 侧没有任何自动解除手段，保护只能经
`recovery.releaseProtection` 的 `no-os-process`（无子进程模型的程序事实）解除；有子进程 runtime
的 UNKNOWN 保护将无限期保留，直到人工核对。

这是**全功能交付前需要解决的能力**（用户令第十轮四），不应被永久归为「已完成的设计边界」。
本文比较候选方案、给出评估结论与验收条件；**不阻塞当轮交付**，也不在缺乏新证据时重写周期快照
释放规则。

## 2. 候选比较

| 维度 | A. Windows Job Object（首选候选） | B. ETW/WMI 进程创建订阅 | C. 受管启动器包裹 | D. 维持现状（保守关闭） |
|---|---|---|---|---|
| 原理 | 受管执行进程在 spawn 时挂入 job（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`/显式终止）；job 句柄在 daemon 手里，**内核保证** job 内派生进程全部归属 job | 订阅进程创建事件流，维护「本机全部新进程→父链」的实时图，回查受管根的后代 | 所有 runtime 经由本产品 launcher 启动，launcher 回报派生 | 周期快照+现存树，仅产生观察 |
| 覆盖范围 | job 内**全部后代**（含 detached/中间父退出/快照间隔内派生）——派生即入 job，无盲区 | 全机进程，理论覆盖最全；但依赖事件不丢、缓冲不溢出 | 仅 launcher 直接子进程；CLI 自行 spawn 的工具进程不在包裹内——**不充分** | 有已证实盲区（第九轮反例） |
| 平台/依赖 | win32 原生（本项目首版平台 win32）；跨平台等价物：POSIX process group（`setpgid`+组信号）/`PR_SET_PDEATHSIG`（Linux）、macOS 缺直接等价（kqueue proc note 候选） | Windows 事件踪迹（管理员/性能开销）；跨平台无统一等价 | 无平台依赖但语义不足 | 无 |
| 失败回退 | spawn 时挂 job 失败 → 该次执行**不派发**（启动前置失败，如实报错）；job 查询失败 → 按 unknown 处理，保护保留 | 事件丢失/订阅断开 → 必须显式标记覆盖缺口，回退保守 unknown——复杂度集中在「如何证明没漏」 | 不适用（不解决根本问题） | 现状 |
| 解除证明强度 | `QueryInformationJobObject(JobObjectBasicProcessInformation)` 返回 job 内活跃进程数=0 + 句柄存活（证明期间无逃逸）→ 可作为**自动解除的充分条件**；父退出时 `KILL_ON_JOB_CLOSE` 兜底终止 | 从事件图推导「无存活后代」——仍是对模型的信任，弱于内核归属 | 无 | 不可解除 |
| 实现量级 | 小-中：spawn 侧包装（Node `process.platform==='win32'` 分支）+ 解除判定一处；不引入新服务 | 大：常驻订阅、缓冲管理、丢失恢复、噪声过滤 | 中，但收益不成立 | 0 |

**结论**：首选 **A（Job Object）**，按进程模型分别接入：
- per-turn CLI：每次 spawn CLI 时创建（或复用 per-turn）job 并把 CLI 挂入；
- shared server：daemon 首次拉起 server 时挂入 job，server 的所有派生随之归属；
- 历史/在途执行（升级前已启动、未挂 job 的进程）：**不追认**——继续走保守关闭路径，与第九轮
  语义一致；只有「登记时带有 job 归属」的执行才允许服务端自动解除。
- 跨平台（若首版外溢）：Linux process group 为 A 的等价实现；macOS 另评（届时允许按平台分列
  能力矩阵，不虚构等价）。
- B（ETW）保留为**增强候选**（如需要「job 外泄漏检测」审计），不作为解除依据的首版实现；
  C 评估为不成立；D 保留为降级路径（job 能力不可用时如实返回，不放宽）。

## 3. 验收条件（实现工作包完成时逐条验证）

1. **归属**：job 内派生 N 代（含 detached 孙、中间父退出）后，job 查询仍报告全部后代；
   升级前启动的进程不在 job 内，不得据此解除。
2. **解除**：job 活跃进程数=0 且句柄存活 → 服务端自动解除（写保护释放）成功；活跃>0 或查询
   失败 → 拒绝并保留保护，UI 说明原因。
3. **终止兜底**：持有 job 的 daemon 崩溃 → `KILL_ON_JOB_CLOSE` 使受管执行终止；重启后按
   no-os-process/进程登记对账收口。
4. **回退**：挂 job 失败的派发被拒绝且如实报错（不静默降级为无 job 执行）。
5. **能力矩阵**：按平台/进程模型分列「已证明可自动解除 / 不适用 / 未实现」；现有保守关闭
   语义的测试全部保持通过。
6. 全部验证在本地 fixture（真实 node 子进程）完成，零真实模型调用。
