## 2. 主要观察（有效结果，不重跑）

1. **DIRECT 严格输出合同的系统性合规失败（本批最重要发现）**：三次 DIRECT 各出现不同
   失败形态——A：合法 JSON 但附加 `conclusions` 键（严格 schema 拒绝未知键）；B：两次均
   纯 Markdown 散文（非 JSON）；C：JSON 被 \`\`\`json 围栏包裹。C 的修复 turn 为通过校验
   把内容削薄（交付仅 998 字符摘要，完整分析在被拒的首轮）。**机制对照**：DELIB 分阶段
   payload schema+编排内一次格式修复在同类模型上的表现为 24 次中 23 次直接成功、1 次
   格式失败经修复即过——单轮严格合同 vs 阶段化合同+修复的产品差异被真实放大。
   产品改进项（批次后，已实施部分见第六轮 commit）：DIRECT 输入合同字段用途说明+
   单层围栏规范化+修复绑定原输出（§四修复）。
2. **预算超发缺陷（A·DELIB 实发 10>9）与修复**：前置阶段（IND/CR/DIS/修复）派发不设
   占用预留——双成员争议讨论并行领取时各自读到旧账，第 10 个调用漏出。修复=occupyFrontForDispatch
   （`915f0db`）+回归测试。**准确表述**：B/C 两轮实测走的是**无争议路径**且未超限（各 7≤9）；
   事故分支（争议+修复+并行竞争派发）的修复有效性目前依赖**本地回归证据**（cap=6 用例+
   第六轮新增 cap=9 同构场景用例）——不为补真实验证额外调用模型。A 的第 10 次调用如实
   入账（执行偏差记录，不抹除）。
3. **C 组可发现性阻塞（两侧对称；原定目标未达成）**：日志文件名 `app-week.log` 不可猜；
   两侧模型自述仅有按已知路径读取能力（无目录枚举/Glob）。**证据分层（第六轮修订，先取证
   后定论）**：CLI 参数声明=adapter argv 含 `--allowedTools Read,Glob,Grep`（observed，
   回放/manifest 双证）；**运行时 CLI 实际启用的工具清单=未捕获（unknown）**；**发给模型的
   工具定义/输入提示=不可见（unknown——CLI 内部）**；实际工具调用=两側 tool.started 仅
   Read（observed）。因此「仅 Read 事件」**既不能证明 Glob 可用、也不能证明只是模型认知
   错误**——根因保持在 unknown，改进项照做（后续版本：输入合同明示工具面+程序提供经授权
   的受限文件清单，两模式一致规则，不倒改本批实验条件）。
   **C 组结论（如实）**：原定「一周日志异常分析」目标**未达成**（无内容产出）——受阻处理
   （DIRECT 2 次调用即如实阻塞；DELIB 耗 7 次做 60–90 候选名探测后 unanimous 上报）只作为
   **附加诊断维度**记录，不替换原目标使样本看起来通过。
4. 争议分支真实出现（A·DELIB DIS×2）——正是预算缺陷的触发场景；B/C 实测无争议分支
   （各 7 次收口）。修复 turn 消耗：A·DELIB 1、C·DIRECT 1，均一次成功（C 为本批唯一
   DIRECT 正式交付）。
5. 全批无 UNKNOWN、无截止中断、无停止链路触发；DIRECT 侧 5 次 FAILED 均为 outputInvalid
   （非链路故障——派发/校验/记账链路六侧核验全过）。
