## 2. P1：第一次从真实旧版升级仍遗漏草稿/未知账本

当前 loader 先按新 `v2.<dataRootId>|<user>` 键初始化；新键缺失时即持久化空态，再扫描旧键。

两个缺口：

1. `collectLegacyPersistKeys` **跳过 dir===currentAppDataDir 的旧键**，注释声称“正常路径由 init 读过”，但 init 实际只读新的逻辑身份键，未读当前绝对路径旧键。
2. v3/v4 从未创建 root-identity，旧快照也没有内嵌 dataRootId。复制到新目录后 v5 生成随机新 ID；再读取旧目录标记只能得到 null，不能证明旧快照同根，所以不继承。新格式根未来复制成功，**不能证明真实旧格式首次升级成功**。

独立 UI 反例：

- 冻结 v4 仅记录提交已成功，回执受控丢失；旧 key 中 payload.v=1、embeddedRootId=null、pending commandId=`cmd_214etuyy`，服务消息 1 条。
- 切冻结 v5：生成逻辑 key，原旧 key 保留；但正文为空、未知横幅消失、新 pendingCommands=[]。
- 普通再发相同正文：服务消息 **1→2**，工程零模型调用。

要求：

- 覆盖真实 v3/v4 的**旧键无内嵌身份/旧根无标记**状态；同目录升级和跨目录复制分别实现，不依赖用户旧程序没有生成过的标记。
- 采用有明确来源与同用户/同数据集校验的继承机制；例如可信导入过程记录来源并在副本准备身份与旧键映射，或准确的兼容迁移。保全旧键与原目录，不能为了迁移去修改唯一用户原件。
- 不盲扫导入无关根、不信任任意声称同根的字段；但不能把确属用户选定旧根的历史仅写成“不合并”诊断就正常开放新发送。
- 继承待完成/暂时读取失败必须有可见状态、重试路径和必要发送防重。**先写空 v2 键、下次因 hadKey=true 永久跳过继承**的窗口要关闭；在途恢复与普通草稿冲突各自处理，空的新键不应成为“迁移完成”证据。
- 普通草稿 24h TTL；未知账本/queued 全部完整保留原 commandId/参数/目标/阶段，不按草稿 TTL 清理、不自动发送。多个同目标未知信封按 commandId 保留并去重，不能只按 at 保留一个就丢另一个不同命令。
- README 清楚区分“已有新逻辑身份的数据未来移动”与“第一次从旧 v3/v4 升级”。现在不要要求用户按现有 v5 步骤迁移。

## 3. P1 配套：继承版本校验与身份原件保全不能绕过

### A. 未来版本快照被继承路径接受

`mergeInheritedSnapshots` 只检查 JSON/plainObject/条目字段，**没有检查 data.v**；直接初始化路径的版本/隔离规则被旁路。

自有同根负例：在候选旧键放入内嵌当前 root ID、`v:999` 的完整快照，删除新逻辑键后重载。结果：

- `R68-FUTURE-VERSION-DRAFT` 进入正文，未知信封可见；
- 没有“不受本程序支持”提示，也没有 quarantine key；
- 原未来版本旧键虽仍在，但不支持格式已被当作当前格式消费。

说明：当前 **PERSIST_VERSION 仍为 1**，`v2` 是命名空间编号，不能混称快照格式已升级为 v2。

要求把兼容格式白名单、整体/条目损坏校验、隔离失败保全锁定、写失败中断、无 TTL 未确认账本规则用于**所有读取与继承路径**。未来版本不得恢复/重发其未知信封；原件逐字保存，保全失败不覆写、不冒充正常。

### B. 结构不合法的身份标记被自动覆盖

自有 marker=`{"id":"short","createdAt":1}`；正式 `app.identity` 返回 ok 并覆写成新随机 ID，originalPreserved=false。

这会把同一数据根变成新的逻辑根，旧逻辑 key 无法再按原 ID 读取。JSON 语法损坏与字段不合法要统一考虑；不能只处理 JSON.parse 抛错的情况。

要求：仅标记确实不存在时初始化；已有标记无效/未知格式/不可读时保全原件并如实给出健康状态及显式恢复路径，不静默换 ID。创建/落盘原子性、崩溃中断、拒写与复制一致性均验证；不能给出假稳定 ID。

## 5. P2：新增成员的项目边界与只读守卫

### A. 归档项目仍能正式创建成员

独立正式链：新建自有项目 → project.lifecycle archive 成功（status=archived）→ member.create 成功；成员计数 **1→2**。

member.create 只 SELECT 项目 id，没有归档/移除状态守卫。按既定“归档保留历史与只读/移除仅解除关联”规则，新增实体不能绕过状态边界。

补服务端守卫并使旧回执重放同样受当前状态约束；UI 相应禁用/说明。验证归档/移除、并发归档、旧请求/重放、失败零成员/名单/派发副作用，恢复后再允许正常新增。名称全空格等正式 API 校验也要与界面一致。

### B. 弹窗使用实时 activeProjectId

AddMemberModal 没有捕获打开时 projectId，而是直接 useStore(activeProjectId)。**受控成员页项目筛选事件**切 A→B 后，旧输入仍在，最终 member.create 写 B；DB 与发出参数都留证。

如实边界：正常标题栏项目切换会卸载该页，旧框被关闭，已独立确认；受控筛选事件在遮罩下触发，**不声称用户可用鼠标穿过遮罩点击底层筛选器**。它暴露的是对全局焦点/深链/异步切换的目标依赖，需按既有快照规范核清所有实际可达路径。

捕获打开目标，切项目作废/关闭旧表单；提交前核对，迟到回执不得刷新另一项目名单或关闭其新框。runtime 配置等同类弹窗也检查，不再次出现旧 A 内容随全局项目写 B 的模式。
