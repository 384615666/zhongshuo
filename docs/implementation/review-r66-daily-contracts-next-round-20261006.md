## 2. 实际失败与证据

### P1-A：工作区原文件保存恒失败，长文件仍是提取窗

实际从文件树打开自有 `r67-worktree.html` → 更多文件操作 → 下载原文件：

`保存原文件失败：Cannot read properties of undefined (reading 'slice')`；保存桥调用 **0 次**。

根因：`PreviewPane.doDownloadOriginal` 把 `project.file.read` 回执声明成 `{content, sha256, bytes}`，实际命令返回 `{projectId,path,baseName,bytes,truncated,excerptBytes,content,note}`，**没有 sha256**。读取回执与 WorktreeBody 的 FileReadData 接口也不匹配，泛型断言掩盖了 DTO 缺口。

更重要：实际 105028B 的工作区 MD，命令仅返回 **65535B** 文本（64KB UTF-8 安全截断），尾部标记不可读。即使只补 hash、不换字节来源，“下载原文件”仍可能把截断重编码文本存成原件，和报告的“完整文件/原件字节”不符。

要求：

- 工作区屏幕阅读与原文件保存使用正确的正式只读通道/明确 DTO，完整性/范围/大小有界，模型注入窗继续独立。
- 保存的是用户当前预览对应的真实字节；核大小+实际 sha256，不用提取文本重编码冒充原件。空文件、UTF-8/BOM、中文/长文件、原文件读取失败/源文件变更、用户取消及落盘失败都有准确结果。
- 工作区文件可变：当前读取快照与源文件后来变化分清，旧标签不能静默另存新字节；实际重读/版本/hash 接服务事实，不用拼接 `_r2` 等假 hash 当正式内容身份。
- 所有 DTO/渲染字段一起核清，不只把 `.slice` 改成可选访问掩盖缺字段。实际保存链落盘后逐字/hash 验证，桥存在性或服务端原文件 hash 不等于保存结果已验。

### P1-B：换数据目录后草稿/未知发送失去恢复与防重

`loader.initDraftPersistenceFromIdentity()` 用 `${appDataDir}|${localUserId}`；`store.initDraftPersistence` 只读取对应 `zs.hifi.persist.<绝对目录>|<用户>` 键。

所以完整复制 `server-data/electron-user-data` 只保留旧键，换成 v4 的绝对目录后新程序查的是另一个键；“磁盘原件还在”不等于当前界面恢复了它。

独立界面反例（同数据库/用户/目标/参数，仅改变复制来的快照键所属根）：

1. 正式仅记录提交成功，回执丢失，服务侧消息 **1 条**。
2. 原界面已有“上次发送结果未知”；原快照 `pendingEntries=1`，完整原 commandId 在其中。
3. 受控模拟旧根命名空间复制后重载：旧键仍含原 commandId；新界面草稿为空、未知横幅不见、新键不含该 commandId。
4. 普通输入同样正文再发：服务侧消息 **1→2**，工程 `real_calls=0`。

要求：

- 实现经过可信身份校验的跨目录继承/导入：可采用稳定逻辑数据根身份与显式旧键迁移，或准确可靠的继承机制。不同用户/无关数据根不能因为发现旧 key 就混入；不盲扫所有 localStorage 自动合并。
- 普通草稿保持 24h TTL；未知信封/出站账本原 commandId、目标、参数、版本/范围、阶段与恢复状态完整继承，不过期清除、不自动发送、不换号重发。
- 旧根/旧 profile/隔离原件保全，导入冲突/损坏/存储拒写失败安全，不能把读取不到旧键写成“全部延续”。
- 必须补真实 **完整数据根+profile 复制、路径改变、真实启动器重开** 演练：普通草稿、仅记录意图、就绪附件、服务已提交丢回执与早崩账本都跨目录保持，人工同号重试业务恰一次。不要求用户制造该故障。

### P2-A：恢复三态第二次轮询倒退为启动异常并弹窗

App 的判据 `if (isFirstCheck || hadRealAttentionRef.current)` 把已经出现过的 runtime attention 当作 startup。

独立夹具启动干净，随后通过正式持久态 helper 对**自己的库**设置 held gate（受控故障事实，不声称自然产生了 UNKNOWN turn）：

- 下一次真实轮询：**modal=true**，面板标题“启动时已有”，侧栏改判。

这正是用户报告中需要消除的迟到遮挡；R66 G7 只测干净/普通排队，没有连续两次 runtime 异常正例，不能证明三态全过。

要求：启动来源按首次成功快照/异常实体身份稳定记录；持续同一运行中新失败永远不转成 startup。异常消失/再出现、持续多个轮询、关闭后不再被旧事项自动重开、重连/查询失败、多个实体新增都验证。原会话失败原因及时显示，恢复动作仍是用户显式操作，不自动对账/解除保护/派发。

原用户的 startupFailed 原因仍未诊断完成：只读 metadata 时序和 effective 来源不能代替失败 cause。“不读 payload”不是本任务的禁止要求；可以脱敏读取错误 code/phase/classification/必要 message 或既有 task.get.lastStartupFailureMessage，不读 prompt/凭据、不重放真实调用。查不到具体 cause 就如实列未查明，不声明已完成诊断。

### P2-B：HTML 工作区分支仍显示源码

自有同一 HTML：上传附件的默认预览为 sandbox iframe；文件树路径预览 **hasFrame=false**，主体为 doctype/style 原文。

HtmlPageView 仅进入 FullTextReader 分支，WorktreeBody 仍交给 ResourceBodyContent，其 code/text 分支不处理 HTML 页面风味。工具栏风味可以声称页面模式，实际主体仍未渲染页面。

## 3. 升级门与材料声明需要修正（P1-B 的配套）
