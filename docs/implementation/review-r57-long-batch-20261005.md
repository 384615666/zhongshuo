## 2. P1：准入恢复读取失败仍按空账本启动

`DispatchWorker.restoreAdmissionFromDb` 的 catch 明确回落“按空账本启动”。注释认为租约/门禁可以代守，恰好遗漏无租约 retained 且用户随后确认继续的场景。

独立故障注入仅让**构造器恢复占位的 SELECT** 失败一次（模拟临时 SQLITE_BUSY）；其它 DB 操作恢复正常。正式 message.submit 建立同成员两个任务，旧 turn 经 applyRecovery 变 UNKNOWN 并保留 protection_state=retained。事实：

```text
占位查询注入错误：1 次
新 worker 构造：未抛错
dispatch.resume(confirm:true) 后新任务：DONE / turn SUCCEEDED
旧 turn：仍 UNKNOWN、retained
实际 startTurn：2（应保留为1）
```

证据：`restore-read-failure-result.json`。声明：这是只读查询故障注入+fresh-worker 正式 fake 链，非真实 SQLite 文件损坏或 OS 崩溃实测。

要求：恢复占位无法核实时不允许新派发；可将 worker 保持未就绪/门禁保留并呈现恢复读取错误，或按既有启动错误路径拒绝启动，允许明确重试。不能吞错后把未知占用当零。恢复成功再开放，预算/保护/审计不被重写。补查询失败、部分恢复失败、恢复后额度/member 串行及正式解除恰一次的负/正例。

## 3. 返工执行仍缺实际续跑闭环，指南不能让用户等待

R57 修好了返工参数，独立正式链确认意见能入账、任务 REVIEW→ACTIVE。但 task.review 本身只写验收事实，不新增 outbox；三个后续真实 worker 泵均返回 false：

```text
返工前：startTurn=1，outbox=1，delivery=1，task=REVIEW
返工后：startTurn=1，outbox=1，delivery=1，task=ACTIVE，review_note 已记录
继续泵三轮：false / false / false
```

证据：`rework-dispatch-result.json`。R57 TDM2 的第二交付是手工 INSERT + UPDATE task REVIEW，因此它证明“意见记录与展示的新交付可以验收”，不证明“提交意见后真实续跑并产生新交付”。源码材料已经注明 fixture，但用户指南仍要求等1–2分钟出新稿，覆盖声明须统一。

按既定合同，task.review 与执行分离。优先提供明确的**执行返工**入口及“意见已记录、尚未执行”状态；绑定原任务、会话、来源 run，走正式 task.redispatch，沿用所有保护/在途/停止/幂等/额度守卫。不得通过发送普通 DM 新消息另建新任务冒充同任务返工。如果产品决定自动执行，应把自动执行作为独立行为明确说明并依正式门禁实现；本轮默认沿用明确确认执行，避免私自新增自动调用语义。

补证：真实页面提交 note→明确执行→outbox→同 task 新 run/turn→模型输入包含原交付版本与 note→fake worker 自然生成新 delivery→验收 DONE。这个正例不得靠 INSERT delivery 或 UPDATE REVIEW 造后半段；注入夹具仍可用于版本漂移等负例，但必须分列范围。
