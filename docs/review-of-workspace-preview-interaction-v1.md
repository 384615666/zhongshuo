## 2. 必须先解决的冲突

### C1（最高）与权威文档 §17.1 的关系没有真正处理

README 明确开发设计报告是**唯一权威版本**（当前 v1.14），这是仓库里唯一对交互有约束力的基线。[§17.1 末段](zhongshuo-development-design-v1.md)原文：

> 成果/文件/活动/成员/任务详情**仍在串内 tab 就地渲染**；窄窗口可切为线程全屏页，关闭线程不停止任务。

被检查文档的核心主张之一，正是把"具体文件正文"从串内 tab 移到共享预览区（§0.1、§1.1）。它 §1.1 写"在本文中有明确调整"，但：

- 它自己承认"本文是拟替换相关交互条款的独立提案，**未自动把旧基线标记为已更新**"；
- 一份独立提案单方面声明调整权威条款，落地时没有约束力——两个 AI 分别按两份文档写代码，冲突无法裁决；
- §17.2 页面清单第 1401 行"成果预览｜报告、来源、版本、导出"同样需要同步修订，文档 §1.1 未提这一条；
- §17.1 原文的"成果/文件/活动/成员/任务详情仍在串内 tab 就地渲染"是一句整体规定，本文只改其中"成果"一项而保留其余，属于**部分修订**，更需要写明边界，否则容易被读成"§17.1 整条作废"。

**建议**：不要用"本文调整了 §17.1"这种表述。要么在 §17.1 内加一条注记指向本文，要么把本文定位为"§17 的下一次修订草案"，而不是平行提案。**这是本文档落地前唯一必须先解决的外部依赖**——其它问题都可以在本文档内部消化。

### C2（已降级）与候选风格稿 v4.4 的数值并轨问题

> **定级说明**：[docs/design-spec-candidates/zhongshuo-frontend-design-spec-zcode.md](./design-spec-candidates/zhongshuo-frontend-design-spec-zcode.md) 位于 `design-spec-candidates/`，是**评审中的候选风格设计稿，不是权威基线，也不确定会被采用**。它不构成"本文档必须服从"的冲突，因此本项从初稿的最高级下调。（初稿曾把它当作既有基线并据此定级最高，该判断有误。）

即使它不是基线，两份**都在评审中的稿子**对同一交互给出互斥数值，仍会让评审无法同时接受两者，因此需要并轨：

| 事项 | 本方案 v1.0 | v4.4 §8.8（候选稿） |
|---|---|---|
| 预览最小宽 / 默认宽 | 最小 480px；按比例分配 | 320–720px，默认 **520px** |
| 降级断点 | 808 / 848 / 928（内容宽） | 单栏切换 < **1200px**（视口宽） |
| 可打开入口 | 主池、房间文件、成果、项目树、Git | **只有**回复串里的文件名 |
| Esc 行为 | **不**关闭文件或清空标签（§12） | 面板 × 或 **Esc 关闭** |
| 主池在预览打开时 | L3 保留「主池 + 文件」 | 主池**必须收起** |

处理方式二选一，不必现在就选：

1. **分工**：本文档管交互与状态语义，风格稿管像素与断点。据此把本文 §5.2 整张宽度表与 §4.4 顶部栏像素细节改为引用风格稿最终版；本文只保留"语义层最小可用宽度（能否读和操作）"。
2. **各留一份**：两稿数值都保留，但在评审时明确"二者不会同时采用"，避免后续有人把两份当兼容规范执行。

需要说明的是：即便风格稿最终被否，本文档的宽度数值仍然是**唯一的一份**，所以它必须自己站得住（见 C3）。此外本文 §0 声明"不规定配色、字体、圆角和阴影"，这与风格稿的分工并不矛盾；真正重叠的是宽度与顶部栏结构两项。

### C3 主池最小宽出现三个数字

| 来源 | 数值 |
|---|---|
| 源码 `Room.tsx`（当前实现） | `MAIN_MIN = 420` |
| 本方案 §5.2 | 360px |
| v4.4 §8.1 / §8.3（候选稿，仅参考） | 380px / 340px |

文档把主池最小宽从 420 降到 360，却同时在 §5.3 写"**不缩小正文**，不把输入框压成零"。360 相对当前实现 420 就是缩小。请选定一个数值，并说明降级后正文可读性用什么标准验证。注意这一项的**主要依据应是当前实现与实测**，不是候选风格稿。顺带说明：若没有实测支持更小的数值，直接以 420 为下限、只在必要时才放宽，是风险最小的选择。

## 3. 覆盖面缺口

### C4 完全没有覆盖私信

`ContextTarget` 只有 `room | thread | files` 三种，`WorkspaceLayout` 也没有私信分支。但：

- [Dm.tsx:330](hifi-prototype/src/pages/Dm.tsx#L330) 原文：私信"与群聊共用持久历史、线程、**附件**与任务能力，但可见范围独立"；
- 私信已并入 M3（决策 24 / E9 第十一批），与附件七类同批；
- 私信归档相关文案（`Dm.tsx:381/595/664`）明确"历史与附件保留"。

**结论：私信里的附件在本文档中没有预览归宿。**这不是边角情况——私信是 M3 范围内的正式能力。

### C8（并入 C4）搜索/收藏落点在表里出现，却不在类型里

§3.2 表格有"搜索或收藏结果"一行，但 §11.1 的类型系统无法表示"从搜索结果打开"。另外 §8.1 格式矩阵**漏了 CSV**，而原型 [Room.tsx:1344](hifi-prototype/src/pages/Room.tsx#L1344) 列出的七类里含 CSV，开发报告 §25.5 的七类不含 CSV——两者本身就不一致，文档沿用了其中一个而没有指出这个既有矛盾。

## 4. 真正的技术阻塞点

### C5（严重）附件不是一等对象，被埋在 §11.3 末尾一句话

文档 §11.3 最后一行：

> 历史 artifact 模型要求 taskId/threadId，但主池普通附件不应被强行塞成"任务成果"。需要独立附件资源描述或正式统一资源层，保留零任务归属合法性。

这句话决定了验收场景 PV-01（主池普通消息、无 taskId、打开附件）**在当前模型下无法表示**。证据：

| 事实 | 位置 |
|---|---|
| `Artifact.taskId` 与 `Artifact.threadId` 均为**必填** | [types.ts:462-467](hifi-prototype/src/data/types.ts#L462-L467) |
| `Message` 接口没有任何附件字段 | [types.ts:215-236](hifi-prototype/src/data/types.ts#L215-L236) |
| `MessagePayload` 七种卡片中没有附件/文件引用 | [types.ts:248-258](hifi-prototype/src/data/types.ts#L248-L258) |
| Composer 的附件是假对象 `{ name, size }`，**从不落进消息**（`actions.ts` 中 `attachments` 仅作为提交入参，不写入 `Message`） | [Composer.tsx:141](hifi-prototype/src/components/Composer.tsx#L141)、[Composer.tsx:520](hifi-prototype/src/components/Composer.tsx#L520) |
| 回复串里**没有任何可点击的文件名**（grep 无命中） | `MessageView.tsx` 全文 |
| 主池卡片不带附件入口，成果入口只存在于线程卡 | [Room.tsx:845-856](hifi-prototype/src/pages/Room.tsx#L845-L856) |

因此，那份候选风格稿 §8.8 写的"点回复串里的文件名"这一入口，**在原型中当前并不存在**。两份文档都建立在同一个尚不存在的对象上。

**建议**：把"附件/文件引用成为一等资源"提到实施顺序第 0 步，并明确它是 **DEV-01 contracts 的增量**（新增类似 `Attachment` / `ResourceRef` 的契约与 `Message.attachmentIds`），不是原型内部可以自行决定的事。文档 §11.5 把它排在"第 2 步统一文件与版本"，对"第 1 步先验证状态骨架"来说是阻塞项而非后续项。

## 5. 编号与流程

### C6 验收编号自成一套

PV-01—PV-30 没有挂到既有体系（§21.2 RT-xx、TH-xx、AT-xx），也没有说明是否登记进 §30.2 的验收矩阵。仓库已有多套编号，再引入一套平行宇宙会让"这条验收谁负责、跑没跑过"无法回答。建议改为在既有序列下扩展，或在文档中明确"PV 仅为本提案内部索引，正式验收编号由 §30.2 分配"。

### C7 §1 表格中"原型标识"一行不完整（低）

文档 §4.1 写"原型保留'模拟数据'标识"，与现状一致（`ProtoFlag`，[ui.tsx:443](hifi-prototype/src/components/ui.tsx#L443)）。但 §1 现状核查表未记录"项目全停"已于第二十六批第二轮从侧栏底部**移入项目设置 → 高级操作**（[ProjectSettingsPage.tsx:446](hifi-prototype/src/pages/ProjectSettingsPage.tsx#L446)）。文档 §4.1 写"「项目全停」沿用当前原型的项目设置入口"，这句是对的——所以只是核查表漏记，不影响结论。

## 6. 应当保留的部分（这是本文档的真正价值）

以下内容**开发报告 §17 与候选风格稿 §8.8 都没有覆盖**，是本方案不可替代的贡献，建议在收编时原样保留并升格：

1. **§2.1 四个对象分离**——当前项目 / 工作上下文 / 预览对象 / 发送目标，以及 `origin` 与 `openedFrom` 的区分。这是整个方案最扎实的一节，也是防止"文件串线"的语义地基。
2. **§7.2 引用目标表**——从成果列表引用 → 目标是线程；从房间文件引用 → 目标是房间；文件与 Git 页不猜目标。候选风格稿对此**一个字都没有**，而这正是最容易做错的地方。
3. **§7.4 评论归属**——在任务 B 的对话里评论来自任务 A 的文件，评论必须回到 A，且界面要写明。这条能防止一个真实且难查的串线 bug。
4. **§6.2 三类版本**——快照固定 / 工作区读取 / Git 两侧，"不混称最新版"。语义清晰，且与开发报告 §14.5 的版本检查口径一致。
5. **§3.4 关闭恢复快照**——期间只切文件/滚动则恢复快照；期间主动切过任务则保留最新选择。这个二分规则很精确，比"恢复上次布局"的说法可靠得多。
6. **§4.5 操作名称与结果表**——"关闭文件 / 收起预览 / 关闭所有文件"三种行为的区分，以及"Esc 不默认关闭文件"。
7. **§8.3 安全边界**——canonical path、软链接/junction 不得越过项目授权、HTML 不继承应用权限。与开发报告第 16 节一致，值得保留为预览层的显式约束。

## 7. 建议的处置

1. **先解决与权威文档的关系（C1）**：不要在本文里单方面声明"调整了 §17.1"。或把本文定位为 §17 的下一次修订草案，或在 §17.1 内加注记指向本文，并同步 §17.2 的"成果预览"行。**这是唯一的外部阻塞项。**
2. **与候选风格稿并轨，但不必现在选（C2）**：若风格稿最终被采用，本文的宽度表与顶部栏像素细节应让位给它，本文只保留"语义层最小可用宽度"；若被否，本文数值即唯一来源，须按 C3 自行站得住。
3. **补漏**：私信上下文、搜索/收藏落点的类型表示、CSV 类型、主池最小宽定一个数（C3、C4、C8）。
4. **把附件契约提到第 0 步**（C5），并写明这是 DEV-01 增量。
5. **砍到能过门槛的第一片**：README 的界面门槛是"简单原型由 AI 绘制，经用户一轮反馈修改并确认后开工"，而本文 §14 要求交付 10 类状态、§13 列 30 条验收。第一片只做：消息里的文件 chip → 线程+预览两栏 → 关闭/恢复 → 一种格式（Markdown 或代码）→ 两个独立草稿。Office、diff、安全矩阵、评论、跨项目恢复全部后置。
6. **验收编号归位**（C6）。

> 一句话：这份方案的**诊断是对的、细节是好的**；它的问题不在于想错了，而在于**与唯一权威文档 §17.1 的关系尚未确立，且范围远超当前门槛**。收编它，不要照做它。
