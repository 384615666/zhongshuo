# R124：继续寻找非常规组合故障

用户要求在 V65 后继续发散破坏性场景，并指定 `newapi/deepseek-flash`。本轮仅增加测试与审查记录，产品代码和 V65 包保持原样。

## 方法与模型

内置子代理接口拒绝 `deepseek-flash` 和 `DeepSeek V4.1 flash` 两个名字，只列出 GPT 型号。随后读取本机 Claude 渠道的模型设置，发现用户已配置 `newapi/deepseek-flash`；按用户指定通过该 CLI 入口启动两路隔离上下文、max 思考档的场景设计任务。模型不获得文件写入或命令执行工具，只接收公开源码和既有测试说明。设计建议与实际执行结果分开记录，不能把模型的推测当成已经复现。

另有三位 `gpt-6.1-sol` 子代理分别实测操作乱序、异常协议、共享记忆。主代理负责存储故障蔓延及整合。所有业务执行使用脚本模型、独立 SQLite、项目和本地协议进程；不操作原项目或运行库。DeepSeek 设计请求是真实模型调用，不计作产品业务请求，也不能声称本轮总模型调用为零。

## 已实测：存储故障与文件夹变化

| 场景 | 实际结果 | 判断 |
| --- | --- | --- |
| 一个房间的笔记合并持续写入失败，另一个项目发来八个任务 | 连续六次调度均抛错，八个无关任务零启动；解除故障后全部完成，笔记只合并一次 | 新缺陷：记忆故障蔓延到全局派发 |
| 成功任务有待合并笔记，记忆表故障持续到数据库重开 | 新 worker 构造失败；解除故障后可启动，不重跑模型，笔记合并一次 | 同一缺陷的重启路径 |
| 十二个写请求排队后，其项目文件夹被移走；另一项目有六个写请求 | 十二个失败项目请求阻塞，零模型启动；另一项目六个完成，无 UNKNOWN 或遗留写租约 | 这一组合守住 |
| 独立 PowerShell 进程用 Windows FileShare.None 独占项目文件，同时另一个项目排队 | 普通任务允许执行；该文件 before/after 都真实记录为 unknown 和 EBUSY，未伪造为删除/未改；无关四个任务完成，关闭句柄后新请求可完整读取 | 状态诚实，但被占用文件的前像无法恢复，属于能力边界 |

故障注入为合成库的 SQLite 表级触发器；可以模拟该子功能写入失败的影响范围，不能等同已经测试了真实磁盘写满、Windows 杀毒或物理设备故障。第一个注入只影响记忆表，普通任务表仍可写，足以说明无关任务被一条非关键收尾阻塞。

`chaosStorageR124.test.ts` 中两条 `it.fails` 断言的是应有行为，目前预期失败用于固定 V65 缺陷；框架输出绿色代表缺陷成功复现，不能计为产品守住。证据保存在 ignored 的 `dist/r124-chaos/storage/`。原夹具项目位于 `dist/r122-collisions/r124-*`。

最初对独占文件场景假设“任何文件读取失败必然阻塞整轮”，与现行实现不同。最终断言改为验证真实 OS 锁、unknown 不被伪造为不存在/未改、其他项目继续、解除占用后可读；没有把早期超时当作产品死锁，也没有声称能撤销无法读取的旧内容。

## DeepSeek 建议与实际验证

协议方向请求成功，CLI 返回 `subtype:success`、`is_error:false`、`modelUsage` 包含 `newapi/deepseek-flash`，max 档、独立上下文、一回合。状态/记忆方向的第一请求在 300 秒超时，没有取得设计结果；缩短源码输入后独立重试成功，返回相同的模型用量标识、max 档及五项建议。两份成功设计和一次超时均保留，不把超时当完成。

DeepSeek 给出八项候选：终态状态缺失/未知、重复与矛盾终态、同 provider thread 再次启动、旧审批跨进程代次答复、旧 turn 被恢复会话认领、审批多身份矛盾、重复 JSON-RPC 审批 id、已完成 provider turn id 重用。

主代理已把第一项写成真实本地协议进程和正式 worker 的回归。`cancelled`、`inProgress`、`null`、缺失和未知值五种终态状态，全部实际成为 `SUCCEEDED / DONE`；明确 `completed` 的成功对照及明确 `failed` 的失败对照有效。五种变体属于**同一个缺陷**，不能算五个独立问题。这些是畸形/兼容执行端的协议鲁棒性场景，未声称官方渠道必然发送它们。

`chaosDeepseekR124.test.ts` 的五条 `it.fails` 固定应有的“非明确成功不当成功”约束。已核对每个 JSON 证据确实走到任务终态，排除夹具或 SQL 查询出错导致的假预期失败；套件钩子另检查到达业务断言，钩子失败不会被 `it.fails` 反转。明细在 `dist/r124-chaos/deepseek-executed/`。

协议子代理同时实测了 DeepSeek 的重复终态（P04，worker 守住）、审批身份矛盾（P05）、重复审批 id（P06）、旧审批跨进程（P09）、恢复会话认领旧 turn（P10）。“同 provider thread 再次启动”以及“同 thread 已完成 provider turn id 再利用”未在本轮单独认证。

状态/记忆五建议经独立只读核对：同基线同 key 冲突、同名不同 ID 隔离和重复 bundle 拒绝已有实际覆盖；删除重建并强制复用 ID 没有发现生产命令入口；“提交后停止导致同载荷重试拒绝”会经过安全状态重验，但没有全链路卡死证据，正常 worker 合并与删除 pending 同事务，已知门禁拒绝会清 pending 并留审计。停止不撤销历史笔记属于追加式语义。未把模型标为“真实缺陷”的字样直接当作事实，也未将不同房间误写为共享范围。

## 主代理汇总与修复顺序

| 优先处理 | 已证行为 | 证据场景 |
| --- | --- | --- |
| 执行进程退出收尾 | 共享进程真实退出，一条已成功的任务保持成功，另一条仍 RUNNING、消费器和 outbox 等待未结束；默认无执行截止 | P03 |
| 生命周期门禁 | OPEN 根任务排队时归档检查漏过；归档成功后仍启动并实际写文件 | A05 |
| 故障隔离 | 一条记忆收尾的表级写入故障阻塞全局派发，持久故障阻止重启调度器 | 主代理存储两路径 |
| 会话及审批身份 | 矛盾早到/响应 ID 可发布错误正文，旧 turn 迟到启动可被恢复会话认领；审批多身份/重复 id/旧进程代次有缺口 | P02/P05/P06/P09/P10 |
| 完成状态的严格校验 | 缺失/未知/仍在运行的 provider 状态被当作成功 | DeepSeek S1 五变体 |
| 迟到成功的记忆接线 | UNKNOWN 经正式恢复泵收为成功并交付，但增量笔记丢失，重放和重开不补回 | C08 |
| 其他一致性 | 启动显式失败后的同 session 重试、旧未绑定启动与新进程、重复停止代次、跨方法幂等错误码 | P07/P08/A03/A01 |

以上是问题族及触发路径，不按红灯条数计算独立漏洞。P03 应结束消费者并保留真实 UNKNOWN/写保护，不通过自动重跑掩盖执行事实；记忆收尾应隔离延后，不能挡住新任务及调度器构造；归档应拒绝有 OPEN 工作的房间并在启动前重查。协议归属要绑定被正式接受的 thread/turn/进程代次，处理冲突及已关闭身份，审批请求也要带相同边界。迟到成功复用同一笔记准备/合并路径。

两项反例单列，不当作普通用户能直接触发的已证漏洞：A06 在 DISPATCHING 已存在时停用成员仍继续启动，现有合同明确在途不受影响；C09 直接改写隔离库的冻结 bundle 后版本被错认，是存储完整性加强项，未发现用户或模型经业务 API 改写该表的路径。Windows 独占文件的 unknown 前像属于已说明能力边界。

## 本轮验证

主代理联合复跑五个新文件：39 项，18 passed、21 expected fail；后者含同一问题的多个变体、语义边界和数据库直接篡改，**不是 21 个独立漏洞，也不是产品全通过**。每组保留正式命令、状态、实际文件或协议帧与清理证据。无随机操作种子，使用固定序列和屏障；没有将脚本时序称为真实用户随意点击的全覆盖。

完整 TypeScript 检查及七个新增代码文件 ESLint 通过。正式产品源码未改，不重跑上一轮全部 2314 项，也不生成 V66；另跑七个相关旧文件，77 项通过。此前 V65 交付身份不变，本轮没有启动它的沿用数据入口。
