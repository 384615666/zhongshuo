# 众说使用流程排查与整改方案（待评审）

日期：2026-10-25。依据：用户本次两张截图、当前 V51 程序对应源码、原数据中这次请求的只读记录。

**本轮交付排查表和整改方案，尚未修改业务代码、重新封包或重跑用户任务。** 排查覆盖“输入与收件人 → 多人协作 → 等待与状态 → 阅读与定位 → 发送异常找回 → 通知与帮助”这条使用链；不把这次检查称为整个系统的全部缺陷清单。

## 一、先回答截图中的三个问题

### 1. 为什么 Claude 说没有向 Codex 派发的通道？

这里的“通道”指本轮任务允许使用的**成员交接接口**，并不是网络传输连接的名称。这次存在三层断点：

1. **输入识别漏人。** 原消息写了“@Claude 再帮我对比一下，然后@Codex 来验证……”，但保存的正式收件人只有 Claude。当前识别规则要求 `@` 前面是开头、空白或指定标点；“然后@Codex”的 `@` 前面是“后”，所以 Codex 被当作普通文字。直接运行现有纯解析函数也复现了这一点。
2. **顺序协作没有建立。** 该条跟进被路由成只发给 Claude 的单人请求，执行阶段是 `direct.work`。这类回合没有开放追加成员交接，所以 Claude 无法从这一回合继续创建 Codex 的核对工作。只把两个名字都识别出来仍不够：普通多成员请求也不天然等于“先比较、再读取本次比较做核对”。
3. **没有完成后续工作，却显示完成。** 这条消息只产生了一条 Claude 执行请求，成员交接记录为零；Claude 的结果还明确记录“Codex 独立核对尚未发生”，但任务随后进入 `DONE`。

因此，这次没有形成用户要求的 Codex 验证流程。不能仅凭这句话判断 Codex 的网络渠道是否故障。程序应该承接用户已经明确提出的协作要求，而不是让用户看完“没有通道”后自己重新组织调度。

### 2. 为什么“打开回复串”实际去了详情？

已确认是按钮与跳转不一致：程序生成的动作标签是“打开回复串”，前端却固定跳到 `?tab=run`，这个地址在现有界面中对应“详情 → 运行详情”。而且同一动作也放在已经打开的回复串顶部，没有判断用户当前所在位置。

应按位置显示动作：房间外部可“查看回复”；已在该串回复页就不再让用户“打开”自己；确实要看运行情况时，直接写“查看运行详情”。

### 3. 已经在原会话里，为什么还常驻“查询刚才的发送”？

这个功能确实只解决了技术上的“按原请求查回执”。它按当前输入框的身份读取记录，没有提供让用户从其他页面发现、找回发送的入口。只要保留过发送记录就显示蓝色面板，连发送成功、回复已经可见、任务已经完成也不区分。

在原会话里，它对“这一条是否被接收”仍有诊断价值；但对用户真正的“我不知道发到哪里了”帮助不足。**需要先补一个跨页面可访问的发送记录入口，再把原会话中的恢复提示改为只在有异常时出现。** 不能只把按钮删除，导致未确认发送失去入口。

## 三、建议改后的实际使用过程

### 场景 A：Claude 先比较，Codex 再核对

用户写：“@Claude 再比较一下，然后@Codex 验证 Claude 说得对不对。”

1. 输入区展示“Claude 比较 → Codex 核对”，成员姓名可以辨认，不要求用户学习内部模式名字。
2. 发送后，同一串展示程序已接受的步骤，而不是只显示 Claude 接单。
3. Claude 处理时显示“Claude 正在比较；Codex 等待比较结果”。
4. Claude 完成后，Codex 读取这一次交付再核对。串内保留各自作者和本次输入版本。
5. Codex 尚未开始时，整项仍是“等待核对”。不能因为 Claude 已答复就给用户整项完成通知。
6. 核对无差异就简短确认；有差异则指出纠正，再由协调成员汇总。用户只需回原串看结果。

如果 Codex 不可用，界面直接说“Claude 已完成；Codex 未能开始：具体原因”，提供成员配置、等待或取消该核对等合适入口。不能只让 Claude 说“没有通道”后将整件事标为完成。

### 场景 B：忘了刚才发到哪里

1. 无论当前在哪个项目，都能通过“待我处理 → 发送记录”看到最近发送。
2. 每条显示可识别的归属、时间和摘要；未确认项在前。
3. 点“核对是否收到”，只读查询原请求；找到后变为“查看这条消息”。
4. 点击后进入真正的原回复页／私信位置，突出该消息。
5. 已收到、已能看到的发送无需继续占一个蓝色恢复面板。查询结果不确定时仍保留请求，不能自动重发。

“发送记录”是本机可用记录的索引，不承诺能恢复已被删除的浏览器存储，也不按相似文字猜测哪条任务属于哪次发送。要跨页可靠定位，仍应使用已有请求身份和服务端确认的位置。

### 场景 C：正在回复串里看任务

- 正在执行：显示成员和当前可确认阶段；需要进一步核对时提供“查看运行详情”。
- 有成果：提供“查看当前成果”；待验收时提供“验收当前交付”。
- 已经在回复页：不再出现“打开回复串”。
- 进入详情后：通过明确的“回复”页签回正文；保留消息阅读位置和草稿。

## 四、实施顺序与验收方式

### 第一批：不再漏掉用户要求（01–04）

先补收件人识别与发送预览，再让顺序协作与任务完成条件形成闭环。不能只放宽一个正则、让两位 AI 同时开工，就算完成本次整改。

只读核对不应获得修改权限；成员不可用、权限不足、预算不足或上游结果失败时，都保留明确原因。没有授权的成员不因名字相似被自动加入。已经明确选择的成员，也不要求用户反复确认同一安排。

完成判定绑定**用户本次要求的必要步骤**，不把结果里所有“剩余问题”或“未执行验证”一律当成阻塞项。例如“本次 Codex 核对”是必要步骤；历史工程报告里尚未做的其他测试不因此变成本次待办。

### 第二批：每个入口都带用户去正确位置（05–10）

把按钮名称、当前视图和目的地统一处理，再做跨页面发送记录与异常提示收敛。复用已有请求账本和位置校验；全局入口补齐前不删原有恢复能力。“重试”“继续”“取消提示”“停止执行”的实际效果必须分别写清。

### 第三批：减少等待、通知与升级中的困惑（11–15）

整理状态信息层级，补通知管理与事件落点、应用内手册，再整理升级数据入口。通知实际点击和升级数据连续性分别作为独立验收，不能只凭组件测试或手册文字宣布通过。

### 本次整改的验收场景

| 场景 | 必查结果 |
| --- | --- |
| 中文相邻 @、正常空格 @、中文标点 @ | 正确识别明确成员，输入与实际收件人一致 |
| 邮箱、代码、引用、未知成员、同名成员 | 不误唤醒，不默认选择错误身份 |
| 本次用户原句：先 Claude 后 Codex | 顺序与依赖成立，核对绑定本次成果 |
| Claude 成功、Codex 不可用／失败／被停止 | 整项不提前完成，原因与下一步清楚 |
| 普通单人对话、多成员共同研讨 | 保留原有使用方式，不强制变成串行流程 |
| 从房间、同一回复串、私信、其他项目点击动作 | 标签与落点一致，不重复打开当前页 |
| 正常发送、回执丢失、服务已接受但客户端报错 | 正常界面安静，异常可查，不重复建任务 |
| 多条未知发送、跨项目、正常重开 | 每条请求分别可找回，不被最近一条覆盖；后续草稿保留 |
| 查询找到原消息 | 落到原回复／私信中的对应消息，不只到概况 |
| 原本要求写文件，点击继续 | 不静默改成仅分析，也不自动扩大权限 |
| 不同类型通知与真实系统点击 | 回到与事件相符的位置；真实点击单独记录结果 |
| 原数据升级与手册 | 项目、成员、草稿、附件保持；应用内能找到当前操作说明 |

实施获准后，先用隔离数据验证，再按明确范围验证真实渠道；不重放原任务作测试，不裸跑会操作远端 GitHub sandbox 的测试套件。若需要为真实渠道产生新调用，应使用明确的合成任务与预算，不能把开发测试塞进用户原对话。
