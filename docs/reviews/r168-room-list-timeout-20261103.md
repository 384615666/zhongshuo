# R168：room.list 超时与清理旧开发文件的排查

用户在清理旧开发过程文件后看到四个项目的 room.list 均超过15秒；清理完成后仍持续。只读核对安装版 beta.19 的全部667个清单文件，缺失0、改动0。此结果不支持“安装程序文件被清理坏了”。未修库、迁移数据或停止用户后台。

## 复现与修复

R163 为房间状态图标调用了完整 readTaskExecutionStatus。该投影除执行事实外还计算“继续/重试/结束”等操作资格；结束资格遍历完整任务树，并按历史 outbox、事件和恢复记录判断归属。每5秒刷新所有展示项目时反复计算这些详情动作，在历史较多时会使同步 SQLite 查询和 IPC 排队累积。

隔离内存库（0用户数据、0模型）测得：20根任务/200子任务/20000事件、无历史outbox时262ms；4根/40子/8000事件/40已完成outbox时602ms；10根/100子/12000事件/100已完成outbox时 **5351ms、1021次查询**。多项目请求叠加足以形成15秒超时的条件；这是可复现的程序性能问题，不能把原因直接归给磁盘清理。运行后台的独立凭据认证仍被拒，未直接测到截图原请求，因此不声称它是所有现场超时的唯一原因。

新增 includeActions=false 内部读取选项。房间状态汇总、待办的历史筛选和原因摘要使用它，跳过操作资格推导；详情和正式动作入口默认仍做全部核对。执行阶段、未知/保护、停止、等待、待验收和事件依据不变，没有延长超时、隐藏真实失败或跳过操作守卫。

同一10根任务样例修复后 **69ms、331次查询**，约缩短98.7%。新增测试比较九种状态下完整/摘要执行事实完全一致，并验证增加100个历史子任务后房间摘要查询次数保持有界；不靠硬件相关的耗时阈值做CI断言。
