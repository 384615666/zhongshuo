## 1. 用户确认的产品行为：历史图片一并发送，保持现状

位置：[src/daemon/turnInput.ts:31](../../src/daemon/turnInput.ts#L31)。由 `9beee03` / R194 引入。

R194 将图片装配条件从 `image_mode === 'include'` 改成 `image_mode !== 'local-only'`。因此，旧版本保存的 `imageInput:'omit'` 也会转成真实模型图片输入。用户明确确认“仅发送文字”功能已经去掉，现在全部带图片一起发，本轮遵从该决定，不改此条件。

实际复现：构造旧版本合法的私信消息及图片关联，将持久字段保留为 `omit`；处理该消息后，在同一私信发送一条不带附件的普通后续问题。捕获的第二轮 `TurnRequest.images` 仍包含旧图片，数量为 **1**，且 `artifactId` 就是原来选择不发送的附件。

验收改为正向验证：后续私信仍实际携带这张历史图片；新消息的图片直接传递；`record_only` 的既有仅记录语义保留。

## 2. [P1] 较晚请求的附件会提前进入前一个请求的模型输入

修复位置：[src/daemon/dispatchWorker.ts:1753](../../src/daemon/dispatchWorker.ts#L1753)、[src/daemon/turnInput.ts:312](../../src/daemon/turnInput.ts#L312)。这是审计时存在的关联旧缺陷，不能归因为本轮 UI 或 R194 首次引入。

`turnInput` 只有在传入 `inputThreadMessageSeq` 时才限制人类消息和附件的序号；缺少该字段时，查询会读取整个回复串。普通初始派发没有这个边界；DELIBERATE 装配也只传了任务根信息和 DM 使用的 `inputThroughSeq`，没有传入当前 `thread_reply_requests.input_thread_seq`。传入 `inputThroughSeq` 不能替代回复串的请求序号。

两个独立复现均失败：

1. 先接受一个根请求，再排队一条给其他成员的后续请求并附上 `future.txt`，然后才派发根请求。后续文件里的唯一标记出现在第一轮 `coordination.planning` 的模型输入中。
2. 已完成根请求后，先排队独立研讨 Q1，再排队另一条请求 Q2 并附文件。Q1 的第一轮 `delib.independent` 已包含 Q2 文件的完整唯一标记，尽管 Q2 尚未执行。

影响：每条排队请求的材料边界失效。较晚请求中的附件可被提前发送给前一轮 AI，影响原请求的处理结果；不同成员、模型或服务商之间也可能出现非预期传递。这不证明跨房间或跨私信的 audience 检查失效，复现范围是同一回复串内的不同请求。

建议修复：为每次初始派发、线程续问及 DELIBERATE run 固定自己的消息序号边界；从所绑定请求读取该边界并传给附件与历史装配。根请求应使用接受该请求时的范围。用户后续提交的明确新要求由自己的队列处理；若另有主动调整在途任务的功能，应使用其正式语义。需要保留的既有 AI 成果、依赖结果和当前交付应按来源显式选取。

验收：两条 `future attachment` 用例通过，并补充图片、文档、原始根请求、DELIBERATE 后续阶段、仅记录及停止续接组合；Q1 的输入中不得出现 Q2 的附件标记，Q2 自己的输入仍须包含它。

## 3. [P2] “继续任务”丢失最后一次执行的成员和选择范围

修复位置：[src/daemon/commands.ts:5500](../../src/daemon/commands.ts#L5500)、[src/daemon/threadReplies.ts:134](../../src/daemon/threadReplies.ts#L134)。原缺陷由 `c774c90` / R181 的停止续接入口引入。

停止后的正式 `task.continue` 只读取最近运行的 `mode`，随后以空 `mentions` 重新调用 `selectThreadRecipients`。空选择会回退到根任务负责人；DELIBERATE 会重新采用当前串内可用名单，最后一次请求的 `route_json`、执行成员和明确选择的参与者没有沿用。

两个实际复现：

- 根任务负责人为甲，后来明确 `@乙` 发起 DIRECT 跟进。停止乙的运行后点击正式继续动作，新队列的成员变成 **甲**，模式由 **DIRECT 变成 AUTO**。
- 串内有甲、乙、丙，只选择乙、丙独立研讨。停止后继续，新队列的参与者从 **乙、丙扩为甲、乙、丙**。

影响：继续动作可能唤醒错误的 AI、改变协作方式或增加模型调用，而用户没有重新选择参与范围。普通私信停止后继续的对照用例可以完成，问题集中在串内最后一次请求与根任务选择不同的情况。

建议修复：根据所绑定的最后一次停止运行，定位其正式线程请求和冻结路由；继续时保留原成员、模式及明确选择范围，并重新校验成员是否仍可用、当前授权和运行时配置是否适用。若名单已变化，应明确要求用户重新选择，不能悄悄回退根负责人或扩充名单。继续使用新派发身份，保留现有停止代次和旧结果隔离。

验收：两条 `Continue` 选择用例通过；还需覆盖最后一次跟进模式与根任务不同、成员停用/移除、原请求是指定子集、重复点击和再次停止。

## 已实施的两项修复

- **请求材料边界**：`turnInput` 缺少显式回复串水位时，使用本任务根消息的固定序号，房间主池根消息按串内 0 处理，不再读取实时串尾。DELIBERATE 每个阶段读取所绑定请求的 `input_thread_seq`。当前请求的文字和图片仍传递，后续排队请求不提前进入。协作子任务通过当前协调运行的正式附件关联补入规划/交接完整详情；提醒派发按精确的提醒标识和触发时刻绑定唤醒消息及序号，保留当前提醒，排除其后新请求。
- **停止后的成员与模式**：新增 `selectStoppedThreadRecipients`，按最后一次实际运行定位其线程请求和冻结路由，兼顾协调整合、自动恢复及格式补交的来源；按钮继续和不重新指定成员/模式的普通续接共用此选择。保留原成员、模式及研讨子集，不采用未执行的后续排队请求，不自动加入后来新增的成员。原成员停用或移出时拒绝并回滚续接，允许用户显式重新选择成员。新派发仍冻结当前配置，使用新身份，保留停止代次及旧结果隔离。
- **回归与产品决定**：审计用例移入默认集成套件，历史 `omit` 改为验证当前“全部带图”要求；补充成员停用/移出时两入口原子拒绝和显式更换成员，提醒用例补充排除后来提交的问题。
- **范围**：未改 schema、权限分级、audience、图片能力门、版本或用户运行数据；未打包、安装、提交或推送。
