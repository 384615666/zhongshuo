## 审批回复的协议依据

独立 DeepSeek max 复核指出，旧实现的统一 `{decision:deny}` 与仓内已保存的生成协议不符，且 `Number(id)` 会错误转换字符串编号。指挥会话明确确认这属于第7—9项正确绑定和答复的必要接线，随后实际补测：

- `tests/fixtures/codex-protocol/RequestId.ts`：服务端请求 ID 为 `string | number`。客户端自己发出的请求仍使用数值 ID；服务端回给它们的字符串近似编号不能冒充同一个数值响应。
- `v2/CommandExecutionApprovalDecision.ts`、`v2/FileChangeApprovalDecision.ts`：`item/commandExecution/requestApproval`、`item/fileChange/requestApproval` 使用 `accept / decline`。
- `ReviewDecision.ts`、`ExecCommandApprovalResponse.ts`、`ApplyPatchApprovalResponse.ts`：`execCommandApproval`、`applyPatchApproval` 使用 `approved` 或 `{denied:{rejection:...}}`。
- `ServerRequest.ts`：不同服务端方法有不同回复形状。本 adapter 没有实现的 tool/call 等方法不作为审批投递，实际回包 `{error:{code:-32601,...}}`，不假装返回成功。

本地双向 wire 中验证了上述字面量、原始编号类型及 unsupported error。没有调用真实工具或声称完成官方渠道的真实审批认证。合法的精确早到审批可在启动响应前发出并答复；测试提供方必须等到收到该答复才返回 turn/start 响应，证明本轮缓冲不会在 adapter 公共接口造成这类死锁。普通正文、工具进度和终态仍等身份响应确认。正式 worker 的完整用户审批交互不在本轮新增认证范围。

## 明确保留的边界

- **15 不修**：retired 只阻止新一轮认领旧身份，没有全局“终态后全部丢事件”的开关。P04 仍断言 adapter 发出终态后的消息和矛盾终态，而正式已完成回复保持不变；原流两份完成、一份失败的观察仍存在。
- **19 暂缓**：已绑定但未终结的同 provider thread 不新增互斥。R125 S1 adapter 原健康断言继续注册 `it.fails`；正常 worker 的同会话串行仍通过。另保留相同 thread、不同 provider turn ID 的合法重叠对照。
- **17 不修**：未增加 context bundle hash 校验。16、18以及目录/文件锁能力也未顺带改变。
- 同 provider tuple 无法从正文分辨新旧来源时选择明确拒绝并保留未知结果保护；没有依靠消息内容猜归属，没有自动重跑。
