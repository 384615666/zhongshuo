# R121：房间切换、执行配置与发送提示

本轮针对用户提供的五项桌面反馈修复现有流程。

| 反馈 | 原因与修改 |
| --- | --- |
| 切房间时项目列表闪动 | 同项目切房间也进入整个项目的装载流程；跨项目提前改变焦点时，新焦点的房间事实尚未装载，覆盖了侧栏已有缓存。现在同项目校验目标后直接导航，跨项目装载期间使用已有侧栏缓存。 |
| 一位 AI 回复后研讨仍受阻 | 现场另一位成员在模型调用前因配置快照不匹配失败。旧 Codex 指纹遇到 `[[skills.config]]` 就退回整份配置比较，使其他项目信任记录的变化也能造成误判。新请求使用 v3，识别该独立技能数组；渠道、权限、技能设置、当前项目及祖先信任、未知数组和配置仍保留检查。v1/v2 快照按原算法比较，不覆盖旧授权。 |
| “权限读取失败”与超时 | 权限提示查询与发送共用串行管道，发送准备 CLI 时会阻塞后面的查询。仅该只读提示查询独立处理，写命令继续 FIFO；回执仍按 commandId 关联。读取暂不可用时显示一次简短提示，具体错误留在提示详情中，派发前复查保持。 |
| 正常发送闪“查询刚才的发送” | 恢复组件把 `sending` 也当成待恢复记录。现在仅未确认的原请求显示恢复入口；正常在途、成功及明确拒绝不显示该查询面板。 |
| 已完成仍常驻横幅 | 回复页隐藏无需验收的完成横幅，保留房间卡片、详情事实及待验收提示。 |

## 现场证据与边界

用户当前运行 V63。只读现场数据库证实：研讨中一位成员已成功，另一位成员的失败发生在模型启动前，`callStarted=false`。提交至失败之间，全局 Codex 配置文件确有改写。历史快照仅保存指纹，没有当时的配置原文，无法恢复此次改写的全部字段；不能把“只改了其他项目信任”写成已证明的现场结论。

技能数组与无关信任记录的误判已在独立配置中复现并修复。未重放原业务、未改变旧任务/授权快照、未迁移原运行数据，也未发出真实模型请求。旧失败不会自动重跑；新版本中可在原串提出继续要求，或使用现有的“按原请求继续”动作取得新的明确请求快照。
