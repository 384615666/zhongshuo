## 现场结论

用户截图中“短交流只发布主持人”的判断成立。原记录中，该根请求确实选中两位成员；两人的独立执行均为SUCCEEDED，各自保存了analysis_draft；最终只有主持人的一条聊天消息，运行以run.shortExchangeCompleted结束。不是成员没有接单，也不是草稿没有保存。

同次运行也确有write-root准入延期，现存事件记录为15条。它解释启动等待，不能解释成功交稿后消息仍不显示。本轮修复发布路径，保持同串协作的目录准入规则；不把截图中所有具体计时/计数都当成已经逐项认证。

## 修改

| 问题 | 最终行为 |
| --- | --- |
| 横幅等历史读完才出现 | 回复串立即采用主池已确认的正式executionStatus；实体归属就绪后先发task.get，与thread.history独立收敛。历史很慢或失败仍能更新任务状态，任务读取失败也不妨碍已有历史显示。 |
| 旧缓存覆盖新的等待状态 | 只接受匹配项目/房间/串/根任务的状态，并按任务版本、停止代次、事件水位与观察时间选较新事实。已确认的记录串不借用旧任务，过时读取不盖住较新加载。 |
| @全体短交流只发主持人 | 复用原阶段消息插入路径，分别发布冻结名单中每个真实成功独立执行的可读草稿，准确绑定作者/run/turn。明确no_reply保持静默，避免主持人重复显示；仍直接收口，不额外消耗互评/整合调用。 |
