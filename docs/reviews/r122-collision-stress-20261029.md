# R122：多人多任务撞车测试与会话并行评估

本轮按用户要求模拟非常规并发操作，并评估“共享角色模板、每个对话串独立会话”的方案。基于 V64 后的源码 `04c7f2f`，仅新增测试与本报告，没有修改正式调度、权限、事件处理或记忆策略，也没有生成新程序包。

结论：已有任务隔离、幂等、停止和写入互斥能挡住一部分撞车，但不能宣称产品已具备稳定高并发能力。发现写入排队扫描放大、畸形消息跨串归属缺陷，以及共享记忆覆盖风险。会话并行方向可行，须先修归属和调度开销，并明确文件与记忆的写入边界。

## 测试方法与范围

使用独立 SQLite、临时项目、正式 `dispatchDaemonCommand → outbox → DispatchWorker → adapter → 持久消息/文件` 链路。模拟执行端有受控延迟、挂起、停止不响应和真实文件写入；Codex 适配器另外连接实际本地 Node 协议进程，制造乱序通知、重复 provider item ID、共享进程崩溃及缺少身份的事件。真实模型调用 0，原用户项目和运行库未操作。

共执行 17 个新场景，其中一些断言用于稳定复现已知缺陷或设计风险，**“测试断言通过”不等于“产品通过这些风险场景”**。协议子进程是真实进程，模型输出仍由脚本产生；没有测试真实模型的理解偏差、真实厂商限流、长期耗尽或原生界面大量点击。

## 主要结果

| 场景 | 实测结果 | 判断 |
| --- | --- | --- |
| 三个房间同时发 36 个任务给同一角色 | 36 个独立会话、36 次执行；输入和回复各归原串；角色峰值并发 1 | 隔离守住，但仍串行 |
| 三个项目，12 个根任务各选择 3 位 AI，模型模拟返回正式分工 | 36 个子步骤全部完成，含规划和整合共 60 次执行；无重复派发；模拟渠道峰值并发 2 | 这组有明确计划的交错协作守住 |
| 同一忙碌串连续追加 20 条追问 | 20 条请求按入队顺序结算，根请求加追问共 21 次执行 | 无漏单或重复 |
| 同一 commandId 同时重试 30 次 | 仅一条原消息、一个任务、一次执行 | 幂等守住 |
| 正文相同但 10 个不同 commandId | 10 个独立任务均执行 | 没把不同用户意图误合并 |
| 对一个任务重复停止 12 次，另有 15 个任务在途/排队 | 只取消目标；其余全部完成，没有误停或 UNKNOWN | 目标绑定守住 |
| 一个写入成员运行时改配置，另有 10 条旧请求排队 | 在途请求完成；10 条旧快照阻塞；其他成员仍能完成 | 未静默升级/替换旧授权 |
| 写入端拒绝响应停止 | 旧轮 UNKNOWN，保留写锁；同目录新写者等待；其他项目完成 | 保护有效；等待是有意保护，不应当作普通并发槽随便释放 |
| 24 个可写任务修改同一计数文件 | 最终计数 24，无丢失更新，物理目录写者峰值 1；**300 份基线，约 74 秒** | 正确性守住，排队开销明显放大 |
| 全新独立 Git 仓库，12 个任务修改一份实际纳入快照的文件 | 最终计数 12；**78 份基线，约 17 秒** | 排除了大父仓库影响，扫描放大仍复现 |
| 测试中仅将角色互斥键替换成独立执行槽，12 个同角色只读请求 | 同角色峰值并发由 1 变成 2，12 个会话无输入串线 | 方案有实证可行性；正式策略未改 |
| 同样的试验用于 8 个同角色可写请求 | 峰值仍为 1 | 成员锁并非唯一瓶颈，项目写锁仍生效 |
| 两个独立项目、两个成功会话共同读改写同一份外部记忆文件 | 两个任务成功，但两条记忆最终只剩一条 | 共享可变记忆方案的覆盖风险已复现；不是声称当前存在产品级记忆合并功能 |
| 同角色 24 个原生适配器会话，通知先于响应且 item ID 重复 | 事件、终态及内容分别匹配各自会话 | 正常有身份协议可并行 |
| 两个会话共享的执行进程退出 | 两个会话都收到进程退出事件 | 会话独立不等于进程故障隔离 |
| 缺少 threadId 的未知终态 | 进入第一个会话的原始流；worker 的未知终态保护拦住它 | 适配器归属存在缺口，终态层仍有保护 |
| 缺少 threadId 和 turnId 的普通消息完成事件 | **经过正式 worker，实际保存进另一条对话串** | 已复现用户可见消息串线缺陷 |

计时是本机合成工作负载的观察值，不是吞吐基准。重点是 24→300、12→78 的快照数量放大；模拟业务本身只有几十毫秒。第一次短时限运行在 20 秒时仅完成部分任务，延长观察后全部完成，不能把该超时写成死锁。最初使用 `runOnce` 的轮询还遗漏正式 `drain` 的忙碌项重试语义，最终脚本已对齐正式 drain；早期脚本/协议字段与延迟窗口修正原件保留，不当作产品故障证据。

## 已定位的两个产品问题

### 等待执行名额前就扫描并落库

`src/daemon/dispatchWorker.ts` 的 DIRECT 路径先 `captureBaseline()`、发现文件、组装输入，再执行 `admission.tryAcquire()`。未获准的请求也产生一份持久基线；下次排队重试再次扫描，数量随等待者增加。同步文件/Git 读取还推迟进程内终态消费，放大等待。

建议先取得执行槽及物理写入租约，再捕获基线、装配输入和启动。失败、停止、UNKNOWN、重启恢复要继续按原事实收口；不能只缓存一份过期基线给所有后续任务，也不能把占位移到前面后漏掉启动失败释放。队列应由资源释放唤醒，辅以公平重试，避免每个等待者反复完整准备。

### 适配器猜测无归属事件属于第一个会话

`src/adapter/codex/appServerAdapter.ts` 的 `onNotify()` 在没有 threadId 时选择 `sessions.values()[0]`。`DispatchWorker.consumeUntilTerminal()` 对无 turnId 的终态有拒绝逻辑，但普通 `message.completed` 没有同等要求，因此可能以当前消费者的任务身份保存。

本轮先用原始会话流复现，再用真正重叠的两个会话与正式 worker 补证：一条无归属消息保存到无关串，两个任务最终仍可正常完成。最初延迟窗口不足的验证没有形成重叠，未观察到串线；最终窗口足够后复现。应按明确 thread/turn 映射路由，对无法唯一归属的消息、进展、工具结果和终态统一隔离并记诊断，不能默认选第一个会话。需同时保留已有早于启动响应的合法映射逻辑。

## 角色、会话和记忆如何拆分

| 对象 | 建议边界 |
| --- | --- |
| 角色模板 | 名称、职责、模型、工具权限与提示词；版本化共享。修改影响之后创建/确认的请求，不悄悄替换在途快照。 |
| 会话 | 按“项目 + 对话串 + 角色 + 会话代次”绑定历史、工具事件、运行与取消；不同串可并行，同一串按因果顺序处理。 |
| 串内工作记忆 | 当前任务的临时推理、待处理事项、未确认假设；保留在该串，不自动混入其他串。 |
| 共享记忆 | 按项目/角色及可见范围分区；执行开始读取明确版本，执行完成提交带来源的增量，由单一合并器事务追加/合并。不能把共享文件整份读出后各自覆盖写回。 |
| 工作文件 | 读任务可并行；写任务在同一实际目录保留互斥。真正需要并行改代码时使用独立工作副本，最后串行核验和合并；这是后续方案，本轮未实施。 |
| 执行资源 | 会话运行槽、角色限额、项目限额、渠道限额分别统计；停止只作用于绑定会话。共享执行进程退出时，全部受影响会话必须如实收口。 |

房间执行目前已按任务创建独立 runtime session；同串后续轮也可能创建新 session 并重组该串历史。当前不是所有串共用一条聊天记录，主要限制在 `DispatchAdmission` 的 `memberId` 恒 1 与目录单写者。默认还存在全局 4、每项目 2、每渠道 2 的执行上限。多人同项目使用完整权限时，即使用户只要求分析，也会按实际写能力争用目录写锁；不能仅看“分析员”这个角色名称就放行并发。

同角色多会话可以在现有结构上演进，无须重写所有消息层。优先级建议：先修无归属事件，再修准入前重扫描，接着引入会话级运行槽与角色容量；之后实现共享记忆增量合并，最后再评估独立工作副本下的并行写入。测试中的会话槽替换只是可行性对照，没有覆盖正式改造所需的重启、租约继承和所有停止路径，不能直接移入生产。
