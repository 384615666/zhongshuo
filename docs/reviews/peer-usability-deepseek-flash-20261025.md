# 众说全项目体验方案同行评审

日期：2026-10-25

评审基线：`7520288e5d0f20c60ccaeb9d6a3f10b90a334b04`

评审对象：[全项目使用体验排查与整改总表](project-wide-usability-audit-20261025.md)、[众说 V51 操作手册](../user-guide/README.md)、[R109 原始问题记录](r109-usage-audit-proposal-20261025.md)及其中必要的当前源码。

本评审从普通用户和长期实际使用者的角度回答三个问题：这个问题是否真的妨碍工作，方案是否减少步骤和记忆负担，是否应该现在做。只做了文档、只读源码和只读 Git 差异核对；没有启动程序，没有操作或读取用户业务数据库，没有调用模型，没有运行测试、构建或任何写入远端。源码与原生窗口表现不能互相代替，因此本文把源码可证、原请求记录、条件缺陷和待实机验证分开标注。

## 结论

总表的方向正确：它覆盖了整个项目和完整使用过程，也主动区分了源码证据与真人实测。但这仍不是一张可以原样施工的 52 项排期表。它混合了已确认缺陷、低频边缘问题、产品偏好、功能提案和需要先验证的假设；部分方案会把一个简单动作扩成新的向导、全局索引或长期维护面。

最应优先解决的不是统一 52 个界面，而是先修好四条信任链：

1. **用户写下的要求、程序实际接受的收件人与计划、最终完成判定必须是同一条事实链。** 重点是 U17、U20、U18、U19。
2. **“继续原请求”必须保持原意图和权限范围。** U26 当前把继续入口固定成只分析，这是用户难以发现的错误结果，优先级应高于许多视觉问题。
3. **普通草稿和结果未知的发送必须分开保存、分开清理。** U02 的直接删除会造成恢复能力损失；U03 的 24 小时静默过期也应在广泛整改前处理。
4. **用户看到的“当前结果、当前动作、能否撤销”必须真实。** 优先合并处理 U24/U25，修正 U22 的保存假完成、U35 的静默截断和 U34 的撤销入口断层。

另有两项证据需要纠正：

- U18 不能判定为“顺序协作功能完全缺失”。当前已有 `AUTO` 协调、结构化步骤、依赖图、上游成果版本绑定以及全部必要步骤后的整合。真实故障首先由 U17 的漏识别触发；原请求没有形成正式计划，因此不能从这一条记录单独推出“两个成员都识别后仍不会顺序执行”。
- U19 的核心是“整件事是否按用户可见且已接受的计划收口”，不能改成由程序无限重读自然语言、猜测所有隐含步骤。正式协作本来已有计划完成门；真正要补的是在派发前把必要步骤纳入计划，并让漏识别或计划缺口不能静默变成单人完成。

本文建议把“必须立即修、值得做、暂缓、仅待实测”分开，不以 52 项全部完成为成功标准。最合理的首轮范围是 7 组、约 15 个 U 编号；其余项目继续观察或做小型单点修复。

## 证据口径

| 标记 | 含义 |
| --- | --- |
| **记录** | 已由原请求只读记录或已发生的真实使用反馈证明。 |
| **源码** | 当前可达源码可以确认行为，但没有本轮真人点击结果。 |
| **条件** | 只有达到特定数据规模、时序或系统环境才触发，尚待隔离场景验证。 |
| **待测** | 判断合理，但现有证据不足以称为已确认缺陷。 |
| **偏好** | 设计上可以更好，不应当写成功能故障。 |

原审计基线 `05e5b3d2b511282e49f1ae6cd915197f9f1f5f6c` 与当前提交之间的 `src`、用户手册和打包脚本无差异，因此本次逐项判断针对的仍是审计审阅的那一版业务源码。没有遥测数据能证明操作频率；下文的“常态、条件、低频”来自入口覆盖面和行为性质，不是统计结论。

## 52 项逐项复核

优先级按本轮修订使用：P0 是会误导完成、改变用户意图或损坏恢复线索；P1 是高频或高后果的理解与操作障碍；P2 是值得做但不应阻塞核心闭环；暂缓表示先观察或先完成前置设计。

- **已经存在：** 正式 `changeset.undo` 命令、逐文件 after hash 校验、外部修改冲突保护、未知/超大文件人工处理、单文件临时写入与回读核对、每步持久化、失败后同命令续跑、项目写与 Git 写互斥，以及 `reverted/partial` 应用状态。多文件撤销明确不是整体原子，程序以逐文件结果为准。
- **正式 UI 真缺口：** 当前挂载的 `FormalChangeDetail` 没有撤销/续跑入口；恢复面板只显示未收口撤销数量和命令名，没有定位按钮。旧页面里存在一个禁用占位按钮，但该页面不是当前正式入口，不能把它当作用户已经可用，也不能把它当作后台能力不存在的依据。
- **最小修法：** 复用后台命令接通正式改动详情，显示计划或上次执行状态、逐文件成功/冲突/人工/失败结果；失败和未收口时允许同命令继续，冲突与人工项保留路径和原因，禁止把 partial 显示成全量成功。完成后刷新列表、快照和任务。
- **仍需验证：** 需要在隔离数据上分别验证正常恢复、后续外部修改产生冲突、部分失败后继续、超大或未知文件人工项、重复点击幂等、撤销期间项目/Git 占用和撤销后状态刷新。源码证明能力与保护路径存在，不等于本轮已验证正式 UI、原生窗口、真实用户文件和完整续跑体验。

## 对主审判断的具体纠正

### 被夸大或已有能力被忽略

- **U12 的“添加后才知道影响范围”不准确。** 添加成员弹窗提交区已经列出将自动加入的全部未归档房间。缺的是“房间成员”和“本串收件人”的概念边界。
- **U13 的“仍不知道到底能不能用”说得过重。** 成员卡片已有配置读取失败、模型缺失、执行程序缺失和在途/待核对状态，发送区也有未绑定提示。需要的是一个总入口结论和术语归并，不是重新建状态系统。
- **U18 不是从零增加顺序编排。** 现有 `AUTO` 计划已经支持 `dependsOn`、拓扑推进、上游结果版本和整合。原始故障可确定为漏识别，尚不能证明“双收件人计划一定未形成顺序”。
- **U19 的正式计划完成门已经存在。** 当前缺陷是这次没有形成正式计划，却把用户文字中的另一个必要工作当作任务外内容。解决方案应落在“收件人/计划成立”边界，而不是继续扩大自然语言完成判定。
- **U20 的“发送后也不知道实际安排”不准确。** 协作详情已显示计划摘要、步骤、依赖、上游交付版本及评审版本；问题是发现层级深、初始串里不够醒目。
- **U23 不是违背评论合同的缺陷。** 界面明确说评论只记录。可把它当提高效率的后续功能。
- **U34 不是“完整内容恢复从零开始”。** 后台正式撤销命令和冲突保护已经存在，当前断点是没有正式 UI 入口，恢复提示也到不了该入口。应接已有能力并补状态呈现、冲突处理和续跑，不应凭当前详情只读就抹掉已有实现。
- **U40 已经把未加载内容写明。** 搜索只覆盖已加载集合虽有限，但没有冒充完整；服务端归档搜索需要另算成本。

### 应合并的重复项

| 合并组 | 原因 |
| --- | --- |
| U24 + U25 | 都源自当前动作投影没有区分用户所在页面与当前结果；分别修改会再次产生两套优先级。 |
| U28 + U29 + U30 | 属于同一发送恢复链：发现异常、呈现异常、准确定位。应在一次设计中完成，避免先建全量记录页再删旧面板。 |
| U33 + U34 | 都是正式改动集的读取与动作能力；视觉差异可以单独先做，撤销入口应绑定已有 `changeset.undo` 的版本与冲突合同。 |
| U47 + U48 | Modal/Drawer 的外点关闭、未保存保护和焦点管理应由同一共享组件修复，不能一批改关闭行为、六批后再改焦点。 |
| U27 + U45 + U24/U25 | 都涉及异步状态里的动作落点；建议形成统一“动作目标必须符合当前对象与用户下一步”的规则。 |

### 优先级不合理的项目

- U10 从 P1 降为 P2：不同页面的默认范围合理，问题主要是标签和概念说明。强行统一默认范围可能让待办漏项。
- U13 从 P1 降为 P2：已有可行动状态，主要缺口是总状态和术语聚合。
- U15 从 P1 降为 P2：冻结配置是正确设计，补一句影响摘要即可，不值得列受影响任务并迁移旧任务。
- U28 从 P1 降为 P2 且缩小为异常发送：为所有正常发送建全局历史索引，只是复制已有搜索与任务历史。
- U37 从 P1 降为 P2：搜索条件恢复有价值，但先把稳定参数放进 URL 即可，不必一次解决全部滚动状态。
- U43 从 P1 降为 P2：设置搜索是可发现性增强，错误跳转要修，但设置分区本身仍可直接浏览。
- U46 从 P2 继续保持：它是高级低频路径，不能因为术语复杂就提升到核心工作流之前。
- U48 从“第六批”提升为共享基础项：凡是本轮改弹窗或卡片，就应复用可访问组件，晚做会造成重复返工。

## 可能增加负担或过度设计的方案

以下方案不建议按原样施工：

1. **U07 首次使用清单**：不要做成强制向导。只在项目未就绪时显示一行可行动状态，并允许关闭。
2. **U11 建房成员选择器**：不要给每次建房都加完整人员模式；保留合理默认，在房间内调整。
3. **U12 添加成员后二次询问房间与本串**：会再引入一层确认。展示现有影响摘要，并明确成员范围与收件人范围即可。
4. **U15 保存前扫描受影响任务**：高频配置保存不应为低频信息付出查询成本；显示数量并允许展开即可。
5. **U18 新编排器或强制确认**：现有编排能力已存在。先补入参数识别、预测路线和接受计划，不新增第二套引擎；只在计划缺必要步骤时停住。
6. **U21 每次新建私信都询问**：默认继续最近会话，把“新开独立私信”作为低频次级动作。
7. **U23 评论/派工双模式**：本轮不做或只做单一下拉动作，避免普通评论变复杂。
8. **U28 全量发送记录**：只为未确认/拒绝建异常清单，正常消息交给会话和搜索。
9. **U32 一步上全文索引**：文件名/路径搜索先行。全文索引涉及权限、容量、更新和解析质量，应是独立产品决定。
10. **U34 另造一套文件恢复引擎**：后台已有 `changeset.undo` 和冲突设计。最小改法是接通正式入口、展示步骤结果并复用续跑，不用提交回退冒充，也不需要重写恢复核心。
11. **U37 完整滚动位置恢复**：稳定 URL 参数后即可覆盖大部分需要，精确滚动与网络结果恢复可后做。
12. **U40 为归档建全量索引**：先让用户继续加载并知道范围，等服务端成本与需求都明确。
13. **U44 在设置中列出所有任务**：通知设置只管理例外，任务发现复用待我处理和任务串。
14. **U46 全屏配对向导**：一页步骤和复制按钮就能解决主要障碍，避免把安全细节切成难以回看的多个屏幕。
15. **U51 所有控件统一自动保存**：一致反馈和未保存保护比机制统一更重要。
16. **U52 全面重命名内部模式**：只改用户界面文案，内部模式与协议名按需保留。

## 完整流程复核与漏项

### 首次使用到开始工作

现有入口是欢迎页打开本地文件夹、项目主页新建房间、成员页添加 AI、在串内 `@` 发送。项目目录失效也能重新定位并保留历史。当前主要断点是：

- 准备状态分散在项目、成员、runtime 和发送区，没有一处理解“这个项目现在能否开始”。
- “成员、房间成员、协调者、本串参与者、本次收件人”五个概念没有统一用户解释；用户容易把“已添加”理解成“这件事会被交给它”。
- 操作手册没有覆盖这条完整准备路径，只讲最近几项功能。

这些内容大多已在 U07、U12、U13 和 U08 中出现，但应作为同一条首次使用故事验收，而不是各做一个提示。

### 提出要求到多人协作

当前路由和计划能力比总表文字描述得更完整：

| 用户表达 | 当前源码语义 | 用户需要知道什么 |
| --- | --- | --- |
| 不写 @ | 由房间协调者接收 `AUTO`，协调者可自行决定是否分工 | 默认会叫谁；协调者是谁。 |
| 只写一个明确 @ | `DIRECT`，仅该成员被调用 | 这不是多人协作；其他成员不会自动参与。 |
| 写两个或更多明确 @ | 进入 `AUTO` 显式收件人范围，由协调者规划 | 两个名字表示参与范围，并不自动规定文本里的先后顺序。 |
| 显式开启“独立研讨” | `DELIBERATE`，先独立分析再互评汇总 | 它与“Claude 先做、Codex 后核对”不是同一工作方式。 |

源码依据包括 [selectors.ts](../../src/ui/hifi/data/selectors.ts#L303)、[threadReplies.ts](../../src/daemon/threadReplies.ts#L22) 和 [coordination.ts](../../src/daemon/coordination.ts#L76)。这意味着方案的重点应是让用户看懂并确认程序将采用的语义，而不是把“多成员”一律叫成共同研讨。

### 等待与异常

执行状态已经分成排队、等待成员、等待模型、等你处理、待核对、停止中、失败等，发送未知也有原请求查询。这一层不宜再整体重写。用户最需要的是：

- 一个主状态，不是顶部与底部互相重复。
- 明确“现在在等谁／什么”，能直达占用者或恢复项。
- 查询动作只查询，重试严格同号，放弃提示不代表停止任务。
- 关闭窗口时有进行中任务就说明影响，不能依赖用户记得手册。

### 看成果、返工与验收

现有交付与验收合同较强：待验收绑定具体版本，返工意见也冻结版本，旧交付会被新版替代。主要问题在主动作表达：

- 完成后首先出现的可能是通用导航，当前成果应成为第一动作。
- “按这些意见修改”保存后没有开始执行，主动作名与结果不符。
- 新版到达后，版本历史能列出 v1、v2，但没有把“上次你要求改什么、现在哪些变了”放在一屏。这个漏项不完全被 U22 或 U33 覆盖。
- 文件改动差异仍是前后原文，难以判断返工是否解决意见。

### 找历史

搜索、私信、命令面板、归档、看板和待我处理分别承担不同查找，不应该被强行压成一个“全部”页面。当前真正需要修的是：

- 任务/消息/成员/私信的入口名称与目的地准确。
- 待处理项显示人能认出的标题和来源。
- 搜索返回后能继续原来的筛选工作。
- 旧交付不能因最近 100 条窗口而被说成不存在。

### 关闭与升级

手册已经告诉用户最小化后任务继续、退出后不能继续，也明确最终 V51 的沿用数据入口。可是当前日常包仍要求普通人区分两个启动器，并把数据放在旧包目录，和正常桌面软件的心智模型冲突。最长期的使用场景是升级后仍然打开同一组项目、成员、草稿、附件和未知发送；应把这一点作为独立迁移验收，而不是只改帮助文字。

## 三个原总表没有单独收口的漏项

以下不是为凑数新增的已确认故障，而是跨多个原条目后仍然没有形成单一验收结果的使用链缺口。

### M01 手册不是完整的“从零到恢复”指南

[手册目录](../user-guide/README.md#L7)集中于执行状态、发送找回、通知、补交版本和一个异常示例。它没有完整覆盖项目与成员准备、房间协调者、多人协作、成果返工、文件差异、搜索、归档、关闭与升级。U08 只解决“应用里怎么打开手册”，没有解决“手册是否足以指导整个产品”。

验收不应是“帮助页有链接”，而应是普通用户只读手册即可完成：

1. 打开正确数据。
2. 选择项目。
3. 确认协调者和可用 AI。
4. 发出单人任务和顺序多人任务。
5. 找到结果、提出返工、验收当前版本。
6. 找到历史。
7. 理解关闭、退出、备份和升级区别。

### M02 “房间成员 ≠ 任务参与者 ≠ 本次收件人”没有统一解释

这是 U11、U12、U18、U20 的公共根因。成员加入房间告诉系统它可以被使用；本串参与者说明上下文范围；本次明确 @ 才决定这次谁被叫。普通用户不应从多个提示自行推导三层关系。

建议在房间信息、添加成员结果和发件预览三处使用同一套短词，例如：

- “本房间可用 5 位 AI”
- “本串已有 3 位参与者”
- “本次收件：Claude → Codex”

不要增加第三种“任务成员”管理页。已存在的机制按同一词汇暴露即可。

### M03 返工后缺少“意见 → 新版本 → 改了什么”的一屏比较

U22 修“保存意见后没开始”、U33 修文件 diff、U25 修验收动作，但它们没有合起来回答“我上次要求的三点都改了吗”。这是实际返工周期中反复阅读长文的来源。

建议新版待验收卡片同时展示：

- 上次要求修改的版本和意见摘要。
- 当前新版本。
- 文件/正文是否有实际变化。
- 每条意见的状态：有变化、未发现变化、需要人工判断。

这些状态必须来自绑定的版本和用户意见记录，程序不能凭模型自报声称“全部解决”。若没有足够证据，就如实写“需要人工核对”。

## 重点复核：“先 Claude，后 Codex”

### 当前事实

1. 中文相邻提及在触发和解析两层都要求特定边界，`然后@Codex` 不会成为正式成员。
2. 原请求的真实记录只保存了 Claude，因此进入单人 `DIRECT`；Codex 从未获得该项要求。
3. Claude 的回复自述 Codex 核对未发生，任务仍进入完成状态，说明用户可见文字与程序实际执行合同之间出现了缺口。
4. 如果两个成员都被识别，当前系统会进入有计划的 `AUTO`，并已有依赖步骤、上游结果冻结、阻塞和最终整合能力。
5. 因而“后端没有顺序协作”的说法不成立；“程序会从自然语言绝对可靠地推出用户想要的顺序”也没有被证明。

### 什么才算可靠表达

可靠不能靠向用户保证“模型会懂先和再”，而要靠三层可观察事实：

**第一层，收件人确定。** 用户在输入框看到的成员必须与服务端正式收件人一致。疑似提及无法解析时就地说明，不能继续把正文当普通文字发送。

**第二层，计划确定。** 多成员输入产生结构化计划，步骤有负责人和依赖。若用户明确写了“先 Claude、再 Codex 核对本次结果”，计划必须包含这层依赖；如果程序不能可靠形成该计划，应在派发工作前显示“需要确认顺序”，而不是让协调者自由解释后再宣布完成。

**第三层，完成确定。** 整项完成只以已接受计划中的必要步骤为准。Claude 成功而 Codex 未开始，界面可以显示“Claude 已完成，Codex 待核对／无法开始”，但不能把整项写成已完成，也不能发整项完成通知。

这不要求新增一个多智能体引擎。现有 `AUTO` 编排继续使用；新增的是前端的确定性提示、计划差距门和可见的完成契约。

### 发送前界面建议

不增加普通任务的确认弹窗。只在输入区显示一行可扫描摘要：

```text
交给：Claude → Codex
方式：按顺序核对
任务会在 Claude 本次结果形成后才交给 Codex
```

若用户只写了两个 @ 但没有顺序要求，则显示：

```text
交给：Claude、Codex
方式：自动分工；实际分工在计划通过后显示
```

预测计划应当标成“预计”，计划被程序接受后才标成“已安排”。不要让用户把前端猜测当成服务端事实。

### 现在的有效结果和动作

当前用户可看到的有效结果包括：

- 房间任务状态与执行成员。
- 协作详情中的步骤、步骤状态、负责人、依赖、上游成果和评审版本。
- 每个完成步骤的交付链接。
- 计划阻塞原因和恢复方向。

因此不应再新增一个平行的“协作结果”页面。应把现有信息中的一个当前步骤、当前结果和下一步提升到串顶；详情保留全部工程事实。

### 必须补的验证

至少需要一个隔离合成场景，但不在本次评审中执行：

| 场景 | 可观察结果 |
| --- | --- |
| 输入“然后@Codex” | 两个成员均成为正式收件人；输入标签与实际名单一致。 |
| 输入“Claude 先比较，Codex 再核对本次结果” | 形成 Claude → Codex 的依赖；Codex 开始前读取的是 Claude 本次冻结交付；不能使用旧文件替代。 |
| Codex 停用、程序缺失或预算不足 | 计划显示 Codex 未开始及具体原因；整项不完成；通知不说整项完成。 |
| 普通两个 @ 无顺序词 | 不会被强制串行；协调计划及并行/顺序关系可见。 |
| 邮件地址、代码、引用中的 @ | 不产生成员。 |

一次合成成功只能证明该路径可用，不能保证任意自然语言都可靠。若要承诺高可靠，应把关键顺序放到结构化计划或明确选择中，并把自然语言视为提示。

## 草稿、发送恢复与历史边界

这三类数据应在产品、存储和界面中使用不同名称：

| 状态 | 含义 | 应保留什么 | 允许的操作 |
| --- | --- | --- | --- |
| 普通草稿 | 用户尚未点击发送 | 正文、收件人选择、附件、发送设置、更新时间 | 继续编辑、明确放弃、在草稿箱清理 |
| 待确认发送 | 已点击发送，但客户端未确认服务端是否接受 | 原 `commandId`、原参数、请求摘要、时间、目标身份 | 只读查询、同号重发原信封、明确放弃提示 |
| 正常历史 | 已确认接受并形成消息/任务 | 服务端消息、任务和交付 | 在会话、搜索、任务历史中查找 |
| 已解决恢复项 | 原发送找到，后续草稿已保留 | 正常消息身份和定位 | 不再常驻异常面板 |

当前问题有三处：

- U02 的“清理草稿”删除同一持久化键中的待确认发送。
- U29 的成功发送仍占恢复面板。
- U30 找回后先到任务概况，不能直接到原消息。

正确边界是：

1. 普通草稿清理永远不碰待确认发送。
2. 查询只读，不创建任务，不调用模型。
3. 重发仅在未接受时发生，并严格复用原请求身份。
4. 已在服务端接受就视为已发送，后续“重发”不能制造第二任务。
5. 正常消息不再展示异常恢复；未确认/拒绝项进入待我处理或命令面板的异常清单。
6. 新写草稿、附件和后续错误不能被旧发送回执清掉。

这也回答了 U28 的范围：不需要“全项目每次发送历史”，需要的是“尚未解决的发送台账”和可靠的历史任务定位。

## 对“六批施工”的评估

原方案的六批叙事有条理，但作为排期不够可执行：

1. **第一批过大。** U01–U03、U17–U20、U26、U31、U35、U47、U49 同时包含输入契约、持久化、文件查询、预览、模态框、全局提示和窗口生命周期。任何一项有风险都会阻塞整批，且 U47 与 U49 和任务契约没有直接依赖。
2. **第二批过宽。** U04–U16 加 U43、U51、U52，混合首启、历史迁移、成员、权限、房间、搜索、预算和设置保存。它无法用一位负责人或一个验收故事收口。
3. **结果链被拆开。** U31 在第一批，U33/U34 在第三批；U24/U25 在第三批而辅助动作在后续。当前结果、改动和撤销入口应由同一数据与动作合同先定，但 U34 应复用现有 `changeset.undo`，无需等待新后端。
4. **查找链彼此独立。** U37–U42 虽有共同目标，但不应一次做统一搜索。应先改错落点和可识别摘要，再按需求添加筛选和分页。
5. **设备连接排在通知之后没有依据。** U46 是低频高级功能，不应在同批占核心注意力。
6. **键盘与可访问性放最后会制造返工。** U48 应在第一批改共享弹窗、菜单和卡片时同步完成，每页再验收。
7. **52 项没有真正退出机制。** 总表把已确认缺陷、条件缺陷、普通优化和产品新功能都放在同等状态，容易形成“全部做完才算修好”的长期工程。

建议改成以下顺序。每一步都先在隔离数据中写清用户式验收，再进入下一组依赖项。

### 第一批：真实性与意图保护

最小发布集，目标是停止“看起来做了”和“改变了用户要求”：

- U17：正式收件人与中文相邻提及一致。
- U20：发送前显示实际预测收件人。
- U18 + U19：接受计划、显示真实步骤，按计划完成；复用现有编排。
- U26：继续操作保持原写范围，或明确写“仅分析”。
- U02：清理草稿不再删除待确认发送。
- U24 + U25：当前页面、当前结果和下一动作一致。
- U34 接通已有 `changeset.undo` 与 U35 的截断标识可同期作为小型信任修复。

这些项目并不要求同一开发者在同一提交内完成，但必须在同一验收故事中一起通过；“漏人或计划错误”不能因为按钮已经改好就宣布体验修完。

### 第二批：不丢输入与安全退出

- U03：草稿保留与可见清理。
- U29 + U30：异常恢复面板收敛，找到后定位原消息。
- U01：有活动工作时关闭影响提示。
- U49：提示计时器身份与关键失败持续显示。

在 U29/U30 完成前，不应先删原输入框的查询入口。

### 第三批：成果、返工与当前版本

- U22：提交并开始返工。
- U31：按任务查询交付，不受项目最近 100 条限制。
- U33：可用 diff 和继续读取。
- M03：新版与上次意见的对应关系。
- U42：待我处理显示可辨认任务和来源。

先保证当前版本与要求对应，再优化所有历史浏览。

### 第四批：数据入口与首次使用

- U04：单一日常启动入口和旧数据识别。
- U06：备份位置可见。
- U07/U13：项目就绪摘要。
- U05：取消固定启动项目。
- U08/M01：完整手册与应用内入口。

这一阶段重点是一次完成安装、升级、备份和帮助闭环，不再各加一条孤立提示。

### 第五批：查找与低频配置

- U09、U21、U27、U37、U39、U41、U43、U45。
- U10、U32 的文件名部分、U38 的改词、U44 的作用域收敛可在这个阶段按小项处理。

U45 的代码路由与真实 Windows 通知点击必须分开记录结果。

### 持续基础项

- U47 + U48：共享 Modal/Drawer、Menu、Card 的保存保护、焦点、键盘语义和返回位置。
- U51：只补保存反馈与未保存保护。
- U50/U52：按用户测试结果减少信息重复和术语。

基础项不应等到所有页面完成后再返工；新改过的页面必须直接复用修好的共享组件。

## 建议先做的 7 件事

1. **把自然语言收件与任务计划做成同一契约。** 修 U17，露出 U20 的收件摘要，复用 U18 现有依赖编排，按 U19 的已接受计划判定完成。先不新增确认弹窗或第二编排器。
2. **把普通草稿和发送恢复账本分开。** U02 与 U03 一起设计，确保“清理草稿”不破坏待确认请求。
3. **修 U26 的继续语义。** 原任务要求写入就继续写入范围；只能只读时必须改名并解释未完成。
4. **合并 U24/U25，建立上下文动作规则。** 待处理原因第一，当前交付第二，当前页面无意义导航不显示。
5. **让 U22 的返工主动作真的开始修改。** 同时用 M03 显示新版与上次意见的对应关系。
6. **立即消除内容丢失与入口断层。** U35 不再静默截断；U34 接通已有 `changeset.undo`，显示冲突、人工处理和续跑结果，而不是重写恢复能力。
7. **让长期成果和待办可认。** 先做 U31 的任务级交付查询，再做 U30 的精确消息定位和 U42 的可识别待办；旧任务不能被最近 100 条窗口写成空。

如果还要放一个第八项，应是 **U04 的单启动入口与旧数据识别**。它直接决定用户升级后看到的是自己的项目还是一片空白，适合作为独立升级批次，而不是混进普通界面优化。

## 三个端到端故事与验收标准

### 故事一：Claude 先比较，Codex 再核对

用户输入：

> @Claude 先比较这三个方案，然后@Codex 核对 Claude 本次比较有没有遗漏。完成后一起告诉我。

用户应当看到：

1. 输入区出现两个可辨认成员标签，并显示“Claude → Codex，顺序核对”的预测路线；不需要确认弹窗。
2. 发送后，程序实际接受的计划显示两步依赖，第二步绑定第一步本次成果。
3. Claude 工作时 Codex 状态为“等待 Claude 结果”，不会先独立回答。
4. Codex 开始后读取的是 Claude 本次冻结交付，不能替换成旧文件。
5. Codex 失败或未开始时，整任务显示“待核对／未完成”，有具体原因和查看入口，不发整项完成通知。
6. 两步都完成后，串顶显示当前合并结果和“查看交付”主按钮。

可观察验收：

- 正式 mention 列表含两位成员。
- 第二个步骤的实际开始时间晚于并依赖第一个步骤的交付版本。
- 上游交付 ID、版本或 hash 能在协作详情中对应。
- 未满足计划时父任务不为 `DONE`。
- 普通两人无顺序请求仍可保持其他合理协作方式。

### 故事二：发送后断线，重开仍找得到

用户在隔离环境中发送一条消息，服务端已接受但客户端丢失回执。用户这时又写了新草稿，随后关闭并重开。

用户应当看到：

1. “待我处理”或命令面板中有一条可按目标、时间、摘要辨认的未确认发送。
2. 新草稿仍在原输入框，没有被旧发送提示替换。
3. 点击“核对”只查询原请求，不新增模型调用。
4. 找到后直接进入原消息并短暂高亮，能继续从该串工作。
5. 恢复完成后，普通输入区不再保留蓝色异常面板。
6. 清理普通草稿不会删除任何尚未确认的发送。

可观察验收：

- 查询前后任务数量、消息数量和模型调用计数不增加。
- 同号重发只在一个任务身份内收口，不出现第二条相同请求。
- 新草稿、附件和后续错误逐项保留。

### 故事三：收到成果，要求修改，验收新版

用户打开待验收的 v1，发现两处要改。用户写下意见并点击主动作。

用户应当看到：

1. 主动作叫“提交并开始修改”，一次完成意见保存和返工派发。
2. 返工绑定 v1 的完整身份；界面显示“正在修改”，不是“意见已保存，尚未开始”。
3. v2 完成后成为当前待验收版本，v1 标记已被替代。
4. 一屏显示 v1→v2 的主要变化，以及上次两条意见当前是否有变化证据。
5. “确认验收”和“继续修改”只作用于 v2；旧页面不会还能批准 v1。
6. 文件是否应用、人工是否验收、Git 是否提交分别显示，不互相冒充。

可观察验收：

- 单击主动作后出现真实返工运行，不需要第二次执行按钮。
- v2 页面中的意见来自用户原始记录，不是模型自行总结。
- 如果程序无法判断某条意见是否解决，明确写“需要人工核对”。
- 验收 v2 后不会再出现同一待验收事项。

## 总体建议

允许进入方案的下一阶段，但不建议按原表一次性施工 52 项，也不建议先做一版大而全的“统一体验框架”。先把当前证据最强的信任缺陷修成完整纵向闭环，特别是 U17–U20 的入参、计划和完成边界，以及 U02、U26、U22、U24/U25、U34/U35。随后再整理启动与数据入口、任务成果查询、长任务历史和共享键盘/焦点基础。

每项完成都应记录四件事：用户看到的原文、程序实际接受的动作、服务端确认的结果、隔离数据上的用户式验收。只有源码实现、没有真实窗口或原生系统结果时，应继续标为相应待测，不用“代码已接”替代用户可用。
