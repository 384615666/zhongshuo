## 原因与处理

只读查询截图对应的本机任务，确认 `stage_work` 返回问候正文后，`turn.outputInvalid` 记录 `finalText 不是 JSON（期望 TaskComplete 结构化输出）`，自动 `format_repair` 随后被旧 Pi 适配器拒绝。这是结果格式与补交链路缺口；R138 只修复 Harness，没有把 Pi 同类缺口一起补齐。用户的项目权限没有因此被修改。

本轮 Pi 适配器把完整的本轮 `outputSchema` 和最终 JSON 规则附加到原生系统指令，保留常驻指令，每轮刷新准确 resultKey。模型正文不由程序包装成伪造的成功 TaskComplete；正式 worker 的结构、身份、交付与工作证据校验保持。

格式补交仅接受官方 Pi 1.4.0、有 schema 的文本以及独立的新会话。CLI 明确禁用全部工具并以 `--exclude-tools *` 排除工具，关闭扩展、MCP、技能、模板、主题、项目上下文文件和项目配置审批。补交使用自有替代系统提示词，并阻止自动发现的追加系统指令。提交模型前必须确认关闭原生自动重试与压缩、会话历史和队列为空。工具调用、工具执行事件或意外重试均拒绝成功并停止；版本预检期间的停止请求也会阻止启动。

私信补交与后续普通对话使用不同会话，后续不续接格式补交会话。普通完整权限范围不变，只读分析、项目受限编辑和图片的认证没有扩大。Pi 无需安装新插件或修改模型、凭据配置。

实现依据为本机安装的官方 `@earendil-works/pi-coding-agent@1.4.0` CLI、resource loader、工具选择及 RPC 实现，并核对 [官方 CLI 文档](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/cli.md)。schema 通过系统指令传递，不宣称供应商原生约束解码；输出仍由正式合同验收。
