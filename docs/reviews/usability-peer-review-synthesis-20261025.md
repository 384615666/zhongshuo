## 汇总时的判定标准

- 事实与设计偏好分开：代码中可以确认什么，哪些行为仍需实机观察，哪些只是需要重新评审的既有产品规则。
- 从完整故事判断价值：用户能否顺利开始、知道谁接单、等待、找结果、提出修改、返回旧现场和恢复异常。
- 改法是否减少负担：不能为每个不便都增加面板、模式或确认弹窗；普通路径保持直接，异常路径才增加必要处理。
- 保留实际边界：查看不派发，不自动重放、扩权或合并独立会话；待验证不称已验证。
- 52 项是排查候选，不意味着要做 52 个独立新功能。共享原因应合并成少量完整流程整改。

## 两位共同认可的方向

1. **先恢复用户对结果的信任。** 漏收件人、没完成却说完成、继续任务静默切只读、清理草稿带走发送恢复记录、引用悄悄截断，都应优先于大范围视觉统一。
2. **复用已有能力。** 项目已有 AUTO 计划、步骤依赖、上游交付绑定和正式撤销链；主要任务是让入口、说明、状态和已有后台一致。
3. **不把 52 条等同于 52 个必做功能。** 有些是直接错误，有些是条件缺陷，有些是合理默认或低频增强。应合并公共原因，暂缓缺少频率依据的大方案。
4. **普通操作不增加额外确认。** 不为每条消息加计划弹窗，不为每次建房加必填选人，不为所有弹窗都加退出确认；只在有实际歧义、未保存内容或不可恢复影响时处理。
5. **按真实故事验收。** 发送、等待、结果、返工、验收、历史与异常恢复应连起来测；代码中有接口不等于用户能顺利完成。

## 对原 52 项的关键修订

| 条目 | 评审指出的问题 | 统筹处理与最小整改方向 |
| --- | --- | --- |
| U18 / U19 顺序与完成 | 不应从单人漏发这次记录推出系统根本没有顺序编排；正式计划已有完成门 | **收窄诊断。** 修“提及识别 → 路由进已有协作 → 实际接受计划 → 按该计划收口”。不另造编排器，不扫描任意历史文字自动增加必要工作 |
| U34 撤销 | 正式 `changeset.undo` 和可续跑执行已存在；当前正式改动详情没有入口，恢复页也没有准确带过去 | **复用现有命令。** 接“恢复这些文件”、影响预览、冲突／人工项和续跑结果；不能把提交软回退当文件恢复，也不能称后台恢复能力不存在 |
| U10 页面范围 | 搜索当前项目、看板侧栏项目、待办全项目各有合理目的，不能只因默认不同就认定不合理 | **降为用语与可发现性优化。** 不强行统一默认；只确保范围明确、被排除内容可理解，且能方便切回 |
| U12 / U13 / U20 成员与计划状态 | 添加成员时已经显示要加入哪些房间；成员卡已能报告若干配置问题；协作详情已有实际计划 | **更正“未提供”倾向。** 在已有信息上厘清本房间可用、本串参与、本次收件；把有效主结论与已接受计划放到更容易看到的位置，不重做一套状态系统 |
| U01 / U26 优先级 | 关闭通常就是退出，U01 不是所有情况下的 P0；“继续原请求”切只读却真正改变用户要求 | **U01 按 P1 评审，U26 提升为 P0 意图问题。** 只在有活动工作时提示退出影响；继续动作保持原边界，不能自动提权或自动改成只读 |
| U24 / U25 操作 | 打开当前串与完成后查看结果源自同一上下文动作规则 | **合并施工。** 按当前对象、页面、待处理原因和有效交付生成动作；文案与落点一致 |
| U28–U30 发送找回 | 跨页入口必须补，但建全量发送历史、另造索引可能重复现有搜索 | **缩小首期。** 用现有发送引用与未确认账本做跨页待处理入口，查询后定位原消息；正常历史沿用已有会话与搜索。不把用户又送回“先找原串才能查询”的绕路 |
| U11 建房 / U21 新私信 | 默认直接创建很方便，强制选人、命名或询问继续旧会话会增加摩擦 | **保留快速主路径。** 调整成员是可选项；新建私信仍新建，不能暗中复用或合并旧上下文；先增加可辨认时间与摘要 |
| U32 / U40 查找 | 文件名／路径查找与全文索引不是同一个规模；归档已经披露只查已读内容 | **先做直接查找和准确范围。** 全文索引、服务端全归档搜索单独评估；不把已经披露的分页写成毫无提示的假空 |
| U43 / U51 设置 | 可用小型稳定目标表修搜索；混合保存方式本身不必全改成自动保存 | **做小修。** 设置名与实际控件绑定，补常用别名；给出未保存／保存中／成功／失败及生效范围，无需全站保存框架重写 |

原表保留 U 编号作为追踪线索；这些修订应与原条目一起看，不以旧标题或旧优先级直接开工。

## 尚有分歧的地方，以及统筹取舍

| 主题 | DeepSeek 的倾向 | GLM 的倾向 | 统筹建议 |
| --- | --- | --- | --- |
| 如何表达顺序 | 提及与计划预览接已有 AUTO，只有无法覆盖必要顺序时再处理歧义 | 两位成员提供共同处理／独立研讨／按顺序的轻量选择，首期只做线性顺序 | 不要求每次多 @ 都选模式。明确的两步要求复用现有计划，实际接受后显示顺序；有歧义才给轻量选项。不能声称已能确定性理解任意自然语言依赖 |
| 键盘与弹窗基础 | U48 属共享基础，应在相关页面修改时同步修 | 暂缓全站键盘、通用弹窗重构，先保护高风险表单 | 不做阻塞主流程的大重构；**改到哪个弹窗或卡片，就同时补该处焦点、键盘、未保存保护**，其余按可验证范围逐步覆盖 |
| AI 准备状态 | 已有状态不少，U13 更适合合并和降级 | 一眼知道是否能接任务仍是重要缺口 | 保留为入口改进，不制造未经真实调用证实的“模型已验证”绿灯。配置预检、程序可启动、真实响应分别显示，问题对应具体操作 |
| 草稿长期保留 | 未发送默认保留到发送或主动删除 | 取消 24h 静默过期，但不能无限堆积 | 先确保不会突然丢字，再给可见条数、容量和主动清理；普通草稿与未确认请求无论如何独立保留，不另建复杂同步系统 |

这些取舍是修订后的设计建议，仍待用户评审；两位并没有替用户批准全部施工。

## 建议先落地的八组工作

| 组 | 范围 | 用户能感知的完成标准 |
| --- | --- | --- |
| 1. 请求到完成一致 | U17–U20，复用现有协调 | 用户输入 Claude 先做、Codex 后核对；两个收件人都被接收，依赖绑定本次成果，核对未发生时整项不报完成 |
| 2. 继续不改变原意 | U26 | 改文件的原请求不会静默变只读；只能分析时清楚写出，保留权限与版本边界 |
| 3. 不丢输入与找回线索 | U02 / U03 | 清理普通草稿不删除未确认发送，隔天回来仍能继续长草稿；容量与主动清理可理解 |
| 4. 当前结果与修改真的开始 | U22 / U24 / U25 / U31 | 结果入口直达当前版本，正式修改意见主动作确实排队执行，旧成果不会因项目最近 100 条窗口被误报没有 |
| 5. 跨页处理不确定发送 | U28–U30 | 在其他项目也能找到待确认请求，只读核对后定位原消息；后来写的草稿与附件保留，不重复建任务 |
| 6. 文件内容与恢复如实 | U34 / U35 | 引用不静默截断；正式详情接已有撤销，明确哪些文件成功、冲突或需人工，失败可准确续跑 |
| 7. 日常入口与备份可找回 | U04 / U06，独立升级批次 | 更新程序仍打开同一份数据；备份完成后能看到位置并打开，不靠记住旧包路径 |
| 8. 修改经过的公共交互达标 | U47–U49，贯穿各组 | 长表单误关可恢复或明确放弃；键盘与焦点可用；旧提示计时器不会清掉新错误 |

八组不要求一个大 PR 或一个人一次做完。应按依赖拆成小改动和完整验收故事；小型错误如 U35、U49 可独立修复，不能被大型编排工作拖住。

## 暂缓和补充

**首期暂缓：** 全量发送历史复制、工作区全文索引、全归档新搜索引擎、每个页面的新向导、每次建房必选人、全站自动保存重构、重新开发撤销引擎，以及从任意自然语言自动生成或扩展必要工作。

**需要补成完整使用故事的三处：**

1. **整本手册。** 已交付的 V51 手册重点覆盖近期四项功能及基本操作；不能用“帮助里有链接”替代全产品指南。后续要覆盖项目准备、协调者、成员范围、多人任务、返工、搜索、归档、备份与升级。
2. **成员的三层关系。** “房间可用谁、本串已有谁、本次交给谁”采用同一套短词，直接放在现有位置，不新增一套成员管理页。
3. **返工意见到新版本。** 先在当前成果附近保留上次原始意见、新版本和真实变更入口；是否解决仍由证据和用户核对，不把模型自报变成“每条已解决”的程序认证。
