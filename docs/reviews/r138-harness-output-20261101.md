# R138：Harness 正式任务结果与格式补交

用户现场出现 Harness 已回答“收到”，任务却仍未完成；横幅提示只读、受限编辑和格式修复未认证。

## 原因

只读查询截图对应的本机运行，确认两条相同链路：普通问候与 Pi 转交的 DSH 子任务均先返回自然正文，随后 `turn.outputInvalid` 记录 `finalText 不是 JSON（期望 TaskComplete 结构化输出）`；自动格式补交轮又被旧适配器的 `repairOnly` 拒绝。原回复没有丢失，后一个能力错误掩盖了最初的结果格式错误。

R137 的真实验证覆盖底层读取、跨进程续接和退出，未通过正式 worker 验收 TaskComplete；这次补上这一缺口。旧库仅作只读诊断，不修改任务状态，不重放现场任务或搬迁数据。

## 修改

- 连接组件更新为 0.1.2，将本轮完整 `outputSchema` 作为 agent 作用域的系统指令传入官方 SDK，明确最终消息仅含原始 JSON、固定结果身份和真实结果。没有本地包装自然正文来伪造 TaskComplete，正式 worker 仍严格校验 schema、resultKey 与工作证据。
- 独立的 `format-repair` 模式只接受有 schema 的文本与新会话。禁用模型可见工具，并在官方工具策略与执行管道阻止全部工具调用；模型尝试调用工具即结束补交，不重复原业务。原生完整权限只用于正常执行，未扩展普通只读或项目受限编辑认证。
- 适配器要求组件握手明确支持结果格式与补交，旧组件在提交任务前提示升级；格式补交不能续接已有 provider 会话。私信补交创建新会话，后续正常私信也不复用补交会话。复核同时修正私信恢复引用把 `thread_id=null` 转为 `''` 的既存错误，保留真实作用域供严格身份比较。
- 保留结果不合法、工具拒绝、取消、未知退出与实际进程退出的原有判定。Pi 的正常原生调用保持；其格式补交仍未开放。
- 手册、离线手册与打包说明同步升级步骤。已失败的旧任务不自动重跑，由用户在原串明确继续。

SDK 依据为锁定的官方 0.2.1-rc.5 已安装声明与实现，以及 [官方工具作用域文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/tools/README.md)。`restrict` 单独使用不涵盖自身作用域新增工具，因此补交还需要完整执行阻断与最终工具列表清空。schema 在此版本通过系统指令传递，不宣称供应商原生约束解码；模型输出仍需正式合同验收。
