# R187：模型查询阻塞与 Harness 连接组件随安装器更新

用户在 beta.31 仍见 `room.list`、`project.memberWorkload` 15000ms 超时，并补充 Harness 模型清单读不到，随后确认未执行过上版要求的 `setup.cmd`，要求将这一步整合进安装包。

## 原因与修改

- 当前已安装众说为 beta.31；本机 Harness 已是 0.2.2-rc.1，专用 profile 中组件仍为 0.1.3，其声明仅支持 0.2.1-rc.5。直接执行元数据命令时，官方 Harness 明确输出 `skipping profile bundle` / `incompatible with dsh`，随后不提供众说 JSONL 接口，原适配器等待 30 秒才报超时。没有绕过版本检查或使用 allow-version。
- 模型清单和思考等级查询原来占住同一连接的 FIFO，排在后面的房间、成员、模板及写操作可能先于它超时。R186 只处理设置读取，范围不足。本轮将 `member.runtimeCatalog` / `member.runtimeOptions` 作为明确列举的独立元数据查询：仍等此前写操作完成，以便看到新建项目或已保存配置；开始后不占用默认 FIFO，写命令彼此仍按原顺序执行。没有开放所有 `.get` / `.list` 并发，也没有延长默认 15 秒期限。
- 适配器识别官方明确拒载众说组件的诊断，立即结束自己启动的查询进程，给出运行 `setup.cmd` 的升级提示，不回显原 stderr。现场同一旧组件由等待 30 秒变为约 160ms 返回明确错误；未知扩展的拒载不误判为众说组件失败。
- Windows 安装器完成文件复制后自动执行随包 Node + `setup-deepseek-harness.mjs --installer`。只配置众说的 Harness profile；不安装 Harness 本体。检测不到 Harness 则跳过，支持 PATH 和 Windows 常规安装入口；受支持版本下，当前已安装组件全部文件哈希一致时只做就绪检查，否则用官方 `dsh plugin --profile zhongshuo add --save-exact` 更新经校验的随包归档。归档继续放在用户 Harness home 的持久连接器目录。
- 自动配置失败时，众说安装保留，安装器显示警告且完成页保留 `setup.cmd` 重试指引。静默模式同样不自动启动众说，失败写 Inno 日志的结果码。版本/就绪命令有 30 秒期限，插件安装命令有 120 秒期限。配置、MCP、会话、其他 profile 不由众说复制覆盖或删除。
- 操作手册和随包组件说明同步为安装器自动配置；`setup.cmd` 保留给失败重试或先安装众说、后安装 Harness 的用户。
