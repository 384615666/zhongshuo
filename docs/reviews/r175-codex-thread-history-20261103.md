# R175：Codex 内部会话自动归档与原生续接

用户发现众说的内部输入进入 Codex 客户端“最近”列表，确认采用“调用结束自动归档、续接前恢复、旧记录按精确 ID 整理”的方案。本轮在公开源码仓库实现；没有覆盖安装、直接归档用户现存 Codex 对话或修改用户运行数据库。

## 实现

- 适配器保留持久会话，在成功、失败或停止终态后异步检查 `thread/read` 的身份和空闲状态，再执行 `thread/archive`。会话尚在启动、存在同线程活动轮次、provider 仍报 active 或原连接已结束时跳过；稍后收到 idle 状态可重试。
- 每线程保存归档/恢复状态。下一轮等待在途归档完成，检查持久路径是否位于 `archived_sessions`，必要时 `thread/unarchive`，然后以原模型、权限、cwd 和常驻指令执行 `thread/resume`。归档回执丢失也重新读取实际状态；恢复失败不创建替代会话、不重发模型请求。
- 归档元数据请求单次上限 750ms。归档失败只记录固定诊断，不覆盖终态、交付、预算或执行事实。初始化握手由并发调用共享；维护握手超时会废弃该连接，防止迟到响应使后续真实派发落入“已初始化”错误。
- 新后台每个正常 tick 最多整理一个启动时已有的候选。来源仅为本数据根中 Codex 适配器生成的 `runtime_sessions` ID 和精确 provider ID；要求有关执行已终态且同成员没有未收尾执行，并在实际归档前重查。UNKNOWN、在途、没有正式执行证据、无法确认归属的记录保持可见。维护与正式派发共用成员适配器，纳入原有停机收拢，零模型调用。
- 旧记录整理随新版运行后启用，避免先归档再让旧版直接 `thread/resume` 而破坏续接。未改 Claude、Harness、Pi 的会话策略；Pi 已有专用会话目录，其余渠道没有可据此直接确认的桌面列表刷屏现场。

## 验证与边界

本机官方 Codex CLI 0.166.0 的隔离 `CODEX_HOME` 元数据验证通过：新建空会话→关闭时归档→历史整理元数据调用→新进程恢复同一 provider ID→再次关闭归档，并确认 JSONL 留存。未执行 `turn/start`，真实模型调用为 0；最终证据为 ignored 的 `dist/codex-thread-archive-20261103/native-final.json`。另以原生协议确认，归档后直接 `thread/resume` 会被拒绝，因此显式恢复是必要步骤。

新增本地协议测试覆盖正常/失败/停止、同实例与新连接续接、归档并发、回执丢失、恢复失败、活动会话保护、idle 迟到、维护握手超时与并发握手。真实 SQLite + fake 工作流验证旧记录资格和不改写执行事实；实际 `startDaemon` 定时链路验证仅使用元数据请求、`real_calls=0`、任务仍为原成功状态、正常停机。既有多轮协议夹具补充 `thread/read` 元数据响应，不改变原业务断言。
