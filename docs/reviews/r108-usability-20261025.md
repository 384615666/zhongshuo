## 四项最终行为

### F1：共用权威执行状态

`executionStatus` 合同和 daemon 投影由 room.pool、task.get、task.details、DM conversation.list 共用；房间摘要、串顶/详情和 DM 使用同一组件及摘要函数。覆盖 0-run 启动前失败、队列/准入、在途工具、等待同伴/用户、STOPPING、UNKNOWN、完成与待验收；状态附实际执行/等待成员、阻塞依据、最后真实活动、既有成果和就近处理入口。

“查资料/处理文件/执行命令”依据结构化工具 action 与尚在执行的真实活动，完成过的工具不冒充当前工作；心跳不更新真实工作时间，没有百分比。待验收只在正式 REVIEW 且实际等待用户验收时显示，不覆盖仍在执行、停止中或 UNKNOWN。成员被停用的 0-run 旧审计顺序按明确事件识别，后续重派仍会使旧失败失效。

### F2：持久原请求与只读找回

发送前以可信数据根和本机用户命名空间耐久保存原 commandId、完整冻结参数、目标和 hash；保存失败不发请求。已有未知信封、出站账、草稿和附件仍为同一套结算来源，最后一次引用在成功/拒绝后也可查询并跨重开恢复。

正式 `message.lookupSubmission` 只读回执，核对当前可信用户/项目/会话/目标和原请求 hash，覆盖根消息、串内回复、私信；不开放任意 scope 枚举，不调用 message.submit。未查到、过期与查询失败保留原引用，不自动换号重发。找到后只结算对应快照并由正式深链打开原任务/会话，后来草稿、附件及跨项目导航不被迟回执覆盖。

正式手动打开/冷深链与 sendEnvelope 共用身份初始化，启动设置请求延迟或失败时仍可恢复；不能以随机生产 namespace 或内存保存绕过耐久门。原生验收发现的旧错误残留已按 draftKey+commandId 清理；新请求错误和后来草稿不因旧请求查询成功而被清除。

### F3：真实桌面通知与持久去重

迁移 059 保存通知游标、通知记录与投递尝试。daemon 事件在完成、执行失败需处理、等待用户输入或验收时产生通知；首次游标从当前事件水位开始，分页只前移已处理范围，子任务不轰炸，持续同态安静。去重绑定真实事件/运行周期，同任务返工的新周期可再次通知。

renderer 只向 main 交付通知 ID。main 从 daemon 领取并校验服务器标题、正文与定位，先保存 show_requested，再实际创建 Electron Notification；shown/failed/clicked/closed 分开记账，投递状态不充当业务成功。断线、重开及不确定投递不会自动重复发送。实际 `thread_subscriptions.muted` 生效；设置页读取并回读正式订阅，展示投递健康，不采用原型的未保存全局偏好。

隔离实机 4 个显式 Fake 任务/4 个成功 turn，真实调用 0；4 条通知均有真实 show_requested→shown、attempts=1。重开前已有两条的尝试和显示时间完全不变；另两条来自最终候选明确新建的场景。Settings 实际显示尝试4/请求显示4/系统shown4/未知0/失败0/点击0。

**实际 Windows 通知点击未验。** 编码与指挥会话分别只读发现，Sky 都没有返回通知中心、任务栏或 ShellExperienceHost 可操作窗口；技能禁止 Win 快捷键及自造 UIA 目标。没有人工 emit click、伪造 clicked 回执或更改系统通知/隐私设置。主进程点击 handler 和正式深链导航有隔离测试；这与操作系统端实际点击分列。
