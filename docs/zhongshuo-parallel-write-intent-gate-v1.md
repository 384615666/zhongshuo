## 0. v1.1 相对 v1 的修订（外部评审吸收）

v1 的核心流程被指出**正确性论证不通过**：它让多个 Agent 直接写同一目录，却套用了独立分支「最后合并」的逻辑，而两者安全前提不同。本版据此修正：

| # | v1 的问题 | v1.1 修正 |
|---|---|---|
| 1 | 承诺「声明错误不破坏正确性」「任何文件不会被覆盖」 | 删除。原目录并行下，A 写入后 B 按自己先前读到的内容覆盖写入，A 的修改可能已丢失，事后快照无法还原 A 的独立版本 |
| 2 | 把既有快照称为「精确到文件 hash 的冲突检测与解决通道」 | 收敛为「检测可观察到的变化和潜在重叠；证据不足时保留归属不确定状态」。引用主设计条款不构成该能力已实现的证据 |
| 3 | 整合闸门只有一种定义，「应用」语义不清 | 按两种模式分别定义检查对象（§5）；补版本绑定、失败恢复、未执行验证的记录规则；删除「秒级/毫秒级」等时间保证 |
| 4 | 「无锁 ⇒ Agent 崩溃后其他任务不受影响」 | 不成立。改为：记录失败现场、核对进程与受影响范围、暂停依赖该成果的任务（§7） |
| 5 | 断言过强（「互斥做不到就不该做」「预防等于重复建设」「业界无一采用」） | 降低强度，改为限定条件下的判断（§1） |
| 6 | 未区分越界与归属不明 | 新增 `out_of_scope`（超出批准范围）与 `attribution=ambiguous`（归属不可靠）分开记录（§4） |
| 7 | 「接口变更是唯一值得排队的场景」 | 放宽：共享测试数据库、迁移、全项目格式化等同样可能需要排队或隔离（§6） |

## 1. 背景：为什么不优先走「文件锁 MCP」路线（限定条件版）

外部讨论的 MCP 公告锁方案（上传公告占用文件 → 轮询等待 → 改完解除）本质是**文件级悲观锁**。在下列限定条件下，本提案认为它不是众说的首选：

1. **在众说的边界内，锁给不出强互斥保证**。强互斥需要控制全部写入入口并在写入时校验 fencing token；§14.1 第 6 条与 §6.2 已明确外部编辑器、终端与有本机权限的 CLI 不在协调范围内。这不否定受管理 Agent 之间协调的价值，但决定了它能承诺的范围：**减少冲突，而非互斥**。
2. **范围声明不可信是常态**。Agent 动手前预测的文件集合几乎必然欠声明；悲观锁在「持锁扩锁」时重新引入死锁。乐观机制下欠声明只是检测晚一点——但同样**不保证不丢改动**（见 §4）。
3. **发现问题的成本与减少问题发生的成本不同**，两者不等价；本提案选择先做检测与整合，是基于实现成本与既有机制复用的取舍，不是「预防没有价值」。
4. 受管理执行范围内的整组原子申请、租约、fencing 等机制在 §11.4 已有对应基础；若要走锁路线，应复用它们，不另起服务。

结论：**本提案主张冲突主要靠检测和整合处理，不靠 Agent 运行时锁预防。** 公告保留，降级为「意图声明」，用于调度与依赖发现，不承担互斥。

## 3. 修改意图声明（write_intent）

任务进入写入阶段前，由宿主（不是模型自觉）依据任务输入生成并登记：

```
write_intent {
  intentId, taskId, runId,
  declaredPaths: [文件或目录子树...],  // 预计修改范围，第一版不做任意 glob 交集
  declaredInterfaces: [契约标识...],   // 预计改动的对外接口/模块契约
  kind: modify | interface_change | refactor | format,
  status: active | done | cancelled,
  createdAt, updatedAt
}
```

规则：

1. **声明错误不破坏「声明机制」，但也不保证不丢改动**。欠声明会增加重叠检测的工作量，并可能触发 §5 的重叠处理；在共享目录里，它**不能**保证被覆盖的改动可以找回。界面不得把「已声明」表述为「已受保护」。
2. **声明用于三件事**：界面持续可见「谁在改什么」（满足 §14.1 第 5 条）；调度器发现任务间依赖（§6）；整合闸门的重叠预检输入。
3. **声明不授予任何权利**。能否写入由 `writeConcurrencyPolicy`、写入者上限、修改授权、允许目录与 runtime 权限共同决定，与声明无关。界面必须区分「已声明意图」与「持有写入权」。
4. `kind=format`（全项目格式化类）必须触发人工确认：文件面过宽会淹没重叠检测，建议拆任务或单独窗口执行。
5. 路径身份复用 §3.3 的 canonical path 与目录锁域判定，不另写一套规范化（junction、符号链接、大小写）。

## 4. 乐观并发：检测与记账（复用既有机制）

并行写入期间不干预任何写入。冲突处理沿用既有口径：

- 受管理写入者之间同一文件并发写入 → `attribution=ambiguous`，停止自动应用/撤销，三方内容查看（§14.1 第 2 条、§14.2）。
- 外部进程改动 → 前后快照 + 文件事件检测标注（§14.1 末段）。
- 撤销降级 → 人工三方预览（§14.5 RT-22）。

本提案对 §14.1 只增加两条要求：

1. **重叠扫描**：每次受管理写入完成后，宿主对本次 ChangeSet 与其他 active ChangeSet 做一次文件级重叠扫描，结果记入 `overlaps: [{changeSetId, paths, resolution}]`。
2. **越界记账**：ChangeSet 中出现 `declaredPaths` 之外的文件时标记 `out_of_scope`。

**`out_of_scope` 与 `attribution=ambiguous` 必须分开记录**：前者是「改动超出批准范围」，后者是「无法可靠判断改动归属」。明确知道 A 越界改了某文件时，归属未必不清楚；两者也可能同时发生。

**能力边界（必须如实表达）**：共享目录的前后快照可以判断文件内容是否变化，**不能**天然分清每个 Agent 的贡献、**不保证**保存被后续写入覆盖的每个中间版本、**不保证**得到双方可独立合并的改动集。A 完成时拍下的快照可能已混入 B 未完成的修改。要获得「冲突解决前不影响原项目」的前提，需要独立工作区（§14.4）或统一写入应用入口；本提案的原目录路径不具备该前提。

## 5. 整合闸门（integration gate）

把「并行写入」补成「并行写入 + 串行整合」——与 Git 的分支并行、合并串行同构。ChangeSet 在 §14.3 冻结之后、进入交付验收之前通过闸门：

```
frozen → gate_check → verified → (进入 §10.5 交付验收 / §14.6 提交)
              ↓ 未通过
        integration_blocked（保留现场，不覆盖任何文件）
```

### 5.1 两种模式分别定义

| 模式 | 闸门检查什么 | 通过意味着什么 |
|---|---|---|
| 原目录并行 | 已保存的目录版本、`out_of_scope` 与 `attribution=ambiguous` 项、验证结果 | 这个固定版本通过相应检查；**不表示此前没有发生覆盖**，也不表示当前目录此后未变化 |
| 独立工作区（§14.4） | 任务成果与最新整合基线形成的候选结果 | 该候选结果通过相应检查，可按既有授权策略进入下一步 |

主设计 §14.3 已明确：原目录模式下审阅检查的是已经发生的修改；worktree 模式下「应用到项目」才执行整合。两种模式界面文案必须区分。

### 5.2 闸门步骤

1. **基线漂移检查**：比对本 ChangeSet 的 before_ref 与当前项目最新已整合基线。无漂移 → 直接通过。
2. **重叠重扫**：对漂移涉及的文件，检查与已通过闸门的其他 ChangeSet 是否重叠。无重叠 → 通过并记录漂移说明。
3. **重叠处理**：有重叠且无三方解决标记 → `integration_blocked`，提供三方内容查看，由人工或指定成员产出解决版本（新 ChangeSet 版本；旧审查按 §14.3 不自动有效）。
4. **整合验证**：项目配置了验证命令时，对候选结果执行验证。验证失败 → `integration_blocked` + 证据记录。

### 5.3 规则

- 闸门是**串行点**：同一物理锁域（§3.3）内同时最多一个 ChangeSet 处于 gate_check，队列按冻结时间排序。串行的是检查与验证，不是整个开发任务——这是与悲观锁的本质区别。
- 「无基线漂移」「无文件重叠」只表示对应检查通过，**不能代替后续功能验证**。
- 证据绑定具体的基线、任务成果和整合结果版本；版本变化后不能沿用旧结果。
- 未运行验证命令时记录「未执行」，不得把 `verified` 表达成测试已通过。
- 应用前重新核对目标版本；其他写入者和外部编辑器造成的变化同样需要处理。
- 应用中途失败需要恢复规则；多文件应用不因被称为「短临界区」就成为原子操作。
- 不写「秒级完成」「毫秒级完成」等时间保证：项目测试与大规模改动可能远超该时间。
- 闸门不替代验收：通过后仍按 §10.5/§14.3 走交付验收，两个状态分别记录，不互相冒充（同 §14.6 对 commit 与 ChangeSet 的区分口径）。

## 6. 调度策略与跨任务变更请求

意图声明喂给调度器，规则按优先级：

1. `interface_change` 任务与声明了相同契约的任务**串行调度**：公共契约先落地，依赖方基于新基线启动。用排程消化语义冲突——文件锁解决不了这类问题。
2. 公共资源同样可能需要排队或隔离：共享测试数据库、数据库迁移、全项目格式化等，不限于接口变更。
3. 有先后依赖的两个任务修改同一文件是**合法的**：规则是「两个任务**可能同时运行**且写范围重叠时，才必须调整调度、重新划分范围或采用独立工作区」，不是「范围重叠一律拒绝」。
4. `declaredPaths` 高度重叠但无依赖的两个任务，界面提示建议串行，**不强制**。
5. 无重叠任务完全并行，无额外开销。

### 6.1 跨任务变更请求（评审补充）

范围划分解决不了「另一个 Agent 怎么知道我的需求」。需要轻量闭环：

```text
B 提出：页面需要接口增加 membershipLevel
    ↓
A 确认：接受 / 需要调整 / 当前无法提供
    ↓
协调者更新契约与任务依赖
    ↓
A 交付：对应成果版本 + 验证结果
    ↓
B 使用该版本完成联调
```

记录项：请求方与接收任务、需要改变的行为或契约、状态（待处理/已接受/需讨论/已完成）、完成后对应的成果版本。消息负责解释，状态负责让调度器判断依赖是否满足。「对方知道了」的依据是请求被接收和处理，不是把话发到频道里就默认对方已看见。

契约需结构化才能被程序检查（导入别名、封装函数、动态调用会让自然语言描述不可靠）：模型或代码分析提出依赖建议 → 确认后的结构化契约由程序检查成环与启动条件。拓扑排序只解决先后关系，不会自动让 B 的代码兼容新返回值，仍需适配任务与整体验证。

## 7. 失败与恢复

「不使用文件锁」消除了租约/续期/fencing 一类问题，但**不消除运行恢复问题**。原目录并行下必须处理：

- 崩溃时可能已改了一半的公共接口或多文件修改；
- 父进程退出后仍在运行的子进程（§16.3）；
- 调度器重启后需要识别哪些任务仍在运行（§16.4）；
- 原任务重试时不能与尚未退出的旧运行一起写（§11.4 运行代次）；
- 扩范围申请与正在执行的任务冲突。

规则：**记录失败现场，核对相关进程与受影响范围，暂停依赖该成果或受其影响的任务；可确认不受影响的任务继续。** 与 §16.3、RT-07「旧进程仍存活时不给新写者放行」保持一致。

## 8. 数据模型与界面增量

- 新增/扩展：`write_intent`（§3）；`ChangeSet.overlaps`、`ChangeSet.out_of_scope`、`ChangeSet.gate_status`、`ChangeSet.gate_evidence`。
- 界面：写入者名单区（§14.1 第 5 条）扩展为「写入者 + 意图 + 闸门状态」；ChangeSet 详情增加闸门结果、越界文件与重叠三方入口；`integration_blocked` 必须出现在任务 Activity，不得静默。
- 文案纪律：不出现「已隔离」「不会冲突」「绝不会覆盖」等超出能力边界的表述。

## 9. 验收要点（按 v1.1 边界重写）

1. 两任务并行改同一文件 → 不阻止写入；闸门发现重叠后冻者进入 `integration_blocked`，三方查看可用，ChangeSet 现场保留。（**不承诺「无任何文件被覆盖」**——原目录模式下该承诺不成立。）
2. 任务欠声明（改了未声明文件）→ 重叠扫描与 `out_of_scope` 均能发现并记账，过程无锁等待。
3. 接口变更任务与依赖任务 → 依赖任务在接口任务交付版本后才进入写入阶段；变更请求有接收与确认记录。
4. 有先后依赖的两任务改同一文件 → 不被「范围重叠」规则误拒；串行执行正常完成。
5. Agent 运行中途崩溃 → 失败现场与受影响范围被记录，依赖任务被暂停，旧进程确认停止后才允许新写入者接手（RT-07）。
6. 外部编辑器并发改动 → 快照标注 ambiguous，闸门按重叠处理，界面不出现「已隔离/不会冲突」字样。
