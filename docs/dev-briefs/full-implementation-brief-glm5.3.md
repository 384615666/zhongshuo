## 2. 完整范围与完成口径

### 2.1 总体产品目标

众说是以真实本地项目文件夹为工作对象、以项目/房间/对话为协作入口的多 Agent 工作台。正式软件必须把现有界面连接到真实数据、真实文件、真实 runtime 和可恢复的执行体系。

至少覆盖以下能力域，具体行为逐项对照主设计和 137 项表，不能用本节摘要替代全文：

- 本地项目、多项目导航、目录身份/重定位、房间与成员管理、归档/恢复和设置。
- 消息、原消息锚定的线程、结构化提及、默认与 AI 交流、一次性仅记录、未读、关注、搜索、收藏和待我处理。
- DIRECT 指定成员、DELIBERATE 独立分析/互评/分歧/整合、AUTO 计划/子任务/交接/执行。
- Codex 与 Claude Code 的真实接入、能力检测、权限与确认通道、预算/并发、停止、故障诊断和恢复；更多 runtime 按 FULL-04 扩展。
- 项目内普通一对一私信及独立上下文、提醒、通知、成员生命周期。
- 原目录默认单写者、前后基线、用户未提交内容保护、ChangeSet、Git 操作、审查版本和非破坏撤销。
- 项目级可选任务验收，关闭时不强迫人工验收；Git 提交与任务验收保持独立。
- 文件/附件、共享预览、版本与来源、引用到草稿、评论、导出，以及格式能力的真实识别。
- Windows 桌面安装、托盘、重启、迁移、卸载保留数据；本机/LAN 浏览器及设备配对。
- FULL 的多人/多机、外部 Agent、应用集成、事件、Service CLI、联合频道、账号数据与商业入口等完整范围。
- MCP 外部助手接入：真实工具、连接授权、查询、任务提交/跟进/停止、审计与适配。

### 2.2 三类状态必须分开

| 状态 | 含义 | 可否记为功能完成 |
|---|---|---|
| 设计已定 | 规格/原型/接口方案已有 | 否，仍需实施 |
| 已实现但未验收 | 代码已写，真实行为或所需环境尚未验证 | 否，只能报告已实现/待验证 |
| 已实现并验收 | 对应环境下通过适用的正反用例并有证据 | 可以，仅限已覆盖范围 |

UI 有入口、函数返回成功、TypeScript 通过、进程 exit 0、fake adapter 返回内容、模型自己说“完成”，均不能单独证明全功能已完成。

### 2.3 完整目标的特殊边界

- **MCP 本体 FULL-11 在 v0.1 之后，仍属于本次全功能总目标**。DEV-01 起落实预留，不能做到首版便把 MCP 永久留成设置页假入口。
- FULL-01—04 中首版已做的子集继续复用；FULL 阶段补齐完整范围，不重复实现另一套系统。
- DEV-20 完整权限加固属于后续实施范围，按该包的能力和平台逐项验证。首版原生限制/确认通道不能因此后置，也不能将有限测试夸大为任意 CLI 都无法绕过的系统隔离。
- 多 Agent 并行写入增强、按任务 worktree、写意图与整合闸门等，沿 §14.7 保留“已延期、未批准施工”。当前先单写者；不得为扩大施工并行度擅自开启产品并行写入。

### 3.2 正式工程结构

采用已经确定的 **pnpm、单仓单包、TypeScript strict、六边界目录**。根 `package.json` 与原型自己的依赖分开，不擅自改为多包 workspace。

```text
D:\zhongshuo\
  package.json / pnpm-lock.yaml / tsconfig*.json
  src/
    contracts/      公共 DTO、schema、命令/事件与 adapter 接口
    domain/         纯业务状态机、路由、权限范围、预算与协作规则
    persistence/    SQLite、迁移、事务、仓储、回执与 outbox
    adapter/        runtime/fake、进程、会话、规范化事件
    daemon/         组装、IPC、调度、目录锁、基线、恢复、zs 入口
    ui/            Electron main/preload 与正式 React renderer
  tests/
    fixtures/ / integration/ / e2e/
  docs/
  hifi-prototype/   已确认交互参照，保留其独立工程
```

contracts 不依赖其他内部模块；domain 只依赖 contracts。UI 不直接读写 SQLite 或拉起模型 CLI，adapter 的厂商类型不渗入 domain；daemon 统一组装。MCP/桌面/CLI 共用业务命令，不复制第二套执行循环。

### 3.3 可修改和应保留的内容

- 可创建和修改正式根工程、`src/`、必要测试/fixture、迁移、打包配置、依赖锁文件与工程文档。
- 可以把原型中成熟的组件/样式复制适配到正式 `src/ui`，保留已确认体验；逐页移除对种子 store 的依赖。
- `hifi-prototype/` 保留为参照，避免一边施工一边重画。确需修复与正式接入直接相关的共享问题时，单独说明原因与影响，不进行无关视觉改造。
- 不删除或搬移用户资料，不清理未知未跟踪文件，不修改全局 CLI 配置，不把用户凭据/真实会话数据放进仓库。
- 文件修改、停止进程、Git 和安装/迁移的破坏性用例在专用 fixture、临时目录和测试实例中执行，不能对用户真实业务目录试验。
- 外链/应用消息/真实远端推送/真实支付等外部动作按对应授权处理；不要用真实用户数据代替 fixture。

本次全功能施工默认使用 `codex/full-implementation`，各工作包在同一施工分支按包形成检查点提交，不要求每包新建分支。本条取代基线 §1 的 `codex/<work-package>` 与单独执行 DEV-01 时的 `codex/dev-01` 默认名称；用户指定或已有合适施工分支时沿用，不为命名另行迁移。完成包后可做本次授权范围内的本地检查点提交，明确选择本包文件，不全量打包其他会话改动。不得改写历史、强推或自动合并主分支；远端推送与发布按既有用户授权执行。

| 界面 | 沿当前原型，不重做导航/设置/视觉；仅实际执行中旋转；未读与任务状态独立；不将施工编号塞进产品交互 |

## 6. 核心产品 M0—M3 的施工顺序

## 8. 施工验证与完成标准

本节是施工 AI 的职责，不要求编写本任务书的会话执行。

**操作手册也是交付内容。** 涉及用户功能、按钮入口、交互或操作结果的改动，须同步维护 `docs/user-guide/README.md` 中对应操作、适用版本、日期和使用中的相关截图。`pnpm build:ui` 从同一源码生成设置内的完整手册与离线HTML，桌面打包附带离线版；交付前检查“设置 → 操作手册”可阅读且内容与版本一致。工程验收报告不代替操作手册。 用户手册面向所有用户，以通用示例、带编号的截图、短步骤和操作结果讲清楚用法；个人路径、专用启动器与本机升级安排写入单独交付说明。界面变化同步更新对应截图和编号。

### 8.1 验证分层

验收闸门沿开工契约 §9，完整映射如下。编号表示能力闸门，不取代每包独立完成定义。

| 闸门 | 承载与时点 | 必须证明的内容 |
|---|---|---|
| G0 契约 | DEV-01 | schema、路由、目标/主体/范围与预算纯校验；无真实模型调用 |
| G1 存储和进程 | DEV-02—05/17；真实用户闭环前 | 事务/回执/outbox、重启记录、进程身份与目标/事件隔离 |
| G2 原生权限 | DEV-06/10；对应 runtime 档位开放前 | 固定版本与真实适配路径中的限制、允许/拒绝、续接及故障不降级；第二 runtime 另行认证 |
| G3 M0 真实闭环 | DEV-07/17/21-M0，依 G0/G1 及所用 runtime 的 G2 | 真实目录→指定成员→正确回复→停止→重启保留记录；双任务不串线 |
| G4 协作 | DEV-08—11/21，按 M1/M2 分段 | FOLLOW/LATE/E11 的允许与拒绝路径、研讨/自动分工；M1 价值闸门结论不得被技术测试替代 |
| G5 发布 | DEV-16，依首版全部实施包及适用 G0—G4 | 集成验收、安装/恢复/兼容/性能与限制；G5 是本包产出，不作为 DEV-16 的循环前置 |

各层具体执行要求：

- contracts/domain：有效/无效输入、作用域、状态转换、重复请求、旧代次、边界预算与真实允许路径；不能只测拒绝路径就声称功能可用。
- persistence/daemon：真实 SQLite 事务/迁移、进程与 outbox、提交后丢响应、崩溃重启、并发占用和恢复。
- runtime：实际版本、适配路径、输入/续接/停止、直接编辑与 shell 写入、确认允许/拒绝和失败不降级。Codex 使用实际 App Server 路径，不能拿其他入口实测替代。
- UI：正式工程中的实际点击、真实命令结果、切换上下文、窄窗口、中文输入、草稿/附件、错误状态和截图；浏览器与 Electron 宿主能力分别验收。
- 文件/Git：真实临时仓库/非 Git fixture、未提交内容、路径重叠、前像/撤销与失败；不能把内存 diff 当磁盘操作证据。
- 外部集成：认证、范围、过期/撤销、幂等、断连、签名/重放和真实兼容客户端；测试环境/生产环境结果分开。
- 安装发布：安装、首次启动、退出/重启、升级迁移、卸载保留数据、缺依赖机器及适用平台。

按 AT/RT/TH/PP/WPV、DM-BASE/MCP-BASE/FOLLOW/LATE/E11/LAN 和 ALL 对照表维护验收；一个场景可提供多项证据，但不能互相替代未覆盖的断言。先跑本包必要检查，再在阶段边界做集成回归；无改动/无新疑点时不重复刷全套数值。

### 8.2 单包可以标“完成”的条件

1. 对应范围已有可运行代码，不是空实现、TODO、假成功回执或只显示占位界面。
2. 正常流程与关键失败/恢复路径满足合同，必要正反用例已实际执行。
3. 接口/schema、数据库迁移、配置/启动说明与代码一致。
4. 证据包含环境、执行命令、退出码/结果、实际文件或记录，以及未覆盖的限制。
5. 所属功能在进度表中有明确映射；已知缺陷、下游未接入和阻塞不被删除。
6. 对需要人工业务判断或真实外部环境的部分，取得对应结果后才能将整个依赖项标完成。

### 8.3 整个全功能工程可以标“完成”的条件

首版和 FULL 工作包在批准范围内全部收敛；137 项及额外众说需求逐项有可追溯实施/验收；真实单成员、研讨、自动分工、修改审查、私信、恢复、LAN/MCP/应用等适用场景跑通；Windows 安装交付和文档齐全；所有“尚待账号/决策/环境”的项有真实结论。

存在受阻的必需项时，只能交付“已完成部分 + 未完成清单”，不能称全功能完成。用户明确延期的并行增强单独列“授权范围外的延期项”，不偷偷实现，也不混成已经完成。
