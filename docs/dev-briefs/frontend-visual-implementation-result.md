## 0. 用户实测反馈的三处缺陷（第二轮，已修复）

三条都不是"感觉不对"，而是可复现、可量化的缺陷。修复前的证据与修复方式如下。

### 0.1 输入栏消失 —— `.workspace` 的 `flex-wrap: wrap` 把内容撑出视口

| | 修复前 | 修复后 |
|---|---|---|
| `.workspace` `flex-wrap` | `wrap` | `nowrap` |
| 内容列高度 | **1618px**（视口仅 872px） | **834px**（= 视口高） |
| 回复串输入条 `top` | **1554**（视口外） | **769**（可见） |
| 输入条 `inView` | 否 | 是 |

**成因**：为了让「单区域切换器」独占一行而给 `.workspace` 加了 `flex-wrap: wrap`。
一旦子项宽度之和超出容器，flex 会换行，而**换行后的行高按内容自然高度计算** ——
两个内容列因此长到 1618px，输入条被推到 `top=1554`，用户看到的就是"输入栏不见了"。

**修复**：`.workspace` 改 `nowrap` + `min-height: 0`（后者约束 flex 项不被内容撑开）；
单区域切换器改用 `flex-direction: column` 独占一行，不再依赖 `wrap`。

### 0.2 回复串底色发灰、气泡看不出层级

| | 修复前 | 修复后 |
|---|---|---|
| `.col-thread` 底色 | `--bg-surface-2` = `rgb(247,250,252)` 灰 | `--bg-surface` = `rgb(255,255,255)` 白（与主池一致） |
| `.msg-body` 底色 | 无（透明） | agent = `rgb(247,250,252)`；人类 = `rgb(232,239,253)` 浅蓝 |
| 层级表达 | 整列铺灰 + 消息无底 → **完全看不出层级**，两栏之间形成"灰色夹层" | 两栏同为白，层级由**气泡自身**表达 |

**成因**：原设计想用"回复串比主池低半档"分栏，但**消息本身没有底色**，
于是灰色只起到底噪作用 —— 既没做出层级，又违反规范 §4.1「禁止灰色夹层」。

**修复**：`.col-thread` 改白底，分栏交给 1px `--border-subtle` 竖线；
`.msg-body` 加气泡（圆角 + 内边距），人类消息用 `--accent-soft`、
agent 用 `--bg-surface-2`；系统消息不套气泡（它不是"某人说的话"）。
`MessageView.tsx` 相应加 `is-human` 类。

按 **kimi-clean-layout-reference.png 的发送按钮实测**（在按钮顶行/底行避开文字取样）：

| 位置 | 实测值 |

### 0.4 顺带查出并修掉的两处窄窗缺陷

在复验 §0.1—0.3 时，用 1100/900px 实拍又发现两处**此前未被任何断言覆盖**的缺陷：

**（a）900px 下线程面板被渲染两次。**

`RoomPage` 有两处渲染 `ThreadPanel`：「窄窗覆盖式」分支与「桌面双栏」分支。
900px 时两个条件**同时成立** → `col-thread` × 2、输入条 × 3、页签组 × 3，
用户看到的是"回复串被复制了一份"（并排两个半宽面板）。

修复：给窄窗分支加上 `!showThreadRegion`，让两个分支**显式互斥**。

**（b）1100px 下线程只占一半宽度，右侧留 420px 空洞。**

`.col-thread.narrow` 仍带着为"与主池并排"设计的 `max-width: calc(100% - 420px)`。
窄窗下主池是 `display: none`，这 420px 就成了右侧空白 ——
实测 1100px 时线程仅 **434px**、右侧空 **420px**。

修复：`.col-thread.narrow` 增加 `max-width: none`。修复后线程 **854px**、空洞 **0**。

> 这两处的价值说明：它们**不是**本次视觉改造引入的，而是既有实现里一直存在的
> 窄窗缺陷 —— 但只有真正按规范要求的采样点（1100/900px）**实拍**才会暴露。
> 若只对着 1372px 出图，它们会继续藏着。

### 0.7 第四轮反馈：按钮"占位却完全看不见"（已定位并修复）

用户继续反馈："**没选中和选中的时候，颜色和我给你的截图完全不一样，
选中后直接全白什么都看不见了**"，并附了两张截图。

**第一步：量用户截图，而不是猜。**
把两张截图逐像素读出来：

| 截图 | 内容 | 结论 |
|---|---|---|
| 图1（83×37） | 发送按钮 + 绿色勾 | 按钮**有**蓝→青渐变，正常 |
| 图2（391×170） | 输入区右下 + 蓝色聚焦环 + 绿勾 | **发送按钮的位置被占着，却是纯白** |

图2 的关键证据：工具条一行里，「计划模式」芯片结束在 x≈265，
绿色勾在 x≈355，**中间约 90px 是空白** —— 正好是一颗发送按钮的宽度。
逐行扫描确认那片区域除边框外**没有任何非白像素**：
按钮不是"淡"，而是**彻底看不见**。

**根因（可复现的 CSS 陷阱）**：
`.btn.primary` 原先写的是简写 `background: var(--grad)`。
`background` 简写里只要有一个值解析失败，**整条声明会被丢弃** ——
于是回落到 `.btn` 的 `background: var(--bg-surface)`（**纯白**），
而 `color: #fff` 依然生效 → **白底白字的隐形按钮**。
它仍然占位（所以那 90px 空着），只是完全看不见。

同一类问题还影响：
- `.brand-mark`（品牌方块）
- `.new-msg-pill`（"有新回复"胶囊）
- **11 处选中态** `background: var(--grad-soft), var(--bg-surface)` ——
  一旦 `--grad-soft` 失效，连同垫底的 `--bg-surface` **一起**被丢弃，
  选中项退化成"没有任何底色"，看起来与未选中一模一样。

**修复：把简写拆成"实色打底 + 渐变叠图"两条独立声明。**

```css
/* 修前：一条简写，全有或全无 */
background: var(--grad);
background: var(--grad-soft), var(--bg-surface);

/* 修后：底色与渐变各自独立，渐变失效也不丢底色 */
background-color: var(--accent);
background-image: var(--grad);
background-color: var(--bg-surface);
background-image: var(--grad-soft);
```

涉及：`base.css`（品牌方块、主按钮、3 处选中态）、
`components.css`（6 处选中态 + 新回复胶囊）、`preview.css`（2 处选中态）。
构建产物已确认：`background:var(--grad)` 简写残留 **0** 处。

**验证**：`scripts/prove-fallback.mjs` 故意让 `--grad` 失效后，
按钮仍是实色 `rgb(37,99,235)`，白字对比度 **5.17:1** —— 不可能再隐形。
`verify-visual.mjs` 新增 2 条回归锁：
**主按钮有非白兜底实色** · **选中态有可见底色且与未选中不同**。

> 顺带说明：这类"简写被整条丢弃"的问题在 CSS 里很隐蔽 ——
> 它不会报错、不会警告，只是让元素静默消失。改成显式分层后，
> 自定义属性无论哪一层出问题，都不会再让元素变成隐形。

### ② 附件页只显示半个 —— 根因是线程绝对定位盖住了预览

这条最难查。**用户报的路径在 1372/1440/1920 都复现不出来**，一度以为不是缺陷。
改用"是否被裁"这个硬指标（`scrollWidth - clientWidth`）逐宽度扫描后，
定位到 **1280px 整点**：

```
col-thread   x=666  w=614  right=1280  position: absolute  ← 覆盖式面板
preview-pane x=246  w=579  right=825   position: static
```

两者**重叠 159px** —— 线程整块压住预览的右半部分，用户看到的就是"半个附件页"。

**根因**：断点判定不一致。

| | 判定 | 1280px 的结果 |
|---|---|---|
| CSS | `@media (max-width: 1280px)` | **命中**（≤1280） |
| JS | `useNarrow()` = `innerWidth < 1280` | **不命中**（不小于） |

于是 1280px 整点上：JS 认为"不是窄窗"→ 线程不带 `.narrow`；
CSS 认为"是窄窗"→ 命中 `.col-thread:not(.narrow)`，被改成
`position: absolute; z-index: 30`。而预览区仍在文档流里 → 被盖住。

**修复**：给覆盖式样式加布局互斥 —— 双区时线程必须留在文档流：

```css
.workspace:not([data-layout='context-preview']) .col-thread:not(.narrow) {
  position: absolute; /* 覆盖式面板只用于"无预览、线程接管房间" */
}
```

### ③ 开关附件时宽度跳变 —— 去掉记忆，改用当前宽度

**原来的问题**：两侧都写死成解析值（`flex: 0 0 contextWidth` +
`flex: 0 0 previewWidth`），打开附件的一瞬间回复串从 **620px 跳到 517px**，
关闭又跳回来；宽度还存在 `localStorage`（`zs.threadWidth`），
跨窗口尺寸读回时跳得更狠。更糟的是两侧都不可收缩，
解析值之和一旦超过容器就**溢出被裁**（即缺陷②的另一半）。

**修复**：
- **不再记忆**：删掉 `zs.threadWidth` 的读写，宽度只留在本次会话内；
- 对话侧（回复串）**保持它此刻的宽度**，`flex: 0 1` 允许空间不足时收缩；
- 预览侧 `flex: 1 1 0%`（basis 归零）**只吃剩余空间**，保底 480px。

> 预览侧为什么用 `0%` 而不是 `auto`：`auto` 的基准是"内容自然宽度"，
> 会和对话侧一起参与收缩分摊，回复串仍被挤掉一点（实测 620 → 578）；
> 归零后才真的"只吃剩余"。

实测：打开附件前后回复串 **620px → 620px**。

### ④ 打开/关闭缺少过渡动画 —— 部分完成

**已做**：`flex-basis` / `width` / `opacity` 走 0.18s 过渡；
`.col-thread` 与 `.preview-pane` 挂载时淡入（`zs-pane-in`）；
并在 `prefers-reduced-motion: reduce` 下全部关闭（无障碍正确行为）。

**验证坑**：CDP 驱动的 Chrome **默认上报 `prefers-reduced-motion: reduce`**，
于是降级规则生效，测出来"没有动画"。必须显式 `Emulation.setEmulatedMedia`
设为 `no-preference` 才测得到 —— 这不是缺陷。

**未做**：**收起时的退场动画**。面板是条件渲染（`hasPreview` 为假即卸载），
要让关闭也动起来需要"先播完再卸载"或"常驻 + 折叠"的结构改动；
而"先播完再卸载"在 React 里会**卸载→重挂→再卸载**闪烁
（render 阶段拿不到 closing 标志），收益不抵风险，本轮未做。

### 0.11 第六轮：②③④ 的返工（我上一轮理解错了）

#### ② 上一轮的修复引出了新症状：切回后只剩附件

上一轮我给覆盖式样式加了布局互斥（对的部分），但同时把预览宽度写成
`flex: 1 1 0%` —— 预览会**吃掉全部剩余空间**，用户看到的就是
"附件占满整页、对话区像消失了"。

**真正的修复**（见 ③）：两列宽度改成"对调"后，预览只拿回复串原本的宽度，
不再无限膨胀。

同时收紧了一处逻辑缺陷：`showMainPool` / `showThreadRegion` 原是**两个独立条件**，
在 `previewFromDm` 为真时**同时成立**（会渲染主池 + 回复串 + 预览**三个区**），
在别的组合下又可能同时为假。现在统一由 `previewSide`（`'thread' | 'pool'`）派生，
天然互斥且必有一侧：

```ts
const previewSide = hasPreview ? (previewFromThread ? 'thread' : 'pool') : null;
const showMainPool   = showContextRegion && previewSide !== 'thread';
const showThreadRegion = Boolean(threadId) && showContextRegion && previewSide !== 'pool';
```

#### ③ 我理解错了：不是"宽度不变"，而是**左右两列宽度对调**

用户澄清："打开附件后，回复串变到左边，用的原来左边对话池的宽度；
右边变成附件后，附件使用的是原来回复串的宽度。"

即：打开附件时把左右两列的宽度**原样换位**，而不是重新分配。

```ts
const rightColW = …threadWidth.width…;                     // 右列 = 回复串当前宽
const leftColW  = navVisibleWidth - rightColW - SPLIT_W;   // 左列 = 剩余（原主池宽）
```

实测（`scripts/repro-only-preview.mjs`，干净序列）：

| 视口 | 打开前 主池 / 回复串 | 打开后 回复串 / 附件 |
|---|---|---|
| 1440 | 574 / 620 | **566 / 620** |
| 1600 | 734 / 620 | **726 / 620** |
| 2048 | 1182 / 620 | **1174 / 620** |

> 两个易错点，都实测踩过：
> 1) 基准必须用 `navVisibleWidth`（= app-body − 246 侧栏），
>    误用 `workspace.width`（整个 app-body）会让两列基准之和超出容器，
>    flex 只能按比例收缩，"对调"变成"各缩一点"（实测 677/517）；
> 2) 双区里不能再给回复串传 inline `width`（620px 会和 flex-basis 打架）。
>
> 已知残差：容器很紧时（1440 及以下），回复串内部内容最小宽度 597px
> 会顶住 flex-basis 566px，此时实测是 597/597 而不是 566/620。
> 宽屏（≥1600）不受影响。

另外顺手修了**分隔条拖拽方向**：L4 里分隔条在回复串**左缘**，
方向与 L2 相反，原实现会出现"往右拖反而变宽"。

#### ④ "完全没感受到" —— 找到原因了，但结论是**这版做不了**

先查出两个硬事实（`scripts/probe-anim-env.mjs`）：

1. **`to { flex-basis: var(--preview-w) }` 里的 var 不被关键帧采纳** ——
   动画停在起始帧，预览列被压成 **1px**（实测 `previewW=1`）。
2. 更关键：页面处于 `visibilityState: hidden` 时（后台窗口、CDP 驱动），
   **CSS 动画完全不推进**（实测 720ms 后仍是 0px），**`setTimeout` 也被冻结**
   （实测 2.5s 内 `.entered` 类始终加不上）。而**过渡会正常推进**
   （实测过渡 700ms 后已到终值）。

我试了两种入场写法，都因此**永久停在起始帧**：一种让预览列塌成 1px，
一种让面板 `opacity` 恒为 0（整块隐形）。**两者都已回退** ——
不可靠的入场动画比没有动画更糟。

**本轮实际交付**：`flex-basis` / `width` 的**过渡**（可靠、可验证）；
打开附件时两列宽度对调的那 54px 变化会平滑移动。
**未交付**：面板自身的展开/收起动画 —— 它需要"元素保持挂载、
只让 `--preview-w` 在 0 与真值之间切换"的**结构改动**，
这样过渡才有起点，且不会因定时器被冻结而停在隐形帧。
`verify-four-fixes.mjs` 里已加一条锁：**附件面板 opacity 必须为 1**，
防止将来有人再把"入场动画失败"变成"面板隐形"。

## 4. 施工中发现并修复的真实缺陷

**四条**不是"换肤本身"，而是**规范要求的能力此前并未兑现**，实测才暴露：
### 4.1 输入框没有自动增高（§5.6 要求"增长到 200px 上限"）

`Composer.tsx` 只有 CSS `height:54px; max-height:200px`，**没有任何 JS 增高逻辑** ——
`max-height` 永远触不到，输入超过两行就在 54px 里滚动。
实测：2 行 `scrollHeight=55`、5 行仍 55、10 行 `scrollHeight=227` 而 `clientHeight=54`。
**已补 auto-grow effect**（先置 `auto` 读 `scrollHeight` 再钳到 [54,200]），
现测：2 行→55px、5 行→119px、10 行→**200px 且内部滚动**。

### 4.2 容器宽度测量会冻结（影响全部宽窄适配）

`useElementWidth` 在 effect 开头就 `const el = ...; if (!el) return;`，
而依赖只有 `[selector]` —— 若首次执行时目标尚未挂载，**永远不会重试**，
宽度永久冻结在 `useState` 初值。
实测：900px 窗口下布局仍按 ~1426px 计算，预览宽 661px **溢出容器 654px**，
自动隐藏侧栏与单区域切换都不触发。
**已改为每次测量重新解析 + rAF 重试 + 观察者补挂**，真实 Electron 窗口下每档都正确。

### 4.3 消息正文与元信息不符合可读性要求（§3.1/§5.3）

- `.msg-text` 原为 13px/1.72、**无限宽** → 大屏实测 1432px 通栏长行。已改 15px/1.65/**76ch**。
- `.msg-time` 用 `--text-4`（对比度 3.47:1 不达 AA），而规范规定 `--text-4` 只给装饰与禁用控件。已改 `--text-3`/12px。
- 任务标题原 13px（规范要求 14px/650），任务号原为 accent 胶囊（规范要求 mono `--text-3` 无容器）。均已改。

### 4.4 深色主题下亮渐变配白字不达标（规范 §2.8）

深色 `--grad` 是**亮**渐变（`#60a5fa→#6ee7b7`），而 `.brand-mark` 与 `.new-msg-pill`
仍写死 `color:#fff` —— 对比度仅 1.86:1，属规范明令禁止的组合。
已为二者补 `:root[data-theme='dark']` 深字（`--text-inverse`，实际渲染色 `rgb(13,17,23)`）。
主按钮在第五轮改为浅渐变族后，深色主按钮为深色 `--grad-soft` + 亮蓝字 `#93c5fd`（§0.9a）。

### 4.5 验证夹具自身的两个坑（记录以免重犯）

- **`Emulation.setDeviceMetricsOverride` 不保证触发 `ResizeObserver`**：
  容器 rect 已变但观察者回调不来，布局输出冻结。
  实测证据：同一套用例在浏览器里 900px 误判为两区，而真实 Electron 窗口（Win32 调窗）每档正确。
  已在夹具里显式 `dispatchEvent(new Event('resize'))`，并**不因此放宽任何断言**。
- **L2 下有两个输入条**：早期用 `document.querySelector('.composer-input')` 取到的是**主池**那个，
  把"读到另一个输入框"误报成"草稿串线"。已改为按 `.col-main` / `.col-thread` 限定作用域。
  草稿隔离本身**一直是正确的**（4 项断言现全通过）。
