# 原型交接：任务验收可选，Git 流程独立

2026-09-20 第十四批决定，对应[主设计 v1.12](../zhongshuo-development-design-v1.md) §10.5、§14.6、§17、RT-24/25。用户已确认功能方向；下面的新项目默认值、版本绑定和切换边界为本次实现规则。修改对象是 `hifi-prototype/` 的交互与 mock 状态，不在本包接真实 Git、runtime 或文件写入。

后续导航覆盖（第十五批，v1.13）：按[侧栏与多项目交接](./prototype-sidebar-project-navigation.md)将文件/Git 合为两个页内标签、看板按项目分组、Runtime 收入设置；本文件的验收状态与去重规则继续有效，下面的旧页面名称理解为合页中的对应区域。

## 1. 这次要解决什么

熟悉 Git 的用户应能继续“看 diff → 暂存 → commit → push”，不需要学习或使用众说的验收流程。希望人工确认 AI 交付的人可开启“任务验收”。4 个 Agent 修改 20 个文件、产生 8 次提交，最终同一次用户任务交付只出现 1 条验收待办。

不要将关闭验收解释成自动同意权限、自动提交/推送、测试通过或任何结果都成功。文件、差异、任务来源和验证记录两种模式下都保留。

## 2. 项目设置

第十六批入口更新：本节开关位于“项目行 ⋯ → 项目设置”的独立项目页，路由 `/project/:projectId/settings`；从应用设置移除，表单与兼容细节见[设置分离方案](./prototype-settings-separation.md)。验收行为保持不变。

新增开关：**任务验收**。

说明：**开启后，任务交付需要你确认；关闭后，满足交付要求即完成。不会自动提交或推送 Git。**

- 新项目默认关闭；与是否 Git 仓库无关。
- 旧项目有明确设置时保留；缺字段且沿用旧“代码人工审阅”的项目迁移为开启，标注“沿用旧项目的人工验收设置”。已有任务继续使用原 reviewPolicy，包括原本自动交付的报告任务；不能静默通过旧任务，也不能给旧报告补造审批。
- 保存设置提示：“仅影响新任务，已有任务保持原规则。”不要因关掉开关删除旧的待验收卡；若存在旧任务，加一句“还有 N 个已有任务按原规则等待验收”。
- 这是项目设置，不放进成员权限下拉，不另造全局同名开关。

## 3. 两条任务路径

| 情况 | AI 满足交付要求后 | 用户看到 | 验收待办 |
|---|---|---|---|
| 关闭 | Task DONE，reviewStatus=not_required | 已完成 · 无需验收；可查看成果/diff/验证 | 无 |
| 开启 | Task REVIEW，reviewStatus=pending | 待验收；可查看交付详情 | 每个用户任务的当前交付 1 条 |
| 未满足交付要求 | 按实际失败/阻塞状态 | 错误、缺失内容和下一步 | 不伪造“待验收成功交付” |

进入交付详情后：

- **验收通过**：针对当前交付版本确认，Task DONE、reviewStatus=accepted，写入通过人/时间/版本，移除该待办。
- **要求修改**：先收集必填意见，再记录 changes_requested、关闭本轮待办、任务回 ACTIVE。正常调度仍核对预算和权限；原型可用明确模拟按钮演示返工，不声称真实调用。
- 返工发布新版本：revision 增加，出现同一任务的一条新待验收交付，旧版及意见可查看。旧页面按钮不能批准新版；提示“交付版本已更新，请重新查看”。
- 通过不执行写文件、暂存、commit 或 push；要求修改不 reset、不撤销 commit、不删除成果。原目录已写入时注明“修改已在项目中，验收仅确认交付结果”。
- “无需验收”与“人工已验收”是不同状态，不互相冒充。

## 4. 页面与入口改动

| 位置 | 修改要求 |
|---|---|
| 项目设置 | 增加开关和仅影响新任务的说明 |
| 任务详情 | 展示任务创建时的验收策略；提供当前交付版本摘要与唯一验收详情；关闭时没有验收按钮 |
| 线程成果卡 | 显示成果摘要、当前状态和“查看交付”；跳到同一交付详情，不生成第二条审批 |
| 文件与改动 | 保留文件浏览、diff、归因；移除“验收单个改动集就把任务标 DONE”的行为，改为查看所属交付；无需启用验收也能使用 |
| Git | 保留常规暂存/commit/push/历史/分支/远端/冲突；移除“验收这个提交”和 commit 专属待审阅队列，不依赖任务 REVIEW 状态禁用操作 |
| 待我处理 | 只为当前 pending 用户任务交付生成一条卡，深链携带 taskId、deliveryId、revision；权限请求和阻塞项继续独立存在 |
| 侧栏角标 | 验收数量按当前交付去重，不能把同一交付的文件、ChangeSet、commit 各算一次；Git 可保留工作区改动数，但明确它不是审批数 |

验收详情的信息顺序：**任务目标 → 完成摘要 → 可用效果预览 → 实际验证与未验证原因 → 残余问题 → 文件清单与完整 diff**。原型用 mock 数据时标明模拟，不填“真实测试通过”。不提供跨任务“全部验收通过”。

验收行为与导航重构分开实现：第十五批已明确文件/Git 两标签合页，路由迁移以新交接说明为准，旧路由保留兼容跳转；不采用三标签方案。共用 diff 组件与同一交付数据，任务来源摘要可多处展示，但决定与待办只有一份。

## 5. Git 用户的路径

- 默认仍可看全部工作区改动、按文件/代码块操作。按任务或改动集筛选/暂存是便利入口，不是必须先走的步骤。
- 按任务批量暂存仍跳过用户原有改动；归因不明时不能假装只包含 AI 的修改。不要因取消验收流程删除这条保护。
- 不再使用 git.reviewCommit 作为交付验收入口，也不要把“退回”实现成软回退；用户需要撤销提交时走原有明确的 Git 撤销操作。
- 可显示“关联交付待验收/已验收/无需验收”，但不能只凭 taskId 关联就给整个 commit 打“已审阅”勾。新增或混合修改不自动继承验收。
- 用户主动 commit/push 不受任务验收开关限制；原生权限、凭据、冲突和目标检查仍在。任务完成或验收通过不会自动触发 Git。
- 非 Git 项目仍能查看文件和任务交付、使用可选验收；Git 页面继续说明不是仓库，不自动 git init。

## 6. 给实现者的数据约束

- Project：`taskReviewEnabled`；新建用户任务将其快照成 `reviewPolicy='auto_deliver'|'user_review'`，不再通过 access=modify 自动推导人工验收。
- Task：`currentDeliveryId`。子任务执行不单独制造用户审批；显式另起的用户任务独立处理。
- TaskDelivery：`id/taskId/runId/revision/manifestHash/artifactRefs/changeSetRefs/verificationRefs/reviewStatus/reviewedBy/reviewedAt/reviewNote`。只允许一个当前 pending 版本。
- ChangeSet：用 `applicationStatus` 表示 applied/not_applied/reverted/partial；验收状态来自 TaskDelivery。旧 status=pending_review 不能直接换成 not_applied，因为原目录可能已写入。
- 所有决定通过共享 store/action 更新，并验证当前 pending 的 ID、revision 与 manifestHash；重复点击幂等。不要让四个页面分别更新本地 state。
- 页面刷新仍沿用现有 mock 持久化边界，不在本包声称已实现数据库。新字段的缺省与 seed 迁移要明确，不把刷新后的假状态当功能完成。

建议检查文件（按实际目录核对）：`src/data/types.ts`、`actions.ts`、`actions-git.ts`、项目设置所在页面、`pages-task.tsx`、`Room.tsx`、`pages-misc.tsx`、`GitPage.tsx`、`App.tsx` 与现有验证脚本。原权限与 Git 原有能力不因本次改动被移除。

## 7. 原型验收清单

1. 开关关闭时新任务成功 → 已完成且无验收卡；失败 → 仍失败/阻塞。文件和 Git 能继续使用。
2. 开关开启时新任务成功 → 一条待验收卡；多个 Agent、文件、子成果、commit 不增加重复卡。
3. 开启下验收通过 → 任务完成；未发生任何 Git/文件操作，审批请求也没有自动获准。
4. 要求修改必须有意见；旧内容保留，返工新版本仍只有一条当前待办。
5. 等待验收期间关闭项目开关 → 老卡保留，新任务无需验收；重新开启不为过去已完成任务补造审批。
6. 旧版本操作与重复点击不错误批准新结果。任务详情/线程/待办/文件的状态一致。
7. Git 页没有“验收这个提交”按钮或 commit 专属审批；合法 commit/push 在开关两种状态下都可操作，权限和冲突限制仍生效。
8. 非 Git 项目两种开关路径可演示；关闭不初始化仓库，不要求先配置 Git。
9. DELIBERATE 的 RATIFY、执行前原生审批和代码内部审查均未因任务验收关闭而消失。
10. 跑现有 build 与相关交互回归；报告真实执行的检查、修改的文件及尚未实现的能力。模拟验证不能写成真实 runtime/Git 验证通过。
