# 03 · 对比与决策

> 你的目标：**完整替代现在用 Raft 的全部用法**，需要本地客户端形态。
> 两条路线共用同一份领域模型（`00-shared-spec.md`），所以差异**只在实现技术**。

---

## 1. 一页对比

| 维度 | 路线 A：DSH 应用/插件 | 路线 B：独立 daemon |
|---|---|---|
| **起步速度** | ⭐⭐⭐⭐⭐ 1–2 周见效果 | ⭐⭐ 3–4 周才见效果 |
| **总工期到「可替代」** | 约 7–10 周 | 约 11–16 周 |
| 执行层 | 全部白拿（agent loop/工具/沙箱/权限） | 自己写 ACP 客户端（但只是一层） |
| 持久层 | 白拿 session 持久化 | 自己写日志 + 索引 + 跨进程信箱 |
| **编排层** | 借 agent-team 的 mailbox/task CAS | 全部自己写 |
| UI | ⭐⭐⭐⭐ 复用 `dsh-client-ui-*` 全套 | ⭐ 从零写 |
| **多 runtime** | ⭐⭐ 受限于 DSH 内核 | ⭐⭐⭐⭐⭐ ACP registry 加一行 |
| **稳定性** | 依赖 `experimental` 包，官方明说会变 | 全部自控 |
| **被锁死风险** | 高（架构 = DSH 的架构） | 低 |
| Windows | DSH 已是本地应用，天然满足 | 需自己做进程/管道/信号 |
| 隐私/离线 | 满足（DSH 本地） | 满足（更强，无任何上游依赖） |
| **共享 checkout 隔离** | agent-team 明确不做 → 要自己补 | 要自己补（同样） |
| 分发 | 走 DSH 插件市场，触达现成用户 | 独立产品，要做安装器 |
| 长期演进 | 被 DSH 的路线图牵引 | 完全自主 |

## 2. 成本拆解（人周）

| 模块 | A | B | 说明 |
|---|---|---|---|
| 事件日志 + 回放 + 迁移 | 2 | 3 | B 要自己处理跨进程 |
| 房间/频道/线程/消息 | 2 | 3 | A 可借 UI 槽位 |
| 成员册 + 生命周期 | 2 | 3 | |
| 任务状态机 + 看板 | 2 | 3 | A 可改造 agent-team 的 task board |
| 跨进程信箱 | **0.5** | **3** | ★ A 的最大红利 |
| 调度器 + 上下文装配 | 3 | 3 | 两者相同 |
| 熔断与预算 | 1.5 | 1.5 | 两者相同 |
| Reminder | 0.5 | 2 | A 可复用 `dsh-schedule` |
| Supervisor（进程管理） | 1 | 4 | ★ B 的最大负担 |
| RuntimeAdapter | 1 | 2 | A 只需包一层；B 要写 ACP 客户端 |
| 多 runtime 接入 | 3 | 1.5 | ★ B 的红利（ACP registry） |
| UI（房间/看板/活动流/diff） | **3** | **8** | ★ B 的最大负担 |
| Worktree 隔离 | 2.5 | 2.5 | 两者相同 |
| Electron 壳 + 托盘 | 1 | 1.5 | A 可复用 `tray/` |
| **合计** | **≈ 25** | **≈ 41** | |

**结论**：路线 A 大约省 **40%** 的工作量，省下的主要集中在
**跨进程信箱、UI、Reminder、Supervisor** 四块。

## 3. 关键判断点（决定性的三个问题）

### Q1：你能不能接受「架构就是 DSH 的架构」？

`dsh-experimental-agent-team` 的官方原文：

> 「**实验原型，无稳定性承诺**——本包公开发布，但孵化期间约定仍可自由变更。」
> 「单进程、共享 checkout……不提供 worktree、远端成员、merge 或文件锁。」
> 「扁平且不可变的 roster——只有 Lead 可以创建直接 teammate。」
> 「**mailbox 不保证跨进程 exactly-once**——不支持多个 harness 进程并发操作同一 Team。」

**这三条恰好都压在我们的核心需求上**：
1. 我们要的是「持久房间」，它是「会话内团队」——**这一层必须自己写**。
2. 我们要的核心卖点是「多 agent 并发写同一 repo 不打架」——**它明确不做**。
3. 我们要多 runtime 独立进程——**它不支持跨进程**。

**所以路线 A 并不是「白拿」，而是「白拿 L1 + 部分 L2/L3，自己补房间层和隔离层」。**
这个判断很重要：它意味着 **A 和 B 的差距比看上去小**。

### Q2：你的 agent 是「DSH 里的 subagent」还是「独立的 CLI 进程」？

- 如果是 **subagent**（进程内）→ 路线 A 顺畅，但一个崩全崩，且无法混用 Claude Code。
- 如果是 **独立进程**（`dsh --profile acp`、`claude-agent-acp`、`codex-acp`）→
  **你已经在走路线 B 的执行模型了**，那不如直接用路线 B 的架构。

**我强烈建议后者。** 因为：
- `dsh --profile acp` 现在就能用（你本机装了）
- ACP 生态有 40+ agent，Raft 支持的 runtime **几乎全覆盖**
- 独立进程 = 真正的多 runtime、真正的故障隔离、真正的独立 cwd

### Q3：你更怕「做慢了」还是「做歪了」？

- 怕做慢 → 路线 A
- 怕做歪、将来推倒重来 → 路线 B

考虑到你的目标是**完整替代 Raft 的全部用法**（这是一款产品，不是一次性工具），
我倾向于认为**「做歪」的代价更大**。

## 4. 调研后我的建议

### 推荐：路线 B 的架构 + DSH 作为第一个 runtime，用路线 A 做 2 周技术验证

```
第 0 步（1 周，验证）：用路线 A 的 A-M0 快速搭一个房间 UI，
                       跑通「@一个 agent → 它在文件夹里干活 → 结果回房间」。
                       目的不是交付，是验证编排体验的手感。
                       ★ 关键：这一步写的 UI 和调度器，要放在独立的包里，
                         不要直接依赖 DSH 的类型。

第 1 步（决策闸门）：问自己三个问题——
                      ① DSH 的 UI 槽位够不够撑起房间视图？
                      ② 我能不能接受 agent 是 in-process subagent？
                      ③ 我最想要的是「快」还是「不被锁死」？
                      按答案选 A 或 B。

第 2 步：按选定路线推进到 M1。
```

### 为什么是这个顺序

| 理由 | 说明 |
|---|---|
| **验证成本极低** | 路线 A 的 A-M0 只要 1–2 周，而且用的全是你已装的 DSH |
| **验证的东西是通用的** | 「怎么把一条房间消息变成一次 agent 行动」这个链路，A 和 B 完全一样 |
| **不会白做** | 调度器、上下文装配、熔断规则、领域模型，两条路线共享 |
| **DSH 在新的判断下不亏** | 即使最后走 B，DSH 也作为第一个 ACP runtime 继续用 |
| **避开最大风险** | 不会在没验证编排手感的情况下，先花 4 周写 daemon 和 UI |

### 一句话总结

> **领域模型只有一份，先把它写死；执行层用 ACP，所以路线 B 的成本已经大幅下降；
> 用路线 A 做 2 周验证，然后按「能否接受 DSH 架构」做最终选择。**

## 5. 无论选哪条，都必须先做对的三件事

这三件事做错，哪条路线都会失败：

### ① 领域模型先落地，别泄漏实现类型

```ts
// packages/protocol —— 两条路线共用，零依赖
export interface RoomEvent { seq: number; ts: number; kind: string; /* ... */ }
export interface RuntimeAdapter { /* 见 01/02 文档 */ }
export interface Room { /* ... */ }
```

**硬性约束**：`protocol` 包**不许 import 任何 DSH 类型**。
哪怕走路线 A，也要在自己的 `core` 里把 DSH 的 teammate 包一层。
这是你将来能不能换路线的唯一保险。

### ② 熔断从第一天就在

无限对话、成本失控是这类产品的头号杀手。`maxHops` / `maxTurns` / 预算 / `stopAll`
必须在 M0 就有，不能留到 M2。**哪怕默认值先写死。**

### ③ 上下文装配规则先写在纸上

「给 agent 喂什么」决定了成本上限。全量历史 = token 爆炸 + 互相污染。
按 `00-shared-spec.md` §3.4 那张表执行，**先定规则再写代码**。

## 7. 下一步具体动作

1. **读 `00-shared-spec.md`，把 §1.2 的能力表按你自己的优先级重排一遍。**
   你是唯一知道「我现在用 Raft 到底用哪些功能」的人——这张表决定了 MVP 边界。
2. **把 §3.1 的事件模型抄进一个 `packages/protocol` 骨架**（哪怕只有类型定义）。
3. **做 A-M0 的技术验证**（1 周）：
   - 建一个 `dsh-room` 插件骨架，注入 web profile
   - 挂一个最小的房间 UI 到 DSH 的槽位
   - 用 in-process subagent 跑通「@agent → 它读文件 → 回复」
4. **拿验证结果回来做最终决策。**

> 我的判断：你大概率会落在 **B**——因为你的目标是产品级的完整替代，
> 而且「多 agent 并发写同一 repo」这个最硬的卖点，agent-team 明确不做。
> 但先花 1 周验证，比现在猜要划算得多。
