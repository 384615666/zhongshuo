## 1. 必须修改的问题

### P0-1 · 缺少价值验证里程碑（结构性缺陷）

**问题**

- §20.3 的 M1 演示是「三个成员分别指出 fixture 中不同问题，互评修正至少一个错误」——
  这证明**管道通了**，不证明**答案变好了**，属于机制演示而非价值演示。
- 全文 24 节没有一节回答"多 AI 研讨是否优于单模型"。
- §20.2 要到 M3 才交付，即 **6–10 周之后**才第一次知道这东西有没有用。

**为什么这是 P0**

原 `README.md` 的原始判断与 `docs/cli-orchestration-plan.md` 的 M2 决策闸门，讲的都是
**先验证价值、再决定是否投入重工程**。v1 把顺序倒置了：先盖两个月基础设施，再验证。

**修改动作**

在第 2 节版本定义**之前**插入 `M-1 价值验证`，定义见 §6。**未通过不得进入 M0。**

### P1-5 · 用「调用次数」作主闸门，控不住成本

**问题**

§10.4 以调用次数为主要限制（DIRECT 6 / AUTO 20 / DELIBERATE 24），但：

- 最贵的两次是 **SYNTHESIS** 和 **RATIFY**——它们要读**全部报告 + 全部互评**。
  19 次调用里这两类的 token 占大头。
- 按实测：DELIBERATE 24 次调用，若走 claude 默认模式，**仅 claude 部分就 ≈ $2.27 起**，重上下文调用更高。
- v1 自己承认费用可能是 `unknown`（第 635 行），但**没有给出任何量级估算**。

**修改动作**

- 把 **token 预算**提升为一等闸门，调用次数降为辅助。
- 在 §10.4 增加一行"单次研讨成本量级估算"，基于本机实测数据。
- 明确：**调用次数上限不能防止成本失控**，因为每次调用的 token 量差 10 倍以上。

## 4. 需要新增的内容

### 4.1 新增 §2.0 · M-1 价值验证（最重要）

**目标**：在投入任何基础设施之前，回答"多 AI 研讨是否真的比单模型更好"。

**做法**

1. 选 **5 个真实问题**（需有客观对错，或可用明确标准判断质量）。
2. 对每题跑两条路径：

   | 路径 | 做法 | 成本记录 |
   |---|---|---|
   | 单模型 | 一个 claude 直接回答 | 调用数、token、美元 |
   | 三方研讨 | 独立 → 互评 → 整合（§6.1 流程，手工或薄脚本驱动） | 同上 |

3. **盲评**：交由一个**未参与**的模型判断哪份答案更好（顺序打乱，不告知来源）。

**判据（必须预先写死，防止事后找理由）**

- ✅ 通过：研讨版在 **≥ 3/5** 的问题上更优，**且** 平均成本 **< 3 倍**单模型
- ⚠️ 边缘：2/5 或成本 3–5 倍 → 缩小范围（如只用于高风险决策）
- ❌ 不通过：≤ 1/5，或成本 > 5 倍 → **停止，不进入 M0**

**产出**：一份对比记录 + 明确结论。**这一步不做，后面 6–10 周不应开始。**

把 §8 的实测数据（见本文附录 A）写进正文，作为适配器开发的起点事实。

### 4.3 新增附录 · 本机环用事实

CLI 版本、可用模型、网关地址（脱敏）、代理 DNS 特性等，

## 5. 建议的里程碑重排

```
M-1  价值验证（3–5 天）        ← 新增，最高优先级，未过即停
  ↓ 通过
M0   技术闭环（1–2 周）
     打开目录 → 指定成员 → 读真实文件 → 回流 → 持久化 → 能停止
     范围收敛：不含 daemon 恢复 / 不含多成员 / 不含 outbox
  ↓
M1   协作原型（2–3 周）
     共同研讨：独立 → 互评 → 分歧 → 整合（含 §6.2 的阶段过滤）
  ↓ 此处才引入 SQLite/outbox/daemon 全套可靠性设施
M2   功能 Alpha（4–6 周）
     自动分工 + 两种 runtime + 单写者修改
