## 这是桌面客户端，不是网页

形态按 §8.2「桌面 = Electron」实现：

| 桌面能力 | 实现位置 | 验证方式 |
|---|---|---|
| 原生窗口（无边框 + 自绘标题栏） | `electron/main.mjs`（`frame:false`）+ `src/components/TitleBar.tsx` | `verify-desktop.mjs` |
| 系统托盘（左键切换显示/隐藏、右键菜单） | `electron/main.mjs` 的 `buildTray()` | 托盘菜单含"后台任务 N 个" |
| 关闭窗口 = 缩到托盘继续运行 | `close` 事件 `preventDefault()` + `hideToTray()`（决策 43） | 关闭后窗口数仍为 1，应用未退出 |
| 显式退出前展示正在终止的任务数量 | `requestQuit()` 用原生 `dialog.showMessageBox` | 退出菜单触发 |
| 原生目录选择器 | `dialog.showOpenDialog`（§8.2） | 调用后 1.8s 未返回，证明系统模态对话框已弹出 |
| 单实例锁 | `app.requestSingleInstanceLock()`（§8.3） | 第二个实例聚焦既有窗口 |
| contextIsolation 受限桥接 | `electron/preload.cjs`（§16.2） | 渲染层 `require/process/module` 均为 undefined |
| 托盘提示同步运行态 | `reportRuntime` IPC | 顶栏任务数 → 托盘 tooltip |

浏览器仍然可用（`pnpm run dev`），但**能力不同**：没有托盘、没有窗口控制、没有原生目录选择器。界面上会如实标注「浏览器宿主」，不假装有这些能力 —— 这也是验证"是不是真桌面"的依据。

## 运行

```bash
pnpm install
```

**桌面客户端**（推荐，这才是成品形态）：

```bash
pnpm run build          # 构建渲染层
pnpm run desktop        # 在原生窗口里启动
```

开发模式（渲染层热更新 + 桌面窗口）：

```bash
pnpm run desktop:dev
```

**浏览器模式**（同一套渲染层，能力降级）：

```bash
pnpm run dev            # http://localhost:5280
```

**验证与截图**：

```bash
pnpm run desktop:debug  # 带调试端口启动，另开终端执行下面两条
node scripts/verify-desktop.mjs   # 桌面能力验证 8 项
node scripts/shot-desktop.mjs     # 截真实 Electron 窗口 → screenshots-desktop/

# 浏览器用例需要先起 dev server（注意端口与 Electron 调试端口隔离）
pnpm dev --port 5284
node scripts/shot.mjs http://localhost:5284    # 浏览器逐页截图 → screenshots/
node scripts/smoke.mjs http://localhost:5284   # 交互冒烟 27 项
```

要求 Node 18+。截图与验证脚本复用本机 Chrome/Edge headless，不额外下载浏览器。

> **端口约定（踩过的坑）**：Electron 调试端口是 **9333**（`desktop:debug`）；
> 浏览器用例 `smoke.mjs` 用 **9334**（可用 `ZS_SMOKE_CDP_PORT` 覆盖），两者必须错开。
> 其余专项各自独占端口：9335 视觉（`verify-visual*` / `verify-workspace-preview` / `verify-quote`，需先起一个 headless Chrome）、9336 减负、9337 缩放探针、9338 私信输入区、9339 默认交给 AI、**9340 侧栏状态矩阵（`verify-nav-marks.mjs`）、9341 侧栏状态截图（`shot-nav-marks-states.mjs`）** —— 后两个自己拉起 headless 浏览器并指向 dev server（5284）。
> 早期两者都是 9333：Chrome 抢不到端口时 `cdpTargets()` 会连上 **Electron 窗口**，
> 然后把它导航到 `localhost:5284` —— 真实窗口变白屏，之后所有用例连锁误判失败
> （表现为"整套用例突然全红"，但代码其实没问题）。
> 若窗口已被导航走，用 `node scripts/restore-window.mjs` 导回打包产物。

主题可用 URL 固定：`?theme=dark`。`?recovery=0` 抑制启动恢复弹窗自动弹出。

> **仓库**：本工程与设计文档同仓，根目录是 `D:\zhongshuo`（分支 `main`，2026-09-25 初始化，初始提交 `84a2250`）。`node_modules/`、`dist/`、截图目录与 `archive/` 不入库 —— 新克隆后先 `pnpm install && pnpm run build` 再跑桌面宿主的用例与截图；改动前的基线改用 Git 提交记录，不再需要手工快照。

### 筛选控件的统一规格（用户反馈后定稿）

用户指出：「下拉选择的组件样式你都没统一，而且应该放左边，不然你在左边点击菜单后鼠标又挪去右边操作很反直觉」。

核实确认这是**我这轮引入的缺陷**：`.field.inline` 这个类被四个页面使用，却**从未定义过样式**，于是退化成块级 `.field`（label 独占一行）并被子项 flex 拉伸 —— 实测同一行出现 **33px / 70px / 33px 三种高度**，且控件挂在页头右侧（离侧栏最远）。

现在统一为 `.page-filters` 筛选行，规则固定为：

| 约定 | 说明 |
|---|---|
| **位置** | 页面级筛选一律放内容区**左上角**，不塞进 `.page-head-actions`（页头右侧只放"动作按钮"，如添加成员/新建） |
| **高度** | 行内所有控件同高 30px（下拉 / `.seg` 分段 / `.btn.sm` 都归一到 30，此前分别是 30/33/25） |
| **标签** | 每个控件都带 `.field-label`（如"范围""项目""房间""作者"），不用裸下拉 |
| **宽度** | 不在 JSX 里写 `style={{width:N}}`；下拉按内容宽（`min 132 / max 260`），搜索框可用 `flex` 撑满 |
| **说明** | 只读计数/范围说明用 `.filter-note`，与控件同基线 |
| **不合并** | 数据筛选（对整页生效）与表单字段（如成员模型、房间协调者）是两回事：后者仍在设置卡里用竖向 `.field` |

由 `verify-nav.mjs` 的「筛选控件同高且靠左」逐页断言（八个页面 + 页头不再残留筛选下拉），避免以后再漂移。

本轮实现时**踩到并修掉的真问题**（都留了回归断言）：

1. **单项目页不同步焦点** —— URL 里有 `projectId` 的页面（项目/房间/合页/成员/私信、以及看板 `scope=project`）此前不会更新顶栏当前项目，会出现"顶栏写着众说、页面在操作另一个项目"。现在统一走同一个 `focusProject` 动作，并顺带承担**深链补选**（进入隐藏项目的合法深链 → 自动加入可见集合 → 聚焦 → 轻提示）。
2. **`replace` 重定向与路由订阅的竞态** —— `history.replaceState` 不触发原生 `hashchange`，代码里是手工 dispatch 事件；而 React effect 是**子先父后**，声明式重定向（子组件）先跑完，`App` 里的监听还没挂上，那个事件被丢掉：地址栏已是新路径、界面却仍按旧路径渲染（实测 `/task/:id` 重定向后房间与线程面板整块不出现）。在 `useHashRoute` 订阅处补读一次即可覆盖该窗口。
3. **写入租约是全局单例，跨项目串状态** —— `writeLock` 原为 `AppState` 上的单个对象，没有 `projectId`；于是打开 notes-vault 的文件页会显示**众说任务 #13** 的"当前写入锁"（截图时发现）。而 §10.3 定义锁域是"同一物理原目录"，不同项目本就是不同目录。已改为 `writeLocks: Record<projectId, Lock>`，房间页/文件页/项目设置三处都按当前项目取；`stopTask` 与 `stopAll` 也只释放对应项目的租约。
4. **`?section=project&projectId=X` 不同步焦点** —— 焦点同步的判定只认 `?scope=project` 与路径里的 `/project/:id`，漏了**设置页的项目设置段**。实测 `/settings?section=project&projectId=data-backfill` 显示的是"项目设置 · **众说**"——地址栏与页面作用对象不一致，正是交接文档点名要避免的那类缺陷。已补上该写法，并让设置页**自己按 URL 的 projectId 取项目**（不只依赖 effect 同步，避免首帧还没同步完时显示错项目）。现在七种带项目的 URL 写法都有断言。
5. **返工写操作绑定的是全局当前项目** —— `publishRework(projectId, taskId)` 的调用处传的是 `s.activeProjectId`。若用户在**另一个项目上下文**里打开该任务（聚合看板、跨项目搜索、深链），新产生的验收待办就会带上**错误项目的 projectId**，进而"点待办补选项目"会跳到错的项目。已把签名改为 `publishRework(taskId)`，项目归属**从任务实体推导**，从根上消除这类误用（§17.7 的"写操作绑定按钮所属对象"）。
6. **筛选控件样式不统一、且位置反直觉**（用户反馈）—— 见上节「筛选控件的统一规格」：`.field.inline` 从未定义样式导致三种控件高度，且控件在页头右侧。
7. **两条验收用例当时无法被验证**（数据缺口，不是代码 bug）：
   - §9.4「非 Git 文件树与预览可用」—— 当时唯一的非 Git 项目（legacy-docs）目录也是失效的，实测树恒为 0 个节点。**新增 `notes-vault`（`proj_notgit_04`）**：目录正常、不是 Git 仓库、有成员/房间/已完成任务，并带自己的 mock 文件树与"整目录快照"前像的改动集。

### 应用内顶栏删除（第二十六批）

用户提出"这条顶部栏不要了，项目选择栏放到左侧边栏最顶部，搜索放在左侧边栏搜索菜单的左边小按钮，
其他的都可以收到设置里"。照做，并按职责分到三处：

|---|---|---|
| 折叠/展开侧栏 | **自绘标题栏最左** | 侧栏折起来后自身不可见 —— 搬进侧栏会造成"折起来再也打不开"的**死状态**（`sidebarOpen` 默认 true）。标题栏属于窗口外壳，永远可见 |

**「项目全停」的落点变更（第二轮反馈）**：用户提出"还是放到设置里防止误触吧"。
移是移了，但**放进「项目设置」而不是应用设置** —— 它是**项目级**动作，
而 §17.8 明确要求应用设置"不含项目配置"，放应用设置会自相矛盾。
新位置在项目设置页底部的 warning 色「高级操作」带里，且保持两步：
先点「项目全停」，再在确认弹窗里点「停止本项目全部任务」，弹窗会先列出将影响的任务与 turn 数。

> 第一轮我曾把「项目全停」放在侧栏底部，理由是"紧急停止埋在设置里不好找"。
> 用户更看重误触风险 —— 这个取舍由用户定，且移入项目设置后仍有二次确认兜底，
> 所以接受。破坏性动作（重置原型数据 / 退出）在应用设置里也各自放进「高级操作」警示带。

**折叠时补一个当前项目提示**：侧栏收起后，项目选择器和项目列表都不可见了，
所以标题栏在折叠态会显示当前项目名（点击即展开侧栏）—— 否则用户看不到"我在哪个项目"。

**顺带修掉一个跨项目缺陷（实测发现）**：`stopAll` 里写的是
`members: st.members.map((m) => ({ ...m, workState: 'stopped', ... }))` ——
**完全没按 projectId 过滤**。于是停在众说会把 data-backfill 的成员也标成"项目全停"，
而那个项目的任务其实还在跑。`turns` 同样没按项目过滤（归属要 turn→thread→room→project 才能判）。
这与更早修过的 `writeLock` 全局单例是同一类问题：**项目级动作污染其他项目**。
现在只改本项目成员与本项目 turn，并加了回归断言锁住（停 A 后 B 的成员状态必须逐字不变）。
另外确认弹窗里的计数也改为**按本项目**重算 —— 原来那个 `runningCount` 是全局的，
摆在"只停本项目"的弹窗里会显示别的项目的数字。

**顺带清掉两处死代码/缺陷**：

1. **账号菜单成了打不开的浮层** —— 它原来由顶栏最右的头像打开，顶栏删掉后就没有入口了。
   里面的三项已各有正当去处（应用设置 / 重置原型数据 / 退出），浮层本身连同
   只服务于它的 `userMenu` 状态与 `Avatar`/`ProtoFlag`/`resetStore` 等导入一并删除。
2. **`--warning-text` 是我上一轮自己造的、并不存在的 CSS 变量** —— 这轮用在 3 处
   （侧栏目录失效提示、标题栏恢复检查），全都会退化成继承色。已改为 tokens 里真实存在的
   `--warning`。

**一个我自己引入又修掉的视觉回归**：把"全局搜索"塞进「搜索与收藏」那一行后，
该行的图标被推到 x=46，而其余三个功能入口在 x=16 —— 视觉上「搜索与收藏」变成了
缩进子项，层级读起来是错的（实测 16/46/16/16）。已统一把四个功能入口的图标对齐到
x=32 这一列（与项目行齐平），房间仍是 42px 保持"缩进在项目下"。回归断言也改成
"功能与项目同列、房间再缩进"，而不是原来那个会掩盖问题的 `proj > func`。

### 项目设置与应用设置分离（第十六批 §17.8 / RT-27）

用户提出："项目的设置合并一个页面后，就不要和整个软件的设置在一起了，单独每个项目一个设置入口，
不然整个软件的设置里同时混有项目的就很奇怪？" —— 同意，并按要求拆开。

| | 入口 | 内容 |
|---|---|---|
| **项目设置** | 侧栏每个项目行的 **⋯ → 项目设置**，路由 `/project/:projectId/settings` | 任务交付、协作限制、文件修改 |
| **应用设置** | 底部「设置」，路由 `/settings?section=general` | 通用、执行工具、设备与局域网、诊断与帮助 |

心智模型变直接了：**想改某个项目，去那个项目旁边；想改整个软件，点底部设置。**

**项目设置单页**：标题为「项目名 · 项目设置」+ 真实路径，**不放项目下拉**（切项目走顶栏/侧栏），
也**没有页内二级分类导航** —— 三节直接排在一页。内容宽度收在 920px（原来卡片横跨整屏，
一行小开关配一整屏宽的大卡片）。每行统一为**左名称与说明、右控件**。

两条入口的高亮互斥：项目设置页时底部「设置」**不高亮**，应用设置页才高亮 —— 不让两个入口
同时看起来是当前页。

**「⋯」按钮**：独立按钮，点击**只打开菜单**，不切换项目、不跳房间、不折叠。
hover / focus-within / 菜单打开 / 正处该项目设置时显形；键盘可 Tab 到；触屏（`@media (hover: none)`）
常驻可见 —— 不能只靠鼠标发现。

**这一轮修掉的三个实测确认缺陷**（前两个是另一位 AI 复核时指出的，我逐条复现确认）：

| 缺陷 | 实测证据 | 修法 |
|---|---|---|
| **单写者承诺过强** | 正文写着「撤销**一定可靠**」—— 与 §14.2/§14.5 冲突（同目录外部编辑仍可能破坏撤销） | 改为「减少任务之间的并发冲突；其他写入任务排队。**撤销前仍会检查文件变化**」 |
| **通用设置是假开关** | 点击前后 `[true, true, false]` **完全不变**，只弹 toast —— 用户会以为设置坏了 | 新增 `AppState.appSettings` 真实内存状态 + `setAppSetting`，点击即变并留痕；同时用「原型模拟」标签如实说明没有系统桥接 |
| **数字输入清空被钳回** | 输入框原为受控 + `Number(v) \|\| 20`：清空后立刻变回 20，无法把「20」改成「45」 | 改为本地草稿 + 失焦/Enter 校验提交；Escape 恢复；无效值不写入并显示行内错误 |

**路由规范化**（§17.8 兼容表）：先规范化 URL，**再**同步焦点 —— 禁止"看到任意 `query.projectId` 就切项目"。
这条很关键：一个被改过的应用链接（如 `/settings?section=runtime&projectId=B`）若据此切焦点，
会悄悄把当前项目换掉。实测确认现在不切、且参数被清除。

| 旧链接 | 规范化到 |
|---|---|
| `/settings?section=project\|collab\|budget&projectId=A` | `/project/A/settings?anchor=collab` |
| `/settings?section=write&projectId=A` | `/project/A/settings?anchor=write` |
| `/settings`、`section=app\|general` | `/settings?section=general`（清除多余 projectId） |
| `section=runtime\|lan\|diagnostics` | 对应应用分区（清除 projectId） |
| `section=errors` | `section=diagnostics&anchor=errors`，自动展开速查 |
| `section=reminders` | `/activity`（提醒仍在待我处理） |

项目类旧链接**没带 projectId** 时：只有存在有效当前项目才补上并规范化；否则提示从项目菜单进入 ——
**不替用户挑第一个项目**。显式无效 projectId 则直接报错，且不渲染任何写入控件。

实施中另外自己发现并修掉两处：

1. **`section=errors` 重定向后速查表不展开** —— 判定用的是 `raw === 'errors'`，但路由层已把它改写成
   `section=diagnostics&anchor=errors`，于是永远为 false（实测 `aria-expanded="false"`、找不到
   `WORKSPACE_BUSY`）。改为认 **`anchor=errors`**，并在展开后滚到该节。
2. **非 Git 项目的适用性声明被我在重写时丢掉** —— 「与是否 Git 仓库无关」这句对非 Git 项目用户
   是"这个开关对我有效吗"的直接回答，已补回。另外把「目录已失效但配置仍可查看」与"项目不存在"
   分开处理（前者可看可改配置并提示目录不可写，后者直接报错）。

### 设置页重构（第十五批，已被上面的分离取代）

> 保留此节只为说明**当时的诊断仍然成立**（按钮排不像设置、满屏设计编号、术语直出、
> 设置/状态/文档混页、危险项未隔离、项目设置拼盘名）。第十六批把项目部分整体移出，
> 应用部分沿用当时的左导航树形态但只剩四个应用分区。
> 其中「不建顶级高级区、危险项就地降权」的做法保留：设备页底部仍有 warning 色「高级操作」带。

原来是"设计文档展示橱窗"，不是给人用的设置页。核实确认的具体问题：

| 问题 | 实测 |
|---|---|
| 导航是按钮排，不像设置 | `seg` 切换 + 一排 `.btn ghost/primary`，没有"我在设置树哪一节"的位置感 |
| 满屏设计编号 | 卡片标题就是「任务验收（v1.12 §10.5 / RT-25）」「写入并发策略（v1.9 §14.1 / E20）」「并发上限（决策 12）」「恢复边界（REM-03）」 |
| 术语直出 | 字段名当标题：「缺席容忍 absentGrace（分钟）」「单轮硬保护 turnDeadline」 |
| 设置/状态/文档混一页 | 可改开关 + 只读租约与 kv 表 + 19 个错误码表平铺 |
| 危险项没隔离 | 「并行写入·风险自负」「吊销设备」「测试安全边界」与「开机自动启动」视觉权重相同 |
| 项目设置只有一子区却叫拼盘名 | 「任务验收与并发」把验收、并发、循环预算塞在一起 |

> **以下三小节均为第十五批的当时做法，第十六批已改动**：
> 项目部分（任务与协作 / 文件写入安全）整体移出为独立项目设置页；
> 应用部分不再有「当前项目」组、项目选择器，「错误码速查」并入「诊断与帮助」。
> 保留原文是为了说明当时的诊断依据，**不要照着它实现**。
> 仍然有效的是三条原则：用户语言标题 + 一句影响说明、可改/只读/帮助分开、危险项就地降权。

改为**左侧分区导航 + 右侧内容**（这一形态沿用；第十六批收窄为只剩应用分区）：

```
（第十五批当时的形态，第十六批已变）
当前项目   任务与协作 · 文件写入安全        ← 已移出为独立项目设置页
应用       通用 · 执行工具 · 设备与局域网
帮助与诊断 诊断与日志 · 错误码速查          ← 速查已并入「诊断与帮助」
```

三条落地原则：

- **用户语言的标题 + 一句"改了会怎样"**。设计依据移进 `<details>` 折叠块与 `title` 悬停。
  但**保留设计文档的正式术语与内部字段名**（`absentGrace` / `turnDeadline` / `写入并发策略` /
  `writeConcurrencyPolicy`）在说明里 —— 原型要能对照设计文档，删掉就失去可追溯性；
  它们出现在提示行与折叠块，不再当标题。
- **可改 / 只读 / 帮助分开**：只读状态收进「当前状态」卡并标 **只读**；错误码表归入「帮助与诊断」。
- **危险项就地降权**，而不是建一个顶级「高级」区 —— 见下。

**为什么没有独立的「高级」顶级分区**（与另一位 AI 方案的分歧）：建顶级区会把
「单写者 / 并行写入」这组**互斥单选拆到两页**，用户无法同屏对比两个互斥选项；
也违反 RT-22「界面必须持续显示当前策略」。改为在各区**底部**放 warning 色的
「高级操作」分隔带（设备吊销 / 令牌轮换 / 安全自测集中于此），既隔离又不用跨页。

**「提醒」移出设置**：它不是配置而是内容管理。落到「待我处理」页内并**独立成节**，
不混进待办流 —— 待我处理是"别人给我的、要我现在响应的"收件箱，提醒是"我设的定时器，
到点唤醒某个成员"，方向相反。界面写明这个区别（与另一位 AI"并进待办流"的建议不同）。

**旧 URL 全部兼容**（旧深链不死）：

| 旧/文档写法 | 现在打开 |
|---|---|
| `?section=project&projectId=X` | 任务与协作（§17.7 记录的写法） |
| `?section=budget&projectId=X` | 任务与协作 |
| `?section=app` | 通用 |
| `?section=runtime` | 执行工具 |
| `?section=lan` / `diagnostics` / `errors` | 对应分区 |

### Git 页（§14.6，用户要求新增）

不是通用 Git 客户端，而是**把 Git 接到协作流程上**：每条提交、每个分支都能回溯「哪个任务、哪个改动集、谁批准的」——通用客户端没有这层信息。

页面分三个分区：**工作区**（冲突 → 已暂存 → 按任务分组的待提交改动 → 你自己的改动）、**历史**（提交 + 关联任务 + reflog）、**分支与远端**。

**两条既有边界没有因为「完整客户端」被放宽**，这是本次实现最需要说清的部分：

| 边界 | 文档 | 本页怎么体现 |
|---|---|---|
| 不 stash / reset / 自动提交用户原有改动 | §14.2 | 用户改动**单独分组**并明确说明；「暂存本任务改动」**默认跳过** `userPreExisting` 文件（有断言锁定） |
| 不做 `reset --hard` / 强制 checkout / 删除用户项目 | §14.5 | 撤销提交走 reflog **软回退**：内容回到工作区，文件一个都不删 |
| 冲突不自动应用，保留三方内容 | §14.2 | 冲突**阻止提交**；只给 base/ours/theirs + 手动编辑，**没有**整文件「一键全部用某边覆盖」按钮 |
| 凭据缺失不假装成功 | §16.5 | 远端凭据状态常驻可见；缺失时推送/拉取按 `AUTH_REQUIRED` 明确失败 |
| agent 产出不静默生效 | §14.3 | agent 提交带「待审阅」+「agent 提交」标记，验收或退回；退回时内容回工作区 |

另有一处容易搞混、已在类型与文档里写明：**Commit 与 ChangeSet 是两个维度**。ChangeSet 记录"改动是否已应用到原目录"，commit 记录"内容是否进入版本历史"，提交**不改变** ChangeSet 的 `status`，界面不互相推断。

### 可选任务验收（§10.5 / RT-25，第十四批）

习惯 Git 的用户可以直接「看 diff → 暂存 → commit → push」，不必接触验收流程；希望人工确认 AI 交付的人可以在项目设置里打开「任务验收」。

| | 关闭 | 开启 |
|---|---|---|
| AI 满足交付要求后 | 任务 DONE，显示「**已完成 · 无需验收**」 | 任务进入待验收，显示「待验收」 |
| 验收待办 | 无 | **每个用户任务的当前交付 1 条**（多个 Agent / 文件 / commit 也只算一条） |
| 未满足交付要求 | 按实际失败/阻塞处理，不伪装成功 | 同左 |

几个容易被做错、已用断言锁住的点：

- **开关只影响新任务。** 创建任务时把策略快照进 `Task.reviewPolicy`；改设置不动已有任务，也不清理已产生的待验收卡。关闭时提示「还有 N 个已有任务按原规则等待验收」，不提供隐式「全部验收通过」。
- **`reviewPolicy` 不再由 `access=modify` 推导。** 原实现是 `access === 'plan' ? 'auto_deliver' : 'user_review'`，把「要不要人工验收」和「这次改不改文件」绑死了 —— 任何修改类任务都强制进验收，习惯 Git 的用户绕不过去。现在两者解耦。
- **「无需验收」≠「已验收」。** 两者是不同状态，界面用词与颜色都不同，不互相冒充（任务 #11 是旧报告任务，显示前者）。
- **验收决定必须针对具体版本。** 校验 `deliveryId + revision + manifestHash`；返工后旧页面上的按钮会因版本不匹配而失败并提示重新查看，**不会**批准新结果。
- **返工替换而非追加。** 新版本递增 revision 并替换当前待办，旧版与意见保留可查；「要求修改」必填意见，且**不** reset、**不**撤销提交、**不**删除成果。
- **验收不碰文件与 Git。** 通过后不改 `ChangeSet.applicationStatus`、不 stage/commit/push，也不顺带批准权限请求。

**三处旧行为已移除**（交接文档 §4 要求）：

1. 「文件与改动」页原本「验收单个改动集就把整个任务标 DONE」—— 一个任务可有多个改动集，验收其中一个就完结任务属语义错位。现改为指向所属交付。
2. Git 页的「验收这个提交」与 commit 级待审阅队列 —— 按 commit 逐个验收会造出多条待办，且「退回提交」容易被实现成软回退，与 §14.5 混淆。`git.reviewCommit` 保留为**已废止提示**，绝不暗中映射成任务验收或 Git 回退。
3. `ChangeSet.status` → `applicationStatus`，只表示文件是否已应用，与人工验收彻底解耦（旧的 `pending_review` 不能直接映射成 `not_applied`，因为原目录可能已写入）。

顺带修掉一个真实死路：归档私信的输入框提示「取消归档后才能发送」，但「取消归档」当时只藏在 ⋯ 会话设置弹窗里。现在归档态的输入条直接提供该按钮。

#### 占位卡片：`当前阶段` 是怎么来的

用户截图里问「阶段里的**当前阶段**又是啥」。实测（`node scripts/verify-progress-card.mjs`）确认：
**6 张进度卡全部渲染的是兜底字符串**，因为 `payload.progress` 在整个代码库里**从未被写入过**：

```tsx
// 旧实现：p 永远是 undefined，所以三个值全是兜底的
const p = message.payload?.progress;
<div className="small faint">阶段</div>
<div className="strong">{p?.stage ?? '当前阶段'}</div>   // 恒为「当前阶段」
<div className="small faint">成员</div>
<div className="strong">{memberName ?? '成员'}</div>     // 恒等于消息头已写的作者名
```

三行里两行没有信息量：作者名左边头像旁已经写了，`当前阶段` 是恒定的兜底字面量。
这类"占位即输出"比缺字段更糟——它让界面看起来在报告状态，实际什么也没报告。

处理：
1. **删掉整张卡片**，进度正文直接按普通消息渲染（内容一句没少）。
2. `ProgressCard` 类型收窄为**只承载异常状态**（`blocked` / `late`），并写明为什么不要
   `summary`（正文即摘要）、`stage`（阶段推进由系统卡标注）、`running/done/waiting`
   （消息发出来就已经是过去时，执行状态属于 run/turn 而不属于某条消息）。
3. 「（迟到纳入）」原本混在成员正文开头，改为结构化标签——它是程序附加的运行状态，不是成员说的话。
4. 顺带删掉随之失效的 `.progress-grid` / `.progress-card` 样式，不留死代码。

## 这是什么，不是什么

**是**：一套能真实点击、真实改内存状态、真实给出回执的高保真界面。写操作走 `src/data/actions.ts`，命名逐字来自 §15.2 的 UI 命令清单；点下去会看到状态真的变（任务进 CANCELLED、rosterRevision 推进、锁被释放、未读清零），并记进「待我处理 → 原型写入留痕」面板。

**不是**：没有 daemon、没有 SQLite、没有 runtime 适配器。所有数据来自 `src/data/seeds-*.ts`，刷新即回到种子。不写盘、不启动任何 CLI、不解析目录身份。界面上凡是做不到的地方都写明了"原型不……"，不假装已经跑过真实模型。

## 已知边界

- **业务内核仍是原型**：没有 daemon、没有 SQLite、没有 runtime 适配器。写操作改内存，刷新即回种子。
  桌面外壳（窗口/托盘/原生对话框/单实例）是真的，业务状态是假的 —— 这两者不要混为一谈。
  按 §8.1，真实版本里 Electron 主进程应把窄接口转发给本地 daemon，原型阶段省略了这一步。
- **托盘图标是运行时生成的**：用内联 SVG 转 PNG，避免依赖外部资源文件；正式版应放入平台图标集。
- **未做打包**：`pnpm run desktop` 直接以开发形态启动。要出 Windows 安装包需接 electron-builder（未配置）。
- 研讨矩阵、diff、用量、诊断都是静态样例数据，不做真实计算。
- 「打开文件夹」会真的调起系统对话框并返回你选的路径，但**不会真的扫描磁盘**（不做目录身份解析与索引）。
- 数据为演示一致而设计：任务 #12 的争议、迟到、预算余额互相自洽，便于逐条对照文档走查；不代表真实运行规模。
- 输入条为**单行不折行**布局：窄窗靠收窄间距、隐藏次要说明来保证「发送」按钮始终可见。
- 页面文件只导出组件，不再二次导出 store/format 的符号（否则 Vite Fast Refresh 会因混用导出而整页失效）。
